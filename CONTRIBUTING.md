# Правила работы над TourCRM

## Рабочая модель

Разработка ведётся через GitHub Issues. Приоритет задач определяется их порядком в текущем рабочем backlog.

Стандартный жизненный цикл задачи:

`Issue → анализ → реализация → автоматические тесты → проверка → закрытие`

Следующая задача не начинается до завершения текущей задачи, кроме случаев, когда зависимость или блокирующее обстоятельство явно зафиксированы в Issue.

## Критерии завершения

Issue считается выполненной, когда:

- реализованы все acceptance criteria;
- код соответствует архитектурным правилам проекта;
- автоматические тесты добавлены или обновлены там, где это необходимо;
- локальные проверки завершились успешно;
- CI завершился успешно;
- изменённая документация актуализирована;
- нет известных регрессий, относящихся к задаче.

## Git workflow

Основная ветка — `main`. Изменения, требующие разработки, выполняются в отдельных ветках.

Рекомендуемый формат:

- `feature/<issue-number>-<short-name>` — новая функциональность;
- `fix/<issue-number>-<short-name>` — исправление;
- `docs/<issue-number>-<short-name>` — документация;
- `chore/<issue-number>-<short-name>` — технические изменения.

Изменения попадают в `main` через Pull Request после прохождения автоматических проверок.

## Pull Request

PR должен:

- ссылаться на соответствующий Issue;
- описывать реализованное поведение;
- перечислять выполненные проверки;
- явно указывать известные ограничения, если они остались;
- не содержать несвязанных изменений.

## Тестирование

Автоматическое тестирование является обязательной частью рабочего процесса. Набор тестов будет определён отдельно для frontend, backend, API, базы данных и интеграционных сценариев.

## Документация

Архитектурные решения, бизнес-правила и значимые изменения должны отражаться в `docs/`. Архитектурные решения, которые влияют на структуру системы или ограничивают будущие варианты развития, фиксируются как ADR.

## Персональные данные

Проект обрабатывает данные детей, родителей и сотрудников клуба. Нельзя добавлять персональные данные в исходный код, тестовые фикстуры или логи без необходимости. Детальные требования безопасности и защиты данных находятся в `docs/` и будут уточняться по мере проектирования.
