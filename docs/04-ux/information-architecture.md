# TourCRM — Information Architecture

## 1. Назначение

Документ определяет информационную архитектуру пользовательского интерфейса TourCRM. Он является контрактом для последующего UX/UI-проектирования и реализации frontend.

Документ не фиксирует конкретную визуальную тему, цвета, библиотеку компонентов или пиксельные размеры. Он фиксирует структуру, навигацию, экраны, основные состояния и ролевую доступность.

## 2. Принципы

1. Один адаптивный web-интерфейс используется на desktop, tablet и mobile.
2. Навигация определяется ролью пользователя и доступными permissions.
3. Недоступные разделы не должны считаться только визуально скрытыми: API остаётся источником проверки полномочий.
4. Одинаковые доменные объекты должны иметь единообразный UX во всех модулях.
5. Для критичных действий используется понятное подтверждение и отображение результата.
6. Интерфейс должен поддерживать loading, empty, error, forbidden и offline/unavailable states.
7. Длинные таблицы должны иметь поиск, фильтрацию, сортировку и пагинацию.
8. Формы должны валидировать данные на клиенте для UX, но серверная валидация является обязательной.
9. Mobile-first подход применяется к критичным пользовательским сценариям.
10. Доступность и понятность интерфейса имеют приоритет над визуальной сложностью.

## 5. Dashboard

Dashboard является роль-зависимым.

### 5.1 Administrator

Показывает:

- ближайшие занятия;

- уведомления/ошибки интеграций;
- сводные показатели клуба.

### 5.2 Instructor

Показывает:
- ближайшие занятия;
- свои группы;
- мероприятия, где инструктор ответственен;
- требующую отметки посещаемость;
- ближайшие походы;
- задачи/напоминания.

### 5.3 Member

Показывает:
- ближайшее занятие;
- своё расписание;
- предстоящие мероприятия;
- последние достижения;
- документы/согласия, требующие действия;
- системные уведомления.

### 5.4 Guardian

Показывает:
- секцию «Мои дети» с текущими детьми, к которым Guardian имеет доступ;
- ближайшие занятия детей;
- мероприятия;
- документы/согласия;
- уведомления;
- финансовые обязательства, если разрешены и модуль включён.

#### Guardian: «Мои дети»

«Мои дети» является **контекстной секцией Home/Dashboard**, а не отдельным пунктом глобальной навигации.

Для текущей реализации frontend использует canonical endpoint `GET /api/v1/me/children`, который определяет Guardian по authenticated session и возвращает только текущих разрешённых детей в предусмотренной API projection.

В рамках текущего решения:
- новый глобальный navigation item «Дети» не добавляется;
- отдельный route `/my-children` не создаётся;
- ProfileMenu не используется как entry point для «Мои дети»;
- frontend не вводит новые permissions/scopes;
- frontend не предполагает наличие у Guardian дополнительных данных сверх canonical `/me/children` projection.

Это решение supersede-ит более ранние формулировки, в которых «Children» указывался как отдельный navigation item Guardian.

### 6.4 Текущая реализация: мастер создания человека и вкладки Person Detail (TH-0116, Issue #150)

§6.2 описывает целевую, более широкую архитектуру профиля (включая ещё не реализованные разделы — финансы, достижения, квалификации и т.д.). Текущая реализованная поверхность People — это guided-мастер создания и пять вкладок Person Detail, без отдельного технического понятия «Членство» на UI-уровне:

**Создание человека** — вместо одношаговой формы используется мастер: Шаг 1 (Фамилия/Имя обязательны; Отчество/Email/Телефон/Адрес — опционально) → Шаг 2 (выбор одной начальной роли: Администратор/Инструктор/Участник/Родитель) → contextual-шаг, зависящий от роли (группы для Инструктора — 0..N; группа для Участника — обязательно 1..N; дети для Родителя — обязательно 1..N; для Администратора шаг отсутствует). Учётная запись создаётся автоматически всегда, без отдельного шага в мастере — см. `docs/05-api/people-api.md` §6.1/§24.2.1.

**Вкладки Person Detail**: Обзор | Группы | Представители | Роли | Учётная запись.

- «Группы» заменяет прежнюю пользовательскую вкладку «Членство» — показывает `GroupMembership` (историческую и текущую принадлежность к группам), а не техническое `ClubMembership`, которое остаётся исключительно backend-инвариантом (ADR-0021, ADR-0022) и никогда не показывается пользователю (никакого `club_membership_id`, `membership_type`-как-роли или статуса членства в клубе на этом экране).
- «Представители» — законные представители/дети (GuardianRelationship), без изменений относительно уже принятой архитектуры.
- «Роли» — управление системными ролями (ADR-0039, TH-0112), без изменений.
- «Учётная запись» — состояние User: активная (с логином) или созданная автоматически, но ожидающая email («Для активации учётной записи необходимо добавить email.») — ADR-0038 amendment, TH-0116.

Разделы «Участники клуба» / «Заявки на вступление» / «Импорт» из §6 верхнего уровня остаются как заявленная, но пока не полностью реализованная структура и не противоречат текущей реализации.

## 8. Календарь и мероприятия

Единый календарный раздел строится вокруг Event и является рабочей точкой для просмотра, создания и редактирования мероприятий.

### 8.0 Календарь — MVP UX contract

**Desktop**
- основной режим: месяц;
- текущий выбранный день выделен;
- рядом с календарём отображается список событий выбранного дня;
- календарь не превращается в плотную generic ERP grid.

**Tablet**
- месяц;
- список событий выбранного дня располагается под календарём.

**Mobile**
- отдельная компактная навигация по дням;
- список событий выбранного дня;
- переход между месяцами сохраняется;
- mobile composition не является просто уменьшенной desktop-версией.

**Navigation**
- предыдущий месяц;
- следующий месяц;
- Today;
- /events открывается на текущем месяце и сегодняшнем дне;
- URL date может переопределять начальную дату;
- переход между периодами автоматически перезагружает calendar range.

**Event display**
В календаре показываются:
- время;
- название;
- тип;
- статус;
- признак recurring.

В списке выбранного дня/детали:
- название;
- начало/окончание;
- тип;
- статус;
- группа, если доступна;
- инструктор, если доступен;
- место, если доступно;
- признак recurring.

Используются только данные, доступные текущему requester через canonical API.

**Event interaction**
Календарь в MVP поддерживает полный рабочий сценарий:
- просмотр события;
- создание события;
- редактирование события.

Создание и редактирование используют существующие canonical Event API/domain semantics. Frontend не создаёт собственную доменную модель события.

Не входят в MVP:
- drag-and-drop scheduling;
- resize события мышью;
- inline editing;
- создание по клику на пустой слот;
- recurrence editor;
- редактирование серии без явного backend-supported scope.

Удаление/архивирование доступно только там, где соответствующая canonical Event operation уже разрешена backend API и permission policy.

**Filters**
- группа;
- инструктор/user;
- тип мероприятия;
- статус.

Фильтры сохраняются при переходе между месяцами. Есть отдельный Reset. Новая глобальная filter/search infrastructure не вводится.

**Timezone**
- backend canonical representation: UTC / RFC 3339 instants;
- display timezone: browser timezone;
- frontend выполняет локальное отображение instant;
- отдельное persistent user timezone setting не вводится;
- DST учитывается средствами timezone-aware date/time formatting.

**Status**
Calendar использует существующий catalog:
- published;
- in_progress;
- completed;
- cancelled.

cancelled должен отличаться не только цветом, но и дополнительным визуальным признаком (например, strike/pattern или утверждённый TourCRM icon language).

**Loading / empty / error**
- initial load: calendar skeleton;
- period navigation: предыдущие данные остаются видимыми до загрузки нового диапазона + лёгкий loading indication;
- empty range: «В этом периоде нет событий»;
- mobile empty day: «На этот день событий нет»;
- error: понятное сообщение + Retry, календарный shell сохраняется;
- технические API details пользователю не показываются.

**Pagination**
Calendar requests the required [from,to) range. Если backend возвращает несколько страниц, frontend последовательно загружает все страницы, объединяет события и только затем строит визуальное представление. Отдельная pagination UI внутри календаря не используется.

**Recurring events**
- recurrence рассчитывается только backend;
- frontend отображает persisted occurrences;
- recurring indicator показывается пользователю;
- открывается конкретный occurrence;
- правила RRULE/version не показываются в обычном календарном UI;
- редактирование серии не вводится отдельной frontend-семантикой без explicit backend-supported scope.

**URL**
Выбранный период/дата и фильтры являются deep-linkable через query string. Refresh, bookmark, back/forward и sharing должны восстанавливать состояние календаря. Новая routing mechanism не вводится.

**Architecture boundary**
Frontend отвечает за presentation, navigation, filters, range requests и interaction с canonical Event API.
Backend отвечает за authorization, recurrence, occurrence materialization, status transitions и доступные mutation semantics.

### 8.1 Посещаемость

Для занятий и иных мероприятий с attendance:
- список участников;
- статус присутствия;
- причина отсутствия;
- массовое действие;
- сохранение с явным подтверждением результата.

Доступ на редактирование определяется permission и организационной областью ответственности.

## 9. Походы

Основные представления:

- инструкторов;
- участников;
- плановую и фактическую дистанцию;
- длительность;
- маршрут;
- GPX;
- результаты.

## 18. Mobile navigation

На мобильных устройствах основная навигация должна быть упрощена.

Role-specific контекстные представления, включая Guardian «Мои дети», не добавляются в глобальный navigation catalog.

Приоритетные пункты:
- Dashboard;
- Calendar;
- Notifications;
- My profile / Children;
- быстрые действия, соответствующие роли.

Вторичные административные разделы доступны через отдельный navigation drawer/menu.

Табличные представления на mobile должны адаптироваться:
- карточки вместо широких таблиц;
- горизонтальная прокрутка только там, где без неё невозможно;
- фильтры в bottom sheet/drawer;
- действия в контекстном меню.

## 19. Responsive behavior

Минимально должны учитываться классы устройств:
- mobile portrait;
- mobile landscape;
- tablet;
- desktop.

Конкретные breakpoint values оставляются технической UI-спецификации frontend и не являются частью доменной модели.

## 20. Общие состояния интерфейса

Каждый CRUD/операционный экран должен проектироваться минимум для состояний:

- loading;
- loaded;
- empty;
- validation error;
- server error;
- forbidden;
- not found;
- network unavailable;
- success confirmation.

Для деструктивных или необратимых операций используется confirmation flow.

## 21. Поиск и фильтрация

Глобальный поиск не должен становиться заменой специализированных фильтров.

Минимально предполагается поиск по:
- людям;
- мероприятиям;
- походам;
- документам;
- базе знаний;
- оборудованию.

Фильтры должны сохранять понятное отображение активных условий.

## 22. Accessibility

Frontend должен стремиться к WCAG 2.2 AA как целевому уровню доступности.

Минимальные требования:
- клавиатурная навигация;
- видимый focus;
- labels для form controls;
- понятные ошибки;
- не полагаться только на цвет;
- достаточные интерактивные области на mobile;
- корректная работа со screen reader там, где применимо.

## 23. UI и permissions

Frontend должен использовать permissions для управления:
- видимостью разделов;
- доступностью действий;
- редактированием полей;
- отображением административных данных.

Это UX-слой и не является заменой backend authorization.

## 24. Acceptance baseline для frontend

До разработки конкретного модуля должны быть определены:

1. роль/роли пользователей сценария;
2. entry point;
3. список экранов;
4. данные каждого экрана;
5. доступные действия;
6. permission checks;
7. validation rules;
8. loading/empty/error states;
9. mobile behavior;
10. success/confirmation flow;
11. связанные уведомления;
12. критерии приёмки.

## 25. Открытые вопросы

Визуальный стиль, дизайн-система, точный набор UI-компонентов, брендирование клуба и конкретные usability-тесты будут оформлены отдельной UX/UI спецификацией до реализации frontend соответствующих модулей.
