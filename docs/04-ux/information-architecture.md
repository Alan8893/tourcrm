# TourCRM — Information Architecture

## 1. Назначение

Документ определяет информационную архитектуру пользовательского интерфейса TourCRM. Он является контрактом для последующего UX/UI-проектирования и реализации frontend.

Документ не фиксирует конкретную визуальную тему, цвета, библиотеку компонентов или пиксельные размеры. Он фиксирует структуру, навигацию, экраны, основные состояния и ролевую доступность.

## 2. Принципы

1. Один адаптивный web-интерфейс используется на desktop, tablet и mobile.
2. Навигация определяется ролью пользователя и доступными permissions.
3. Недоступные разделы не должны считаться только визуально скрытыми: API остаётся источником проверки полномочий.
4. Одинаковые доменные объекты должны иметь единообразный UX во всех модулях.
5. Для критичных действий используется понятное подтверждение и отображение результата.
6. Интерфейс должен поддерживать loading, empty, error, forbidden и offline/unavailable states.
7. Длинные таблицы должны иметь поиск, фильтрацию, сортировку и пагинацию.
8. Формы должны валидировать данные на клиенте для UX, но серверная валидация является обязательной.
9. Mobile-first подход применяется к критичным пользовательским сценариям.
10. Доступность и понятность интерфейса имеют приоритет над визуальной сложностью.

## 3. Основная информационная архитектура

### 3.1 Глобальные разделы

- Dashboard
- Клуб
- Люди
- Группы
- Календарь / Мероприятия
- Походы
- Достижения
- База знаний
- Документы
- Финансы
- Снаряжение
- Уведомления
- Отчёты / Аналитика
- Настройки

Доступность конкретного раздела определяется ролью и permission.

### 3.2 Публичная зона

- Landing/login entry
- Login
- Registration
- Invitation acceptance
- Password recovery
- Email verification
- Registration status

Публичная зона не должна раскрывать персональные данные клуба.

## 4. Авторизация и onboarding

### 4.1 Login

Поля:
- identifier (email или другой поддержанный идентификатор);
- password.

Состояния:
- обычная форма;
- ошибка credentials;
- заблокированный аккаунт;
- pending registration;
- network error;
- successful login.

### 4.2 Registration

Сценарии:
- самостоятельная регистрация;
- регистрация по invitation code/link.

После регистрации, если требуется административное подтверждение, пользователь видит статус `pending approval`.

### 4.3 Password recovery

Сценарий:
- request reset;
- подтверждение отправки;
- reset password;
- expired/invalid token.

## 5. Dashboard

Dashboard является роль-зависимым.

### 5.1 Administrator

Показывает:
- текущие мероприятия;
- ближайшие занятия;
- pending registrations;
- attendance alerts;
- документы с истекающим сроком;
- финансовые показатели при включённом finance module;
- уведомления/ошибки интеграций;
- сводные показатели клуба.

### 5.2 Instructor

Показывает:
- ближайшие занятия;
- свои группы;
- мероприятия, где инструктор ответственен;
- требующую отметки посещаемость;
- ближайшие походы;
- задачи/напоминания.

### 5.3 Member

Показывает:
- ближайшее занятие;
- своё расписание;
- предстоящие мероприятия;
- последние достижения;
- документы/согласия, требующие действия;
- системные уведомления.

### 5.4 Guardian

Показывает:
- детей, к которым есть доступ;
- ближайшие занятия детей;
- мероприятия;
- документы/согласия;
- уведомления;
- финансовые обязательства, если разрешены и модуль включён.

## 6. Люди

Раздел объединяет работу с Person/User/ClubMembership и не должен смешивать эти понятия на уровне модели.

Подразделы:
- Участники клуба;
- Инструкторы;
- Родители/законные представители;
- Пользователи системы;
- Заявки на вступление;
- Импорт.

### 6.1 Список участников

Обязательные возможности:
- поиск;
- фильтры;
- сортировка;
- пагинация;
- экспорт при permission;
- переход в профиль.

### 6.2 Профиль человека

Верхний уровень профиля:
- основные данные;
- контакты;
- членство;
- семейные связи;
- группы;
- мероприятия;
- посещаемость;
- походы;
- достижения;
- квалификации;
- документы;
- согласия;
- финансы, если доступно;
- аудит, если доступно.

### 6.3 Профиль участника

Дополнительно:
- туристский профиль;
- километраж;
- виды туризма;
- навыки;
- опыт;
- рейтинг при включённой функции.

## 7. Группы

Экран списка групп:
- название;
- инструкторы;
- количество участников;
- статус;
- период действия.

Карточка группы:
- участники;
- инструкторы;
- расписание;
- посещаемость;
- мероприятия;
- история состава.

## 8. Календарь и мероприятия

Единый календарный раздел строится вокруг Event.

Режимы:
- месяц;
- неделя;
- список;
- день для удобного мобильного сценария.

Фильтры:
- тип мероприятия;
- группа;
- инструктор;
- статус;
- период.

Карточка Event:
- название;
- тип;
- дата/время;
- timezone;
- место;
- описание;
- организаторы;
- участники;
- посещаемость;
- документы;
- уведомления;
- финансы, если применимо;
- специализированные данные для Trip/TourSlet/Competition.

### 8.1 Посещаемость

Для занятий и иных мероприятий с attendance:
- список участников;
- статус присутствия;
- причина отсутствия;
- массовое действие;
- сохранение с явным подтверждением результата.

Доступ на редактирование определяется permission и организационной областью ответственности.

## 9. Походы

Поход представляется как специализированное расширение Event.

Основные представления:
- список походов;
- календарь;
- карточка похода;
- маршрут;
- GPX;
- состав группы;
- фактический результат;
- туристский стаж.

Карточка похода должна позволять увидеть:
- вид туризма;
- категорию сложности;
- регион;
- руководителя;
- инструкторов;
- участников;
- плановую и фактическую дистанцию;
- длительность;
- маршрут;
- GPX;
- результаты.

## 10. Достижения и квалификации

Разделы:
- каталог достижений;
- мои достижения;
- выдача достижений;
- квалификации;
- рейтинг, если включён.

Для automatic achievements UI должен объяснять основание выдачи, не позволяя пользователю произвольно редактировать вычисляемый факт.

## 11. База знаний

Структура:
- категории;
- список статей;
- поиск;
- фильтры/теги;
- просмотр статьи;
- связанные статьи;
- связанные занятия/навыки;
- вложения.

Для редакторов:
- создание;
- draft;
- review;
- publish;
- archive;
- version history.

## 12. Документы и согласия

Раздел должен поддерживать:
- список документов;
- фильтрацию;
- просмотр метаданных;
- загрузку;
- скачивание;
- версии;
- срок действия;
- статус;
- связи с субъектом/мероприятием.

Для согласий отображаются:
- тип;
- статус;
- версия текста;
- дата;
- подписант/представитель;
- связанный документ.

## 13. Финансы

При включённом finance module доступны:
- dashboard;
- платежи;
- расходы;
- бюджеты мероприятий;
- задолженности;
- финансовые отчёты.

Финансовые права должны быть особенно строго ограничены.

## 14. Снаряжение

Разделы:
- каталог имущества;
- категории;
- состояния;
- места хранения;
- история выдачи;
- активные выдачи;
- возвраты.

Карточка оборудования:
- идентификатор;
- состояние;
- хранение;
- стоимость при наличии;
- серийный номер;
- история использования.

## 15. Коммуникации и уведомления

Центр уведомлений должен отображать:
- системные уведомления;
- события, требующие действия;
- ошибки/предупреждения интеграций в административной зоне;
- историю отправленных уведомлений при соответствующем permission.

Настройки пользователя/клуба должны позволять управлять подписками по каналам.

Каналы:
- email;
- Telegram;
- MAX.

## 16. Отчёты и аналитика

Для администратора:
- численность участников;
- активность;
- посещаемость;
- динамика групп;
- мероприятия;
- походная активность;
- достижения;
- финансы;
- оборудование.

Показатели должны сопровождаться периодом и источником расчёта.

## 17. Настройки

Подразделы:
- профиль;
- безопасность;
- уведомления;
- клуб;
- пользователи и роли;
- справочники;
- feature flags/settings;
- интеграции;
- аудит;
- системные настройки.

## 18. Mobile navigation

На мобильных устройствах основная навигация должна быть упрощена.

Приоритетные пункты:
- Dashboard;
- Calendar;
- Notifications;
- My profile / Children;
- быстрые действия, соответствующие роли.

Вторичные административные разделы доступны через отдельный navigation drawer/menu.

Табличные представления на mobile должны адаптироваться:
- карточки вместо широких таблиц;
- горизонтальная прокрутка только там, где без неё невозможно;
- фильтры в bottom sheet/drawer;
- действия в контекстном меню.

## 19. Responsive behavior

Минимально должны учитываться классы устройств:
- mobile portrait;
- mobile landscape;
- tablet;
- desktop.

Конкретные breakpoint values оставляются технической UI-спецификации frontend и не являются частью доменной модели.

## 20. Общие состояния интерфейса

Каждый CRUD/операционный экран должен проектироваться минимум для состояний:

- loading;
- loaded;
- empty;
- validation error;
- server error;
- forbidden;
- not found;
- network unavailable;
- success confirmation.

Для деструктивных или необратимых операций используется confirmation flow.

## 21. Поиск и фильтрация

Глобальный поиск не должен становиться заменой специализированных фильтров.

Минимально предполагается поиск по:
- людям;
- мероприятиям;
- походам;
- документам;
- базе знаний;
- оборудованию.

Фильтры должны сохранять понятное отображение активных условий.

## 22. Accessibility

Frontend должен стремиться к WCAG 2.2 AA как целевому уровню доступности.

Минимальные требования:
- клавиатурная навигация;
- видимый focus;
- labels для form controls;
- понятные ошибки;
- не полагаться только на цвет;
- достаточные интерактивные области на mobile;
- корректная работа со screen reader там, где применимо.

## 23. UI и permissions

Frontend должен использовать permissions для управления:
- видимостью разделов;
- доступностью действий;
- редактированием полей;
- отображением административных данных.

Это UX-слой и не является заменой backend authorization.

## 24. Acceptance baseline для frontend

До разработки конкретного модуля должны быть определены:

1. роль/роли пользователей сценария;
2. entry point;
3. список экранов;
4. данные каждого экрана;
5. доступные действия;
6. permission checks;
7. validation rules;
8. loading/empty/error states;
9. mobile behavior;
10. success/confirmation flow;
11. связанные уведомления;
12. критерии приёмки.

## 25. Открытые вопросы

Визуальный стиль, дизайн-система, точный набор UI-компонентов, брендирование клуба и конкретные usability-тесты будут оформлены отдельной UX/UI спецификацией до реализации frontend соответствующих модулей.
