# TourCRM — Backup and Disaster Recovery Specification

## 1. Назначение

Документ определяет требования к резервному копированию, восстановлению и аварийному восстановлению TourCRM. Он является эксплуатационным контрактом и дополняет infrastructure specification.

## 2. Цели

Система должна обеспечивать возможность восстановить работоспособное состояние после:

- потери данных PostgreSQL;
- повреждения файлового storage;
- отказа диска;
- отказа сервера;
- ошибочного изменения/удаления данных;
- неудачного релиза;
- компрометации/инцидента с необходимостью восстановления из доверенной точки.

## 3. Что резервируется

Минимально:

- PostgreSQL logical/physical backup согласно принятой стратегии;
- object/file storage;
- критическая конфигурация, не содержащая secrets в открытом виде;
- инфраструктурные manifest/config templates;
- список и состояние применённых миграций;
- документация операционного восстановления.

Не требуется резервировать заново воспроизводимые build artifacts, если они доступны из Git/registry.

## 4. Принципы

1. Резервная копия не считается существующей, пока не проверено её восстановление.
2. Backup не должен храниться только на том же физическом диске, что и production data.
3. Secrets должны храниться отдельно и не попадать в backup в открытом виде без документированного основания.
4. Backup operations должны быть наблюдаемыми и аудируемыми.
5. Восстановление должно быть детерминированным и документированным.

## 5. Рекомендуемая baseline strategy

Для стартовой одиночной инсталляции:

- регулярные PostgreSQL backups;
- регулярная реплика/копия файлового storage;
- ежедневная off-server копия;
- отдельная еженедельная долгоживущая точка;
- шифрование backup storage;
- мониторинг успешности и возраста последней успешной копии.

Конкретные расписание и retention должны быть определены перед production launch.

## 6. RPO / RTO

До production launch должны быть утверждены:

- RPO — допустимая потеря данных;
- RTO — целевое время восстановления.

Baseline для MVP предлагается определить после оценки фактической нагрузки и критичности клуба; техническая система должна позволять изменить параметры без переделки доменной модели.

## 7. Restore

Процедура должна включать:

1. фиксацию инцидента;
2. определение последней допустимой backup point;
3. развёртывание чистого runtime;
4. восстановление БД;
5. восстановление файлов;
6. применение/проверку миграций;
7. проверку referential integrity;
8. запуск smoke checks;
9. проверку ключевых пользовательских сценариев;
10. возвращение системы в штатный режим;
11. документирование результата.

## 8. Restore validation

Не реже принятого operational interval должен выполняться тестовый restore в изолированной среде.

Минимальные проверки:

- приложение запускается;
- БД открывается;
- пользователи и membership доступны;
- документы доступны;
- GPX/files доступны;
- аудит читается;
- ключевые dashboard/report queries выполняются.

## 9. Disaster scenarios

Должны быть предусмотрены runbooks минимум для:

- потери PostgreSQL;
- потери storage;
- полного отказа host;
- ошибочной миграции;
- массового удаления данных;
- компрометации приложения.

## 10. Ownership

Должен быть назначен ответственный за:

- контроль backup health;
- выполнение restore test;
- актуальность runbook;
- контроль retention;
- коммуникацию при аварии.

## 11. Acceptance criteria

- [ ] есть автоматическое создание backup;
- [ ] backup хранится вне production disk;
- [ ] failure backup приводит к observable alert;
- [ ] restore procedure документирована;
- [ ] restore test проводится регулярно;
- [ ] RPO/RTO утверждены до production launch;
- [ ] восстановление проверяется smoke/integrity checks;
- [ ] secrets не попадают в backup без явного разрешения;
- [ ] восстановление и backup operations логируются;
- [ ] runbooks хранятся в репозитории/защищённом operational storage.
