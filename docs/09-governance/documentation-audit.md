# TourCRM — Documentation Consistency Audit

Дата аудита: 2026-09-12

## 1. Цель

Проверить документацию TourCRM перед началом формирования implementation backlog для Claude.

Аудит проверяет:

- единство терминологии;
- единообразие расположения нормативных документов;
- отсутствие конкурирующих источников истины;
- согласованность доменной и API-модели;
- наличие явных открытых решений;
- готовность документации к декомпозиции в GitHub Issues.

## 2. Результат

Архитектурный фундамент считается **согласованным на уровне верхнеуровневой спецификации**.

Критических противоречий между Product Vision, требованиями, доменной моделью, API, UX, Security и Infrastructure baseline не выявлено.

## 3. Выявленное структурное расхождение

### ADR location legacy

В истории первоначального наполнения репозитория существовал каталог:

`docs/02-architecture/adr/`

Канонической архитектурной структурой проекта является:

`docs/03-architecture/adr/`

Все новые ADR создаются только в `docs/03-architecture/adr/`.

Старые файлы из `docs/02-architecture/adr/` считаются legacy-копиями/историческим артефактом первоначальной загрузки. Они не являются источником текущих решений.

При возникновении содержательного расхождения между legacy-файлом и каноническим ADR используется канонический ADR.

Удаление legacy-каталога является отдельной housekeeping-задачей, чтобы не смешивать организационную очистку с изменением архитектурных решений.

## 4. Терминология

Канонический словарь находится в `docs/01-product/glossary.md`.

Ключевое правило:

- `Person` = физическое лицо;
- `User` = учётная запись;
- `Membership` = членство в клубе;
- `RoleAssignment` = назначенные полномочия;
- `Member` = участник клуба как доменная роль/статус;
- `Guardian` = законный представитель.

Один Person может одновременно иметь несколько доменных отношений и не должен моделироваться как взаимоисключающий тип пользователя.

## 5. Domain/API consistency

Проверена согласованность следующих базовых цепочек:

`Person → User → Membership → RoleAssignment`

`Event → Series → Occurrence → Participation → Attendance`

`Event → Trip → TripParticipant → TouristProfile aggregates`

`Document → Consent / Person / Event / Trip / Club`

`NotificationEvent → Notification → DeliveryAttempt → Channel`

Производные показатели не должны становиться источником истины там, где существуют первичные факты.

## 6. Security consistency

Security-модель согласуется с доменными границами:

- permissions проверяются на backend;
- scope является частью authorization decision;
- связь Guardian → Child не равна безусловному доступу;
- отключение feature не является способом обхода permissions;
- audit не должен содержать секреты;
- медицинские данные выделены в ограниченный контур.

## 7. API consistency

Канонический стиль API определён в `docs/05-api/api-contract.md`.

Детальные API-документы должны использовать те же:

- URI conventions;
- pagination;
- error envelope;
- identifier format;
- timestamp conventions;
- idempotency rules;
- authorization semantics.

## 8. Intentional open decisions

Следующие вопросы сознательно остаются отдельными решениями и не должны быть скрыто решены в implementation issue:

- юридическая политика обработки персональных данных;
- точная политика медицинских данных;
- нормативные правила туристской классификации и опыта;
- формула рейтинга;
- календарные интеграции;
- конкретный контракт TourSlet после получения архива;
- отдельные бизнес-правила import/export;
- operational retention audit records.

## 9. Implementation readiness

Документация готова к формированию implementation backlog при соблюдении правила:

1. Issue должна ссылаться на нормативные документы.
2. Нерешённый вопрос фиксируется в ODR, а не придумывается локально.
3. Для каждого Issue должны быть определены acceptance criteria.
4. Реализация Claude проверяется против документации и автоматических тестов.
5. Изменение архитектурного решения требует ADR.

## 10. Следующий этап

После данного аудита допускается переход к созданию Epic/Issues.

Первый backlog рекомендуется строить вокруг Phase 0/Phase 1 и не включать функции, заблокированные открытыми нормативными решениями.
