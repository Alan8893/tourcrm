# TourCRM — Финансовый модуль

## 1. Назначение

Финансовый модуль предназначен для учёта денежных операций клуба и финансовой части мероприятий. Он не является полноценной бухгалтерской системой и не заменяет бухгалтерский учёт, если для клуба применимы отдельные требования.

Модуль должен позволять видеть плановые и фактические поступления/расходы, связывать операции с мероприятиями и участниками, рассчитывать задолженность и формировать управленческую отчётность.

## 2. Принципы

1. Первичной сущностью является финансовая операция, а не строка интерфейса мероприятия.
2. Исторически значимые операции не удаляются физически.
3. Исправление операции выполняется через корректировку/сторно с сохранением истории, а не скрытым изменением исторического факта.
4. Денежные суммы хранятся как целые минимальные единицы валюты, а не floating point.
5. Валюта операции обязательна.
6. Finance permissions не должны давать доступ к персональным данным сверх необходимого для финансового процесса.
7. Все значимые действия с финансами проходят аудит.

## 3. Основные сущности

### 3.1 FinancialAccount

Логический источник/назначение денежных средств клуба.

Поля верхнего уровня:

- id;
- club_id;
- name;
- account_type;
- currency;
- status;
- created_at;
- updated_at.

Типы на старте могут включать cash, bank, other.

### 3.2 Payment

Поступление денежных средств.

Может быть связано с:

- person/member;
- event;
- club;
- финансовым счётом;
- назначением платежа.

Ключевые поля:

- id;
- financial_account_id;
- payer_person_id, если известен;
- member_id, если платёж относится к участнику;
- event_id, если связан с мероприятием;
- amount_minor;
- currency;
- payment_date;
- payment_method;
- purpose;
- external_reference;
- status;
- notes;
- created_by;
- created_at;
- updated_at.

### 3.3 Expense

Расход денежных средств.

Может быть связан с клубом или мероприятием.

Ключевые поля:

- id;
- financial_account_id;
- event_id;
- amount_minor;
- currency;
- expense_date;
- category;
- payee;
- description;
- external_reference;
- status;
- created_by;
- created_at;
- updated_at.

### 3.4 EventBudget

Плановая смета мероприятия.

Содержит плановые статьи доходов/расходов и может сравниваться с фактом.

### 3.5 EventExpense

Представление/связь расходов с конкретным мероприятием, если одна финансовая операция должна участвовать в нескольких аналитических разрезах. Не дублирует сам Expense.

### 3.6 ParticipantBalance

Производное представление обязательств участника по мероприятиям. Не является единственным источником истины.

Задолженность рассчитывается на основании настроенных финансовых обязательств, выставленных начислений и подтверждённых платежей.

## 4. Финансовое обязательство

Для корректного расчёта задолженности рекомендуется отдельная сущность `Charge`/`ParticipantCharge`.

Она представляет требование оплатить сумму, например:

- участие в походе;
- транспорт;
- питание;
- экипировку;
- членский взнос;
- другой клубный сбор.

Charge содержит:

- id;
- member_id;
- event_id, если применимо;
- amount_minor;
- currency;
- due_date;
- status;
- description;
- created_by;
- created_at;
- updated_at.

Платёж уменьшает непогашенный остаток через явную связь распределения платежа по начислениям, если потребуется частичная оплата.

## 5. Распределение платежей

Для частичных платежей и одного платежа по нескольким обязательствам должна быть предусмотрена сущность наподобие `PaymentAllocation`:

- payment_id;
- charge_id;
- allocated_amount_minor.

Сумма распределений не может превышать сумму платежа и не должна превышать непогашенный остаток Charge.

## 6. Статусы

Финансовые операции должны иметь контролируемый жизненный цикл. Базовая модель:

- draft;
- confirmed;
- cancelled;
- corrected.

Конкретные переходы и права на них должны быть определены матрицей permissions.

## 7. Платёжные методы

Система должна поддерживать справочник методов, например:

- cash;
- bank_transfer;
- card;
- online;
- other.

Методы не должны зашиваться в UI таким образом, чтобы нельзя было добавить новый тип без миграции бизнес-логики.

## 8. Финансы мероприятия

Для Event система должна показывать как минимум:

- план доходов;
- план расходов;
- фактические доходы;
- фактические расходы;
- результат;
- задолженность участников;
- список неоплаченных обязательств.

## 9. Отчётность

Минимальные отчёты:

1. поступления за период;
2. расходы за период;
3. доходы/расходы по мероприятию;
4. задолженность участников;
5. движение денежных средств по финансовому счёту;
6. сводка по категориям расходов.

Экспорт: CSV/XLSX и PDF там, где это обосновано.

## 10. Права доступа

Администратор: полный доступ согласно finance permissions.

Инструктор: только явно разрешённые финансовые операции в рамках собственных мероприятий, без общего финансового доступа клуба, если отдельным permission не разрешено иное.

Участник/родитель: доступ только к собственным начислениям, платежам и статусу задолженности.

## 11. Аудит

Аудируются:

- создание операции;
- подтверждение;
- отмена;
- корректировка;
- изменение назначения;
- изменение распределения платежа;
- экспорт финансовых данных.

В аудит не попадают секреты платёжных систем и credentials.

## 12. Feature setting

`finance.enabled` разрешает или запрещает использование модуля в интерфейсе и прикладных сценариях.

Отключение feature не должно удалять исторические данные.

## 13. Безопасность

Финансовые данные относятся к чувствительным данным клуба. Должны применяться:

- минимально необходимые permissions;
- аудит;
- серверная авторизация на каждой операции;
- отсутствие доверия к UI-ограничениям;
- защита экспортов;
- запрет логирования платёжных секретов.

## 14. Приёмочные критерии

- можно создавать, подтверждать и корректировать платежи;
- можно создавать и учитывать расходы;
- можно начислить обязательство участнику;
- можно распределить полный и частичный платёж;
- задолженность рассчитывается из первичных данных;
- отчёты совпадают с первичными операциями;
- отменённая операция не исчезает из истории;
- изменение финансовых данных отражается в AuditLog;
- доступ к данным соответствует permissions;
- отключение `finance.enabled` не уничтожает данные.

## 15. Открытые бизнес-решения

До реализации необходимо определить:

- обязательную валюту клуба;
- нужно ли поддерживать несколько валют;
- точную модель начислений;
- правила возврата денежных средств;
- нужна ли онлайн-оплата;
- нужен ли импорт банковских операций;
- нужна ли налоговая/бухгалтерская интеграция.
