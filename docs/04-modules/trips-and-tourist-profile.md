# TourCRM — Спецификация модуля походов и туристского профиля

## 1. Назначение

Модуль отвечает за учёт туристской деятельности клуба и формирование подтверждаемого туристского профиля человека.

Он должен решать три разные задачи:

1. хранить факты о походах и выездах;
2. хранить факты об участии конкретного человека в походах;
3. рассчитывать производные показатели туристского опыта.

Ключевой принцип: **источником истины являются факты о мероприятиях и участии, а не вручную введённые агрегированные показатели профиля**.

## 2. Связь с Event

Поход не является самостоятельным календарным объектом верхнего уровня.

Базовый объект:

`Event`

Специализированное расширение:

`Trip`

Таким образом:

`Event(type=trip) -> Trip`

Event хранит общие свойства мероприятия: название, время, место, статус, организаторов и участников.

Trip хранит туристскую специфику: вид туризма, категорию сложности, маршрут, дистанцию, продолжительность и итоговые характеристики.

## 3. Виды туризма

Тип туризма хранится как справочник/enum, а не как свободный текст.

Минимально необходимо поддержать:

- hiking — пеший;
- water — водный;
- ski — лыжный;
- mountain — горный;
- bicycle — велосипедный;
- speleo — спелео;
- mixed — комбинированный;
- other — другой.

Справочник должен быть расширяемым без изменения архитектуры домена.

Для одного похода допускается один основной вид туризма и при необходимости набор дополнительных видов.

## 4. Категория сложности

Категория сложности должна храниться структурированно.

Нельзя полагаться только на текстовое поле.

Модель должна позволять различать:

- некатегорийный поход;
- степень/уровень, если она используется в конкретном виде туризма;
- категорию сложности;
- источник/основание классификации.

Конкретный набор нормативных значений должен быть вынесен в справочник и уточнён отдельным нормативным документом перед реализацией расчётов квалификационного опыта.

## 5. Trip

### Основные свойства

- `event_id` — обязательная связь с Event;
- `tourism_type`;
- `difficulty_type`;
- `difficulty_value`;
- `region`;
- `country` при необходимости;
- `route_id`;
- `planned_distance_km`;
- `actual_distance_km`;
- `planned_duration_days`;
- `actual_duration_days`;
- `start_location`;
- `finish_location`;
- `leader_person_id`;
- `description`;
- `result_status`;
- `result_summary`.

Плановые и фактические значения должны храниться отдельно.

Нельзя заменять фактические значения плановыми после завершения похода.

## 6. Статусы похода

Рекомендуемый жизненный цикл:

`draft -> planned -> registration_open -> in_progress -> completed`

Дополнительные терминальные/служебные состояния:

- cancelled;
- postponed;
- failed — поход начался, но не был завершён по плану.

Правила переходов должны быть явными и валидироваться backend.

## 7. Руководитель и инструкторы

Руководитель похода хранится явно.

Не допускается выводить руководителя только из того, что у человека роль `instructor`.

Для похода поддерживаются:

- leader;
- instructors;
- trainees/assistants при необходимости;
- другие роли персонала.

Роль в походе является отдельной характеристикой участия.

## 8. TripParticipant

`TripParticipant` — специализированная связь человека с походом.

Обязательные/основные данные:

- `trip_id`;
- `person_id`;
- `role_in_trip`;
- `registration_status`;
- `actual_participation`;
- `started_with_group`;
- `finished_with_group`;
- `completed_distance_km`;
- `result`;
- `notes`.

Возможные роли:

- participant;
- leader;
- instructor;
- assistant;
- trainee;
- other.

Роль и факт участия не должны определяться только ролью аккаунта в системе.

## 9. Частичное участие

Система должна поддерживать случай, когда человек прошёл только часть маршрута.

Поэтому `completed_distance_km` не должен автоматически приравниваться к дистанции похода.

При наличии подтверждённых сегментов в будущем допускается более детальная модель:

`Trip -> RouteSegment -> ParticipationSegment`

На первом этапе достаточно хранить подтверждённую фактическую дистанцию участия.

## 10. Route

Route является переиспользуемым логическим описанием маршрута.

Основные данные:

- `id`;
- `name`;
- `description`;
- `tourism_type`;
- `region`;
- `country`;
- `planned_distance_km`;
- `planned_elevation_gain_m`;
- `planned_duration_days`;
- `status`;
- `created_by`;
- `created_at`;
- `updated_at`.

Один Route может использоваться в нескольких мероприятиях/походах.

Фактические данные конкретного прохождения не изменяют исходный шаблон Route.

## 11. RoutePoint

RoutePoint описывает точку маршрута.

Поля:

- `route_id`;
- `sequence`;
- `name`;
- `latitude`;
- `longitude`;
- `elevation_m`;
- `point_type`;
- `description`.

`sequence` определяет порядок точек.

Координаты должны проходить валидацию по диапазонам.

## 12. GPX

Система должна поддерживать загрузку GPX-файлов.

Файл хранится в object/file storage, а не в PostgreSQL blob без отдельного архитектурного решения.

Для каждого файла хранятся метаданные:

- `id`;
- `storage_key`;
- `original_filename`;
- `mime_type`;
- `size_bytes`;
- `checksum`;
- `uploaded_by`;
- `uploaded_at`;
- `source_type`;
- `status`.

`source_type` должен позволять различать:

- planned_route;
- actual_track;
- participant_track;
- imported;
- other.

## 13. Разбор GPX

При загрузке GPX backend должен уметь выполнять асинхронный разбор, если объём или вычисления этого требуют.

Из GPX потенциально вычисляются:

- дистанция;
- длительность;
- минимальная/максимальная высота;
- набор высоты;
- количество точек;
- bounding box;
- временной диапазон;
- наличие валидных координат.

Производные значения могут сохраняться в БД для быстрого поиска, но исходный файл остаётся первичным источником.

Алгоритмы расчёта должны быть документированы и тестируемы.

## 14. Фактический и плановый маршрут

Для одного Trip допускается:

- ссылка на плановый Route;
- плановый GPX;
- фактический GPX;
- несколько фактических треков.

Плановый и фактический маршрут нельзя неявно смешивать.

## 15. TouristProfile

TouristProfile представляет агрегированное представление туристского опыта человека.

Он может содержать:

- количество завершённых походов;
- количество походов по видам туризма;
- подтверждённый километраж;
- количество дней в походах;
- количество категорийных мероприятий;
- подтверждённые квалификации;
- навыки;
- достижения.

При этом агрегаты не являются самостоятельным источником истины.

Они должны быть вычисляемыми из фактов `Trip`, `TripParticipant`, `Qualification`, `AchievementAward` и связанных подтверждённых данных.

## 16. Туристский стаж

Термин «туристский стаж» должен быть определён отдельно от простого километража.

Минимально необходимо различать:

1. фактическое участие;
2. подтверждённый опыт;
3. километраж;
4. продолжительность;
5. квалификационный опыт.

На первом этапе не следует автоматически считать нормативный разряд или квалификацию только по сумме километров.

Любые нормативные формулы должны быть вынесены в отдельные правила и иметь версию.

## 17. Источник подтверждения опыта

Для каждого значимого туристского факта должна быть возможность указать источник подтверждения.

Например:

- completed trip record;
- approved report;
- official protocol;
- imported historical data;
- administrator confirmation;
- external integration.

Недостаточно просто указать `confirmed=true` без указания основания.

## 18. Импорт исторических походов

Система должна в будущем поддерживать импорт исторических данных.

При импорте необходимо сохранять:

- источник;
- дату импорта;
- исходный идентификатор;
- импортировавшего пользователя;
- результат сопоставления;
- ошибки;
- ручные исправления после импорта.

Импортированные данные не должны терять информацию об их происхождении.

## 19. Регионы и география

Регион не должен быть исключительно произвольной строкой.

На первом этапе допускается текстовое отображение плюс структурированный справочник страны/региона.

В дальнейшем допускается отдельный географический справочник.

Координаты маршрутов хранятся в WGS84 в виде широты/долготы.

## 20. Фотографии и медиа

Поход может иметь фотографии и другие медиафайлы.

Медиа должны храниться через общую систему файлового/object storage.

Связь должна поддерживать:

- владелец;
- мероприятие;
- поход;
- автор;
- дата;
- подпись;
- visibility/access scope.

Особое внимание требуется к фотографиям несовершеннолетних: публичность не должна быть разрешена по умолчанию.

## 21. Результаты похода

После завершения похода инструктор/руководитель должен иметь возможность зафиксировать:

- фактические даты;
- фактическую дистанцию;
- фактическую продолжительность;
- фактический маршрут;
- результат;
- отклонения от плана;
- происшествия/заметки;
- состав реально прошедшей группы.

Завершённый Trip должен быть защищён от незаметной коррекции исторических показателей. Изменения значимых полей должны попадать в AuditLog.

## 22. Связь с Achievement

Поход является одним из возможных источников автоматического достижения.

Например:

- первый поход;
- 100 км подтверждённого опыта;
- первый категорийный поход;
- участие в определённом виде туризма.

Правило достижения должно ссылаться на подтверждённые факты.

## 23. Связь с Qualification

Qualification хранится отдельно от Trip.

Trip может быть основанием квалификационного опыта, но не заменяет саму квалификацию.

Квалификация должна иметь:

- тип;
- уровень;
- дату получения;
- срок действия при наличии;
- источник/документ подтверждения.

## 24. Бизнес-правила

BR-TRIP-001: Trip обязан иметь Event типа `trip`.

BR-TRIP-002: Завершённый Trip обязан иметь фактические даты или обоснованный статус, почему они отсутствуют.

BR-TRIP-003: Завершённый Trip не может иметь отрицательную или невозможную дистанцию.

BR-TRIP-004: `completed_distance_km` участника не может превышать подтверждённую фактическую дистанцию похода без специального правила сегментов.

BR-TRIP-005: Руководитель и роли инструкторов хранятся явно.

BR-TRIP-006: Удаление завершённого похода по умолчанию запрещено.

BR-TRIP-007: Исправление исторических туристских фактов должно быть аудируемым.

BR-TRIP-008: Агрегированный туристский профиль не является ручным источником истины.

BR-TRIP-009: Нормативный расчёт квалификационного опыта должен иметь версию правила.

BR-TRIP-010: Импортированные данные должны сохранять provenance.

## 25. Поиск и фильтрация

Trip должен поддерживать фильтрацию минимум по:

- периоду;
- виду туризма;
- категории сложности;
- региону;
- руководителю;
- участнику;
- статусу;
- количеству участников.

TouristProfile должен поддерживать просмотр статистики по периодам и видам туризма.

## 26. Отчётность

Необходимо предусмотреть формирование:

- списка участников похода;
- итогового отчёта похода;
- истории походов участника;
- сводной туристской статистики клуба;
- выгрузки CSV/XLSX;
- PDF-отчётов в рамках отдельного модуля документов/экспорта.

## 27. Безопасность

Доступ к данным похода регулируется permissions и связью с клубом.

Участник видит только разрешённые ему данные.

Родитель получает доступ к данным ребёнка только через действующую GuardianRelationship.

Изменение туристского стажа, результатов и подтверждений не может быть разрешено обычному участнику.

## 28. Производительность

Большие GPX-файлы и вычислительные операции не должны блокировать обычный HTTP request на неопределённое время.

Для тяжёлого парсинга допускается использование background jobs.

Исходные файлы должны быть пригодны для последующего переноса между storage backend.

## 29. Мобильный сценарий

На мобильном устройстве пользователь должен иметь возможность:

- просмотреть поход;
- увидеть даты и место;
- увидеть состав группы в рамках permissions;
- посмотреть маршрут;
- открыть GPX/карту;
- просмотреть свой туристский профиль;
- увидеть достижения и опыт.

Инструктор должен иметь возможность быстро просмотреть и скорректировать состав участников и результаты похода с телефона.

## 30. Acceptance Criteria

- [ ] Trip реализован как расширение Event.
- [ ] Виды туризма представлены структурированным справочником.
- [ ] Плановые и фактические данные разделены.
- [ ] Маршрут отделён от конкретного факта прохождения.
- [ ] GPX поддерживается через file/object storage.
- [ ] Метаданные GPX документированы.
- [ ] Поддерживается частичное участие в походе.
- [ ] Роли участников похода хранятся явно.
- [ ] История значимых изменений аудируется.
- [ ] TouristProfile рассчитывается из фактов.
- [ ] Импорт исторических данных сохраняет provenance.
- [ ] Нормативные расчёты имеют версионирование правил.
- [ ] Права доступа учитывают клуб, роль и GuardianRelationship.
- [ ] Определены требования к поиску, фильтрации и отчётности.
- [ ] Есть тестовые сценарии для критических бизнес-правил.

## 31. Открытые решения

До реализации нормативных расчётов необходимо отдельно согласовать:

- точную классификацию категорий сложности по каждому виду туризма;
- правила зачёта похода в квалификационный опыт;
- требования к официальному подтверждению спортивных достижений;
- допустимые исторические источники для импорта;
- необходимость хранения покомандных/посегментных треков;
- детализацию географического справочника.
