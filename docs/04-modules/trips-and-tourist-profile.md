# TourCRM — Спецификация модуля походов и туристского профиля

## 1. Назначение

Модуль отвечает за учёт туристской деятельности клуба и формирование подтверждаемого туристского профиля человека.

Он должен решать три разные задачи:

1. хранить факты о походах и выездах;
2. хранить факты об участии конкретного человека в походах;
3. рассчитывать производные показатели туристского опыта.

Ключевой принцип: **источником истины являются факты о мероприятиях и участии, а не вручную введённые агрегированные показатели профиля**.

## 2. Связь с Event

Поход не является самостоятельным календарным объектом верхнего уровня.

Базовый объект:

`Event`

Специализированное расширение:

`Trip`

Таким образом:

`Event(type=trip) -> Trip`

Event хранит общие свойства мероприятия: название, время, место, статус, организаторов и участников.

Trip хранит туристскую специфику. На текущем этапе канонически реализован только минимальный контур Trip→Event и туристский факт участия; остальные туристские атрибуты вводятся отдельными решениями.

## 3. Виды туризма

TourismType — отдельный расширяемый справочник, а не свободный текст и не набор hardcoded значений в Trip.

Для одного Trip допускается не более одного TourismType.

На текущем этапе TourismType является **необязательным**: Trip может существовать без указанного вида туризма.

Каноническое решение текущего этапа:

- TourismType является отдельным справочником;
- Trip может ссылаться на один TourismType;
- отсутствие TourismType не блокирует создание, существование или завершение Trip;
- конкретный каталог типов, их коды, отображаемые названия, активность и правила классификации являются отдельным PO/CTO-решением;
- старые списки значений (`bicycle`/`cycling`, `mixed`/`combined` и другие варианты) не являются автоматически каноническими и не должны использоваться как нормативный каталог без отдельного решения.

Реализация TourismType не должна требовать изменения архитектуры домена при добавлении новых типов.

## 4. Категория сложности

Difficulty — необязательный структурированный туристский факт Trip.

На текущем этапе модель сложности должна концептуально различать:

- `type` — тип классификации;
- `value` — значение внутри выбранного типа;
- `source` — основание/источник классификации.

Каноническое решение текущего этапа:

- Difficulty не является обязательным для существования Trip;
- отсутствие Difficulty не блокирует создание или завершение Trip;
- `type` и `value` не являются произвольным свободным текстом;
- конкретные нормативные типы и значения сложности пока не утверждены;
- категория, степень и уровень не считаются взаимозаменяемыми без отдельного нормативного решения;
- `source` представляет основание/источник классификации, а не произвольный комментарий;
- нормативные расчёты квалификационного опыта и Achievement Engine не используют Difficulty до утверждения соответствующей классификации.

Конкретный нормативный каталог Difficulty и правила его интерпретации являются отдельным PO/CTO-решением.
## 5. Trip

На текущем этапе каноническая модель Trip минимальна:

- `event_id` — обязательная связь с Event типа `trip`.

Trip не получает дополнительных обязательных туристских полей до утверждения их отдельной PO/CTO-семантики.

### Отложенные туристские факты

Следующие поля/сущности ранее присутствовали в расширенной спецификации, но **не являются каноническими полями текущего Trip Foundation**:

- TourismType;
- Difficulty;
- Geography;
- Route / RouteSegment;
- плановая и фактическая дистанция;
- плановая и фактическая продолжительность;
- стартовая/финишная точки;
- руководитель и роли персонала похода;
- Result;
- фактические даты и другие фактические показатели прохождения.

Их семантика и модель вводятся отдельными PO/CTO-решениями. Уже принятые решения G2, G3, G4 и G9.2 определяют их текущую бизнес-семантику, но не утверждают конкретную физическую модель хранения.

## 6. Статус и завершение Trip

Trip не имеет собственного lifecycle/status. Он полностью наследует канонический lifecycle связанного Event.

Для Trip применяются статусы Event:

- `draft`;
- `published`;
- `in_progress`;
- `completed`;
- `cancelled`;
- `archived`.

В частности:

- `published -> in_progress` синхронизируется с достижением `Event.start_at`;
- `in_progress -> completed` синхронизируется с достижением `Event.end_at`;
- `draft` не публикуется автоматически;
- `cancelled` не становится `completed` только потому, что прошло `end_at`;
- фактическое досрочное завершение допускает явный переход Event в `completed`;
- если момент автоматического перехода был пропущен из-за недоступности сервиса, последующая lifecycle reconciliation синхронизирует Event с уже наступившим временем.

Отдельного Trip `planned`, `registration_open`, `postponed` или `failed` статуса не существует.

Статус `completed` означает завершение мероприятия как Event. Он сам по себе не означает, что все туристские факты подтверждены, квалификационный опыт зачтён или Achievement должен быть выдан.

`result_status` не является частью lifecycle Trip и до отдельного PO/CTO решения не используется как нормативный статус.
## 7. Руководитель и инструкторы

Руководитель похода хранится явно.

Не допускается выводить руководителя только из того, что у человека роль `instructor`.

Для похода поддерживаются:

- leader;
- instructors;
- trainees/assistants при необходимости;
- другие роли персонала.

Роль в походе является отдельной характеристикой участия.

## 8. TripParticipant

`TripParticipant` — специализированное расширение существующего `EventParticipation` для Trip.

Канонические правила текущего этапа:

- для одного участника используется существующая запись `EventParticipation`;
- `TripParticipant` имеет связь 1:1 с `EventParticipation`;
- Person определяется через `EventParticipation`, а не дублируется как независимый источник истины;
- собственный registration status у `TripParticipant` отсутствует;
- attendance остаётся отдельным операционным фактом;
- `actual_participation` является отдельным подтверждаемым туристским фактом;
- correction исторически закрытого `actual_participation` выполняется только через будущий correction workflow;
- дополнительные роли в походе, сегменты участия, фактическая дистанция и другие расширения не являются частью текущего минимального контракта.

## 9. Частичное участие

Поддержка детального частичного участия по сегментам маршрута **отложена**.

Будущая модель может различать прохождение отдельных RouteSegment и участие человека в них, но такая модель не является частью текущего Trip Foundation и не должна выводиться из неутверждённых полей.

## 10. Будущая модель маршрута и GPX

Route, RoutePoint, RouteSegment и GPX относятся к будущему слою туристских фактов.

Расширенная спецификация маршрутов/GPX, ранее находившаяся в этом документе, не является текущим контрактом Trip Foundation. Конкретная модель маршрута, сегментов, плановых/фактических треков и производных показателей требует отдельного PO/CTO-решения.

## 15. TouristProfile

TouristProfile представляет агрегированное представление туристского опыта человека.

Он может содержать:

- количество завершённых походов;
- количество походов по видам туризма;
- подтверждённый километраж;
- количество дней в походах;
- количество категорийных мероприятий;
- подтверждённые квалификации;
- навыки;
- достижения.

При этом агрегаты не являются самостоятельным источником истины.

Они должны быть вычисляемыми из фактов `Trip`, `TripParticipant`, `Qualification`, `AchievementAward` и связанных подтверждённых данных.

## 16. Туристский стаж

Термин «туристский стаж» должен быть определён отдельно от простого километража.

Минимально необходимо различать:

1. фактическое участие;
2. подтверждённый опыт;
3. километраж;
4. продолжительность;
5. квалификационный опыт.

На первом этапе не следует автоматически считать нормативный разряд или квалификацию только по сумме километров.

Любые нормативные формулы должны быть вынесены в отдельные правила и иметь версию.

## 17. Источник подтверждения опыта

Туристский факт может иметь Provenance; наличие Provenance не является обязательным для каждого факта на текущем этапе.

Например:

- completed trip record;
- approved report;
- official protocol;
- imported historical data;
- administrator confirmation;
- external integration.

Недостаточно просто указать `confirmed=true` без указания основания.

## 18. Импорт исторических походов

Система должна в будущем поддерживать импорт исторических данных.

При импорте необходимо сохранять:

- источник;
- дату импорта;
- исходный идентификатор;
- импортировавшего пользователя;
- результат сопоставления;
- ошибки;
- ручные исправления после импорта.

Импортированные данные не должны терять информацию об их происхождении.

## 19. Регионы и география

Geography — отдельный структурированный справочник туристской географии.

Каноническое решение текущего этапа:

- Trip может иметь не более одного `Country`;
- Trip может иметь не более одного `Region`;
- `Region` принадлежит `Country`;
- Region не является произвольной строкой;
- Region не обязан соответствовать административной единице;
- конкретный каталог, коды, иерархия, правила активности и классификации географических объектов пока не утверждены;
- отсутствие Geography не препятствует созданию или завершению Trip;
- поддержка нескольких регионов/географических зон одного Trip откладывается до появления канонической модели маршрута и его сегментов.

Координаты маршрутов, если используются, хранятся в WGS84 в виде широты/долготы.

## 21. Историческая корректировка туристских фактов

Исторический туристский факт после закрытия не изменяется обычной операцией.

Каноническое решение текущего этапа:

- исправление закрытого исторического факта выполняется через отдельный correction workflow;
- correction сохраняет исходное значение, новое значение, причину исправления и инициатора;
- операция correction фиксируется в Audit Trail;
- correction не переписывает историю так, будто исходного значения никогда не существовало;
- конкретные права на correction, необходимость дополнительного подтверждения, API, структура correction, правила пересчёта Achievement и другие детали workflow пока не утверждены.

## 20. Provenance туристских фактов

Туристский факт может иметь provenance — структурированную информацию о происхождении и подтверждении факта.

Каноническое решение текущего этапа:

- Provenance не является самостоятельным lifecycle туристского факта;
- Provenance не заменяет audit trail;
- audit trail фиксирует, кто и когда изменил данные;
- Provenance отвечает на вопрос, на каком основании туристский факт считается подтверждённым;
- наличие Provenance не является обязательным условием существования каждого туристского факта на текущем этапе;
- конкретные типы источников, подтверждающие субъекты, уровни доверия и правила достаточности подтверждения будут утверждены отдельным PO/CTO-решением.

## 20. Фотографии и медиа

Поход может иметь фотографии и другие медиафайлы.

Медиа должны храниться через общую систему файлового/object storage.

Связь должна поддерживать:

- владелец;
- мероприятие;
- поход;
- автор;
- дата;
- подпись;
- visibility/access scope.

Особое внимание требуется к фотографиям несовершеннолетних: публичность не должна быть разрешена по умолчанию.

## 21. Результаты похода

После завершения похода инструктор/руководитель должен иметь возможность зафиксировать фактические туристские показатели и описание результата. При этом Result и lifecycle Event являются разными понятиями.

Каноническое решение текущего этапа:

- Result — отдельный туристский факт, а не lifecycle/status Trip или Event;
- наличие Result не является обязательным условием завершения Event/Trip;
- `Event.status = completed` означает завершение календарного мероприятия, но не определяет успешность туристского результата;
- `Event.status = completed` не подтверждает автоматически квалификационный туристский опыт участника;
- `result_status` не является статусом Event или Trip lifecycle;
- конкретная модель Result, включая нормативные значения, критерии успешности/неуспешности, отклонения от плана и правила подтверждения, пока не утверждена;
- `result_summary` может использоваться как описательная информация, но сам по себе не является источником нормативных расчётов;
- Achievement Engine не использует Result до отдельного PO/CTO решения о его семантике;
- отмена мероприятия определяется `Event.status = cancelled`, а не отдельным значением Result;
- состоявшийся поход, прошедший не по плану, не считается автоматически `failed` — отдельная семантика такого исхода требует отдельного решения.

Фактические даты, дистанция, продолжительность, маршрут, отклонения, происшествия/заметки и состав реально прошедшей группы являются отдельными туристскими фактами и вводятся только по мере утверждения их канонической модели.

Завершённый Trip должен быть защищён от незаметной коррекции исторических показателей. Изменения значимых полей должны попадать в AuditLog.

## 22. Achievement Facts

Achievement Engine должен использовать только канонические туристские факты, семантика и нормативные правила которых утверждены отдельным PO/CTO-решением.

Каноническое решение текущего этапа:

- наличие записи в Trip, `Event.status = completed` или Audit Trail само по себе не является достаточным основанием для квалификационного достижения;
- туристский факт должен соответствовать утверждённым правилам подтверждения и происхождения (Provenance), если такие правила установлены для соответствующего типа факта;
- TourismType, Difficulty, Geography, Result и другие туристские факты не используются Achievement Engine до утверждения их нормативной семантики;
- это решение не определяет сами достижения, нормативы, категории, баллы или критерии награждения; они относятся к отдельному Achievement Domain.

## 22. Связь с Achievement

Поход является одним из возможных источников автоматического достижения.

Например:

- первый поход;
- 100 км подтверждённого опыта;
- первый категорийный поход;
- участие в определённом виде туризма.

Правило достижения должно ссылаться на подтверждённые факты.

## 23. Связь с Qualification

Qualification хранится отдельно от Trip.

Trip может быть основанием квалификационного опыта, но не заменяет саму квалификацию.

Квалификация должна иметь:

- тип;
- уровень;
- дату получения;
- срок действия при наличии;
- источник/документ подтверждения.

## 24. Бизнес-правила

BR-TRIP-001: Trip обязан иметь Event типа `trip`.

BR-TRIP-003: Завершённый Trip не может иметь отрицательную или невозможную дистанцию.

BR-TRIP-006: Удаление завершённого похода по умолчанию запрещено.

BR-TRIP-007: Исправление исторических туристских фактов должно быть аудируемым.

Для реализованного на текущем этапе Trip audit-контракт включает создание Trip (`trip.created`), первичную фиксацию `TripParticipant.actual_participation` (`trip_participant.actual_participation_recorded`) и изменение уже записанного значения (`trip_participant.actual_participation_changed`). Повторная запись того же значения является идемпотентной и не создаёт новый audit record. Изменения `EventParticipation.registration_status` остаются в существующем `event_participation.status_changed` и не дублируются Trip-аудитом. Будущий correction workflow для исторических туристских фактов определяется отдельным решением.

BR-TRIP-008: Агрегированный туристский профиль не является ручным источником истины.

BR-TRIP-009: Нормативный расчёт квалификационного опыта, когда будет утверждён, должен иметь версию правила.

BR-TRIP-010: Импортированные данные должны сохранять provenance.

## 25. Поиск и фильтрация

Trip должен поддерживать фильтрацию минимум по:

- периоду;
- виду туризма;
- категории сложности;
- региону;
- руководителю;
- участнику;
- статусу;
- количеству участников.

TouristProfile должен поддерживать просмотр статистики по периодам и видам туризма.

## 26. Отчётность

Необходимо предусмотреть формирование:

- списка участников похода;
- итогового отчёта похода;
- истории походов участника;
- сводной туристской статистики клуба;
- выгрузки CSV/XLSX;
- PDF-отчётов в рамках отдельного модуля документов/экспорта.

## 27. Безопасность

Доступ к данным похода регулируется permissions и связью с клубом.

Участник видит только разрешённые ему данные.

Родитель получает доступ к данным ребёнка только через действующую GuardianRelationship.

Изменение туристского стажа, результатов и подтверждений не может быть разрешено обычному участнику.

## 28. Производительность

Большие GPX-файлы и вычислительные операции не должны блокировать обычный HTTP request на неопределённое время.

Для тяжёлого парсинга допускается использование background jobs.

Исходные файлы должны быть пригодны для последующего переноса между storage backend.

## 29. Мобильный сценарий

На мобильном устройстве пользователь должен иметь возможность:

- просмотреть поход;
- увидеть даты и место;
- увидеть состав группы в рамках permissions;
- посмотреть маршрут;
- открыть GPX/карту;
- просмотреть свой туристский профиль;
- увидеть достижения и опыт.

Инструктор должен иметь возможность быстро просмотреть и скорректировать состав участников и результаты похода с телефона.

## 30. Acceptance Criteria

Для текущего Trip Foundation:

- [x] Trip реализован как расширение Event.
- [x] TripParticipant является 1:1 расширением EventParticipation.
- [x] Регистрационный статус не дублируется в TripParticipant.
- [x] `actual_participation` выделен как отдельный туристский факт.
- [x] Trip не имеет собственного lifecycle.
- [x] История значимых изменений туристских фактов учитывается через Audit Trail.
- [x] Приняты отдельные PO/CTO-границы для TourismType, Geography, Difficulty, Result, Provenance, Historical Correction и Achievement Facts.
- [ ] Будущие туристские факты и нормативные модели реализуются только после соответствующих PO/CTO-решений.

## 31. Следующие отдельные решения

После завершения Tourism Facts Foundation отдельными PO/CTO-решениями могут быть утверждены:

- конкретный каталог TourismType, коды и названия;
- конкретные нормативные типы/значения Difficulty;
- детализация географического справочника;
- модель Result и критерии его подтверждения;
- конкретная модель Provenance и correction workflow;
- Route / RouteSegment и фактические маршрутные данные;
- правила зачёта квалификационного опыта;
- требования к официальному подтверждению спортивных достижений;
- допустимые исторические источники для импорта;
- покомандные/посегментные треки.
