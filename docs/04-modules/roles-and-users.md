# Пользователи, роли и членство

## Термины

### User

Учётная запись, используемая для входа в систему. User содержит данные аутентификации и настройки доступа, но не является одновременно полной карточкой человека.

### Person

Физическое лицо. Используется как независимая сущность для хранения идентификационных и контактных данных.

### Club

Туристский клуб, в рамках которого ведётся работа системы. На текущем этапе клуб один, но сущность должна присутствовать в доменной модели.

### Club Membership

Связь человека с клубом. Позволяет хранить статус членства и историю изменений независимо от учётной записи.

### Parent/Legal Representative

Связь законного представителя с участником. Один родитель может быть связан с несколькими детьми; один ребёнок может иметь нескольких законных представителей.

## Роли первого этапа

- `club_admin` — администратор клуба;
- `instructor` — инструктор;
- `member` — участник клуба;
- `parent` — родитель/законный представитель.

Один User может иметь несколько ролей.

Архитектура должна позволять добавлять новые роли без изменения фундаментальной модели пользователей.

## Регистрация

Поддерживаются три сценария:

1. самостоятельная регистрация с последующим подтверждением администратором;
2. регистрация по приглашению/коду;
3. импорт существующих участников с последующей активацией учётных записей.

## Принцип доступа

Доступ определяется сочетанием роли, связи пользователя с клубом, связями с участниками и объектом, к которому запрашивается доступ.

Родитель не получает общий доступ к базе участников. Он получает доступ только к разрешённым данным связанных с ним детей.

Участник не получает доступ к закрытым данным других участников.

Инструктор работает преимущественно с назначенными ему группами и мероприятиями. Точный ACL будет определён при проектировании авторизации.

## Несовершеннолетние

Система должна поддерживать признак несовершеннолетия и связь с законными представителями. Юридически значимые действия и набор доступных данных будут определены отдельными бизнес-правилами после уточнения требований к обработке персональных данных.

## История

Изменения членства, ролей и связей должны иметь историю. Удаление критически важных записей предпочтительно выполнять как логическое/архивное удаление с сохранением аудита.
