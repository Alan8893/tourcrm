# TourCRM — спецификация каталога бизнес-уведомлений v1.0

- **Статус:** утверждена Product Owner для первой версии
- **Дата:** 2026-10-09
- **Связанные решения:** ADR-0045, ADR-0048
- **Область:** бизнес-события, аудитории, каналы, обязательность, сроки и шаблоны
- **Не входит:** реализация событий в доменных модулях, редактор шаблонов, Email-доставка бизнес-уведомлений, массовые рассылки

## 1. Принятые решения

1. Первая версия включает весь каталог P1 и P2 из этой спецификации.
2. Для бизнес-правил активным каналом является только Telegram. Email не активировать для правил, даже если Email настроен и глобально включён для иных сценариев.
3. Обязательны только уведомления об отмене и переносе события. Пользовательские предпочтения не могут отключить эти два типа.
4. Все остальные события отправляются по настройкам пользователя. Если для типа события нет сохранённого предпочтения, применяется безопасное значение по умолчанию: **не отправлять**, пока продуктовая политика не задаст иное.
5. Глобальная политика канала и включённость правила остаются верхними ограничителями согласно ADR-0045/ADR-0048. Обязательность не переопределяет Global Admin Policy OFF или отключённое администратором правило.
6. Уведомления создаются только после успешного коммита бизнес-транзакции; используется существующая архитектура Notification Engine + transactional outbox.
7. В первой версии аудитория определяется конкретным бизнес-событием. Нельзя рассылать уведомление всем участникам клуба, если они не входят в определённую ниже аудиторию.

## 2. Общие правила обработки

- Доменный модуль планирует уведомления через Notification Engine в рамках той же DB-транзакции, что и бизнес-изменение: бизнес-изменение, Notification, Delivery и outbox job коммитятся атомарно. Внешняя отправка в Telegram выполняется worker-ом только после commit. Нельзя делать единственный вызов Engine после commit без надёжного durable handoff: падение между commit бизнес-изменения и постановкой уведомления приведёт к потере уведомления.
- Для одного факта изменения и одного получателя повторная обработка не должна создавать повторную доставку. Использовать стабильный ключ идемпотентности, связанный с идентификатором события, типом уведомления и получателем.
- Шаблон должен быть доступен и активен до создания Delivery. При отсутствии шаблона не создавать некорректную доставку; записать диагностируемую ошибку.
- Не включать в сообщение секреты, внутренние идентификаторы, закрытые данные других участников или сведения, не доступные получателю по его правам.
- Ссылки должны вести на существующие страницы и проходить обычную авторизацию. Не формировать фиктивные URL.
- Telegram-текст должен безопасно экранировать динамические значения согласно используемому parse mode. При отсутствии необязательного значения использовать явно определённый fallback, а не выводить сырой placeholder.
- Отправка в Telegram асинхронная. «Немедленно» означает постановку в outbox после commit, а не гарантию времени фактической доставки.
- Повторная публикация/повторный вызов обработчика без нового бизнес-факта не должен повторно рассылать уведомление.

## 3. Каталог событий

| Ключ события | Событие | Аудитория | Обязательность | Момент создания | Канал v1 |
|---|---|---|---|---|---|
| `event.created` | Событие создано | Пользователи, которым событие явно адресовано настройками видимости/публикации; только если для события определена целевая аудитория | По настройкам пользователя | После создания и commit, когда событие доступно целевой аудитории | Telegram |
| `event.updated` | Существенные сведения о событии изменены | Зарегистрированные участники, которых касается изменение | По настройкам пользователя | После commit значимого изменения | Telegram |
| `event.cancelled` | Событие отменено | Все зарегистрированные участники на момент отмены | **Обязательное** | После commit отмены | Telegram |
| `event.rescheduled` | Событие перенесено | Все зарегистрированные участники на момент переноса | **Обязательное** | После commit переноса | Telegram |
| `registration.created` | Регистрация создана | Пользователь, чья регистрация создана | По настройкам пользователя | После commit регистрации | Telegram |
| `registration.cancelled` | Регистрация отменена | Пользователь, чья регистрация отменена | По настройкам пользователя | После commit отмены регистрации | Telegram |
| `attendance.changed` | Изменена отметка посещаемости | Участник, чья отметка фактически изменилась | По настройкам пользователя | После commit фактического изменения | Telegram |
| `news.published` | Новость опубликована | Пользователи, входящие в явно заданную аудиторию публикации и имеющие право видеть новость | По настройкам пользователя | После первой успешной публикации | Telegram |
| `achievement.awarded` | Достижение присвоено | Получатель достижения | По настройкам пользователя | После commit подтверждённого присвоения | Telegram |
| `membership.approved` | Заявка на вступление одобрена | Пользователь-заявитель | По настройкам пользователя | После commit одобрения | Telegram |

### 3.1 Уточнения аудитории

- **Создание события:** не рассылать автоматически всем пользователям клуба. Если продуктовый сценарий не определил адресатов, правило не создаёт получателей.
- **Изменение события:** значимыми считаются изменения даты/времени, места, маршрута и условий участия. Изменения технических метаданных сами по себе не запускают уведомление. Если изменены только незначимые поля, событие уведомления не создаётся.
- **Отмена/перенос:** аудитория фиксируется по регистрациям на момент изменения. Пользователь, отменивший регистрацию до этого момента, не входит в аудиторию.
- **Регистрация:** уведомляется только владелец изменённой регистрации. Инструктор не получает уведомление о каждой регистрации в рамках этого события.
- **Посещаемость:** уведомление создаётся только при реальном изменении значения, не при повторном сохранении того же значения.
- **Новости:** уведомление создаётся после публикации, не при сохранении черновика. Редактирование уже опубликованной новости само по себе не рассылается повторно.
- **Достижения:** Notification Engine не рассчитывает достижения; он сообщает только о подтверждённом доменным модулем присвоении.
- **Одобрение членства:** уведомление отправляется только при одобрении. Отказ в v1 не включён.

### 3.2 Родители и законные представители

В v1 уведомления отправляются указанному в таблице получателю-субъекту события. Автоматическое добавление родителей/законных представителей в аудиторию не выполняется. Уведомления представителям о действиях и событиях ребёнка требуют отдельного решения о согласии, видимости данных и настройках предпочтений; нельзя добавлять их неявно на уровне Engine.

## 4. Шаблоны Telegram

Коды шаблонов должны быть стабильными и версионироваться в `notification_templates`. Примеры ниже задают обязательный смысл сообщения; оформление может соответствовать существующему стилю Telegram-бота.

| Ключ | Шаблон сообщения | Переменные |
|---|---|---|
| `event_created.telegram` | «Новое событие: **{{event_title}}**. Дата: {{event_datetime}}. {{event_url}}» | `event_title`, `event_datetime`, `event_url` |
| `event_updated.telegram` | «Обновление события **{{event_title}}**: {{change_summary}}. {{event_url}}» | `event_title`, `change_summary`, `event_url` |
| `event_cancelled.telegram` | «Событие **{{event_title}}** отменено. Дата: {{event_datetime}}. Причина: {{cancellation_reason}}. {{event_url}}» | `event_title`, `event_datetime`, `cancellation_reason`, `event_url` |
| `event_rescheduled.telegram` | «Событие **{{event_title}}** перенесено: {{old_event_datetime}} → {{new_event_datetime}}. {{event_url}}» | `event_title`, `old_event_datetime`, `new_event_datetime`, `event_url` |
| `registration_created.telegram` | «Вы зарегистрированы на **{{event_title}}**. Дата: {{event_datetime}}. {{event_url}}» | `event_title`, `event_datetime`, `event_url` |
| `registration_cancelled.telegram` | «Ваша регистрация на **{{event_title}}** отменена. {{event_url}}» | `event_title`, `event_url` |
| `attendance_changed.telegram` | «Обновлена отметка посещаемости для **{{event_title}}**: {{attendance_status}}. {{event_url}}» | `event_title`, `attendance_status`, `event_url` |
| `news_published.telegram` | «Опубликована новость: **{{news_title}}**. {{news_excerpt}} {{news_url}}» | `news_title`, `news_excerpt`, `news_url` |
| `achievement_awarded.telegram` | «Вам присвоено достижение **{{achievement_title}}**. {{achievement_url}}» | `achievement_title`, `achievement_url` |
| `membership_approved.telegram` | «Ваша заявка на вступление в туристский клуб одобрена. {{membership_url}}» | `membership_url` |

Правила шаблонов:

- Причина отмены, краткое описание изменений и анонс новости могут быть пустыми; для причины отмены использовать «не указана», для описания изменения — безопасное общее сообщение, для анонса новости — опустить необязательную часть.
- Дата и время отображаются в часовом поясе, принятом для соответствующего события в продукте.
- `change_summary` строится из разрешённых для уведомления значимых полей; не включать закрытые заметки или персональные данные.
- `attendance_status` — человекочитаемое значение, не внутренний enum.
- Не добавлять Email-шаблоны и не активировать Email-правила в этой версии.
- URL и доступность целевой страницы проверяются интеграционными тестами; шаблон не должен раскрывать данные, если получатель не авторизован.

## 5. Предпочтения пользователя и обязательность

- Для всех событий, кроме `event.cancelled` и `event.rescheduled`, применяется сохранённое пользовательское предпочтение.
- Если предпочтение отсутствует, уведомление не отправляется (fail closed).
- Для `event.cancelled` и `event.rescheduled` пользовательский opt-out не применяется.
- Ни обязательность, ни пользовательское предпочтение не обходят Global Admin Policy. Если Telegram глобально выключен, новые Delivery не создаются; уже поставленные в очередь доставки приостанавливаются согласно ADR-0048.
- Правило, отключённое администратором, не создаёт доставок. Для обязательных типов UI должен объяснять, что отключение правила прекращает доставку на уровне установки, несмотря на продуктовую обязательность.


### 5.1 Отдельное управление личными сообщениями Telegram

Личные сообщения и публикации в группах/темах Telegram — независимые направления доставки. Настройка личных сообщений в пользовательских Settings TourCRM не должна включать, отключать или менять маршрутизацию групповых сообщений.

- Пользователь управляет только доставкой в собственный личный Telegram-чат.
- Для необязательных событий общий переключатель «Личные сообщения Telegram» выключает личную доставку всех необязательных бизнес-уведомлений. Пользователь может дополнительно управлять отдельными типами событий, если такой детализации достаточно для понятного интерфейса.
- Переключатель личных сообщений не отменяет глобальную политику администратора, отключённое правило или требования авторизации.
- Для `event.cancelled` и `event.rescheduled` пользовательская настройка не отключает обязательное личное уведомление. Глобальный Telegram OFF и отключённое администратором правило всё равно блокируют доставку согласно §5.
- Отсутствующая настройка личных сообщений трактуется как OFF для необязательных событий.
- Если Telegram-аккаунт не привязан, личная доставка невозможна. Настройки сайта должны показывать состояние привязки и предлагать пройти подтверждённую процедуру; нельзя отправлять на непроверенный chat id.
- Настройки личных сообщений не изменяют публикации в общей группе/темах. Маршруты группы и тем настраиваются отдельно администратором.
- Backend обязан применять настройку личных сообщений при планировании доставки; скрытие переключателя на frontend не является контролем доступа и не заменяет серверную проверку.
- Архитектурное решение: настройки личной доставки и групповой/тематической публикации — независимые направления (вариант C, утверждён Product Owner 2026-10-09). Общий переключатель личных сообщений и индивидуальные предпочтения событий управляют только destination=user; они не влияют на telegram_destination. До реализации уточнить и задокументировать модель данных/миграцию и ADR, потому что текущая communication_preferences уникальна по (user_id, channel, notification_type) и не имеет измерения назначения. Не включать бизнес-правила до появления серверного enforcement и тестов.
- Текущий Telegram adapter отправляет сохранённый body_template как обычный текст и не рендерит переменные. Поэтому шаблоны с {{...}} из §4 нельзя считать работающими без отдельного согласованного решения по безопасному рендерингу. До включения бизнес-правил implementation gate должен определить и протестировать rendering contract либо использовать полностью готовый текст, подготовленный доменным интегратором без дублирования бизнес-логики.
- Telegram-бот уже добавлен в рабочую группу. Это позволяет использовать Telegram Bot API для получения доступных боту обновлений и подтверждения маршрутов чата/темы, но не означает доступ к полной истории группы. Доступность сообщений зависит от Bot Privacy Mode, прав бота, типа обновления и того, какие Updates получает webhook/polling. Интеграция должна использовать реальные chat_id и message_thread_id из Telegram, не пытаться выводить их из названий тем.
- Членство бота в группе не даёт права писать пользователям в личные сообщения и не создаёт личную привязку. Для личной доставки пользователь должен пройти существующий подтверждённый linking flow и иметь активную Telegram identity. Групповой маршрут и личная identity — разные назначения.

## 6. Сроки и повторные попытки

- Для всех десяти типов уведомления планируются через Engine и записываются в outbox в той же транзакции, что и бизнес-изменение; worker отправляет их только после commit.
- Для новостей — после перехода в опубликованное состояние; для достижений и членства — после успешного подтверждения соответствующей доменной операции.
- Эта спецификация не устанавливает новый числовой график повторных попыток: применяется существующая политика outbox/worker. Отдельный технический ADR требуется, если потребуется изменить интервалы, максимальный срок или число попыток.
- Временные ошибки провайдера обрабатываются существующим retry-механизмом; окончательная ошибка фиксируется диагностируемым кодом. Токены, bot token, текст секретов и приватные payload не должны попадать в логи ошибок.
- В v1 не вводится отложенная доставка, дайджесты или quiet hours для обязательных уведомлений об отмене/переносе.

## 7. Интерфейс настроек

В Settings → Notifications административный экран должен:

- показывать каталог бизнес-правил, если правило создано и прошло specification gate;
- показывать для каждого правила событие, канал, аудиторию, статус включения, обязательность и краткое описание;
- не предлагать Email как активный канал для правил v1;
- позволять администратору включать/выключать существующие правила в пределах ADR-0048; создание/удаление правил не входит в текущий контракт UI без отдельного решения;
- показывать статус привязки Telegram у текущего пользователя в пользовательских настройках и предлагать привязать аккаунт, если он не привязан;
- не смешивать тестовую отправку с реальными бизнес-уведомлениями. Test-send не создаёт Notification, Delivery или outbox job.

## 8. Критерии приёмки

1. Каталог содержит ровно десять типов событий из §3.
2. Для всех типов бизнес-правил в v1 активен только Telegram; Email не активируется автоматически.
3. Отмена и перенос отправляются всем зарегистрированным участникам и не отключаются пользовательским opt-out.
4. Все остальные типы учитывают пользовательские предпочтения; отсутствие предпочтения означает не отправлять.
5. Событие без определённой аудитории не рассылается всем пользователям клуба.
6. Изменения только технических метаданных не создают `event.updated`.
7. Повторная обработка одного бизнес-факта не создаёт повторную доставку.
8. Notification, Delivery и outbox job коммитятся атомарно с бизнес-изменением; проверены rollback и восстановление worker после commit.
9. Непривязанный Telegram-аккаунт не вызывает отправку в неизвестный чат; интерфейс объясняет, как связать аккаунт.
10. Проверены разрешения на просмотр целевого ресурса, экранирование шаблонов, отсутствующие необязательные значения и безопасные ошибки.
11. Родители/законные представители не добавляются в аудиторию неявно.
12. Проверены правила при Global Telegram OFF, выключенном правиле и временной/постоянной ошибке провайдера.
13. Пользователь может выключить личные Telegram-сообщения в Settings сайта для необязательных событий, не отключая групповые публикации.
14. Сервер применяет настройку личных сообщений; отсутствующая настройка по необязательным событиям означает OFF.
15. Личный opt-out не отключает обязательные уведомления об отмене/переносе, но не обходит Global Admin Policy OFF и отключённое администратором правило.
16. Отсутствие подтверждённой Telegram-привязки исключает личную доставку и отображается пользователю.
17. Настройка личных сообщений не меняет доставку в групповые темы; выбранная модель предпочтений различает эти назначения.
18. Проверено, что Telegram-шаблоны действительно рендерятся до отправки и не уходят пользователю как сырой текст с {{placeholder}}.

## 9. Порядок реализации
