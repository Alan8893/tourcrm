# TourCRM — Уведомления и коммуникации

## 1. Назначение

Модуль предоставляет единый механизм системных уведомлений и клубных коммуникаций. Каналы доставки являются транспортом, а не отдельными бизнес-доменами.

Поддерживаемые каналы на текущем этапе:

- Email;
- Telegram;
- MAX.

Коммуникационный контент должен быть пригоден как для автоматических уведомлений, так и для ручных объявлений.

## 2. Разделение понятий

### Notification

Системное уведомление, вызванное событием или правилом.

Примеры:

- занятие завтра;
- занятие отменено;
- документ скоро истекает;
- изменилось мероприятие;
- назначено достижение;
- появилась задолженность.

### Announcement

Осознанно созданное сотрудником клуба сообщение группе или аудитории.

### Delivery

Конкретная попытка доставки Notification/Announcement через один канал.

Один Notification может породить несколько Delivery.

## 3. Notification

Ключевые поля:

- id;
- club_id;
- event_type;
- subject/reference entity;
- recipient user/person;
- template_id;
- priority;
- scheduled_at;
- created_at;
- status.

Системное уведомление не должно зависеть от одного канала.

## 4. Delivery

Поля:

- id;
- notification_id;
- channel;
- destination;
- status;
- attempts;
- first_attempt_at;
- delivered_at;
- last_error_code;
- last_error_message;
- provider_message_id;
- next_retry_at.

Статусы:

- pending;
- processing;
- delivered;
- failed;
- cancelled;
- skipped.

## 5. NotificationEvent

Должна существовать каноническая модель доменных событий, например:

- event.created;
- event.updated;
- event.cancelled;
- event.rescheduled;
- attendance.recorded;
- document.expiring;
- charge.created;
- payment.recorded;
- achievement.awarded;
- trip.changed;
- membership.approved.

Доменные модули не должны напрямую вызывать Telegram/Email/MAX API в бизнес-логике.

## 6. NotificationRule

Правило определяет:

- событие;
- аудиторию;
- условие;
- шаблон;
- разрешённые каналы;
- задержку/время отправки;
- enabled.

Пример:

`event.starts_soon + participants + 24h + Telegram/Email`.

Правила должны редактироваться в рамках разрешённой конфигурации и не давать возможности обходить security permissions.

## 7. UserNotificationPreferences

Пользователь может управлять собственными настройками там, где это разрешено клубной политикой.

Настройки включают:

- канал;
- тип уведомления;
- enabled;
- quiet hours;
- контакт назначения.

Критичные системные сообщения могут быть неотключаемыми, если это будет отдельно установлено требованиями клуба.

## 8. Каналы

### Email

Нужны:

- подтверждение email;
- шаблоны;
- отправитель;
- HTML/text вариант;
- retry;
- delivery status.

### Telegram

Должен использовать абстракцию провайдера и внутренний идентификатор destination.

Привязка пользователя к Telegram должна быть подтверждаемой, чтобы нельзя было отправить данные на чужой chat id.

### MAX

Интеграция проектируется через тот же Channel Adapter interface. Конкретное API и возможности провайдера уточняются непосредственно перед реализацией.

## 9. Channel Adapter

Каждый канал реализует единый интерфейс:

- validate destination;
- send;
- get delivery status, если поддерживается;
- classify provider error;
- support retries according to policy.

Система не должна распространять провайдерские модели по всем доменным модулям.

## 10. Retry

Для временных ошибок допускаются повторные попытки с backoff.

Для явно постоянных ошибок доставка переводится в `failed` без бесконечных повторов.

Количество попыток и политика backoff являются конфигурируемыми параметрами инфраструктуры.

## 11. Идемпотентность

Повторная обработка одного доменного события не должна создавать бесконечные дубли.

Notification/Delivery должна иметь idempotency/deduplication key, формируемый из источника события и целевого сообщения.

## 12. Аудит

Аудируются:

- изменение правил;
- ручная рассылка;
- изменение привязок каналов;
- отправка чувствительных сообщений;
- массовая отправка;
- результат административных действий.

Токены провайдеров и секреты никогда не записываются в AuditLog.

## 13. Массовые коммуникации

Для Announcement должна поддерживаться аудитория:

- конкретные пользователи;
- группа;
- участники мероприятия;
- родители участников;
- инструкторы;
- клуб целиком, если permission позволяет.

До отправки пользователь с правом рассылки должен видеть предполагаемый размер аудитории и доступные каналы.

## 14. Защита от ошибок

Должны быть предотвращены:

- рассылка аудитории без permission;
- отправка уведомления пользователю без подтверждённого канала;
- утечка данных одного ребёнка другому родителю;
- массовая отправка без явного действия;
- дубли из-за повторной обработки событий.

## 15. Feature settings

- `email.enabled`;
- `telegram.enabled`;
- `max.enabled`;
- `notifications.enabled`.

Отключение канала не удаляет историю доставок.

## 16. API-ожидания

API должен позволять:

- получить уведомления пользователя;
- отметить уведомление прочитанным;
- управлять разрешёнными пользовательскими предпочтениями;
- администратору просматривать delivery status;
- создавать announcement;
- получать доступную аудиторию;
- просматривать историю отправки.

## 17. Приёмочные критерии

- доменные модули не зависят напрямую от Telegram/Email/MAX;
- одно событие может доставляться через несколько каналов;
- повторная обработка не создаёт неконтролируемых дублей;
- временные ошибки корректно повторяются;
- постоянные ошибки фиксируются как failed;
- пользователь видит свои уведомления;
- массовые сообщения ограничены permissions;
- отключение конкретного канала сохраняет исторические delivery;
- секреты провайдеров не попадают в логи и аудит.

## 18. Открытые бизнес-решения

Нужно отдельно определить:

- какие уведомления являются обязательными;
- тихие часы клуба;
- допустимую частоту повторных уведомлений;
- кто имеет право массовой рассылки;
- точный набор возможностей MAX после анализа его API;
- нужна ли двусторонняя коммуникация или на первом этапе только исходящие сообщения.
