# TourCRM — Модуль снаряжения

## 1. Назначение

Модуль предназначен для учёта материального имущества и туристского снаряжения клуба, его состояния, места хранения, выдачи участникам/инструкторам и истории эксплуатации.

## 2. Принципы

1. Каждая физическая единица имущества имеет уникальный инвентарный идентификатор.
2. История выдач и возвратов сохраняется.
3. Текущее состояние не заменяет историю состояний.
4. Снаряжение не должно считаться доступным, если оно уже выдано, находится в ремонте или списано.
5. Связь с мероприятием обязательна для выдачи в рамках мероприятия, если она известна.
6. Удаление исторически значимых записей не допускается без отдельного правила архивации.

## 3. Equipment

Ключевые поля:

- id;
- club_id;
- inventory_number;
- name;
- category;
- type/model;
- serial_number;
- manufacturer;
- purchase_date;
- acquisition_cost_minor;
- currency;
- storage_location;
- status;
- condition;
- description;
- metadata;
- created_at;
- updated_at.

`inventory_number` уникален в пределах клуба.

## 4. Категории

Категории должны быть управляемым справочником. В качестве стартовых примеров:

- палатки;
- спальники;
- рюкзаки;
- плавсредства;
- весла;
- каски;
- страховочное снаряжение;
- навигация;
- кухня;
- ремонтное;
- электроника;
- прочее.

Список не должен быть зашит в прикладной код.

## 5. Жизненный цикл

Рекомендуемые статусы:

`available → reserved → issued → returned → maintenance → available`

Дополнительно:

`lost`, `written_off`, `archived`.

Недопустимые переходы должны отклоняться сервером.

## 6. EquipmentIssue

Представляет конкретную выдачу.

Поля:

- id;
- equipment_id;
- issued_to_person_id;
- event_id;
- issued_at;
- expected_return_at;
- returned_at;
- condition_before;
- condition_after;
- issuer_user_id;
- receiver_user_id;
- return_confirmed_by_user_id;
- notes.

Одна единица снаряжения не может иметь несколько одновременно активных выдач, если предмет не является составной сущностью с отдельными частями.

## 7. Резервирование

Для будущих мероприятий должна быть возможность резервировать оборудование до фактической выдачи.

При конфликте двух резервирований система должна либо отклонять второе, либо явно показывать конфликт до сохранения.

## 8. Состояние

Состояние следует хранить как контролируемое значение, например:

- new;
- good;
- usable;
- worn;
- damaged;
- unsafe.

Для истории значимых изменений состояния рекомендуется отдельный `EquipmentConditionHistory`.

## 9. Ремонт и обслуживание

Оборудование в статусе `maintenance` недоступно для обычной выдачи.

При необходимости используется сущность `MaintenanceRecord` с:

- equipment_id;
- type;
- description;
- started_at;
- completed_at;
- cost;
- provider/performer;
- result;
- documents.

## 10. Комплекты

Система может поддерживать комплекты оборудования, например «палатка + дуги + чехол».

Комплект не должен маскировать индивидуальные единицы: каждая физическая единица продолжает существовать отдельно для инвентаризации и ремонта.

## 11. Поиск и учёт

Нужны фильтры:

- категория;
- статус;
- состояние;
- место хранения;
- мероприятие;
- ответственный;
- инвентарный номер;
- серийный номер.

Минимальные представления:

- всё снаряжение;
- доступное;
- выданное сейчас;
- в ремонте;
- потерянное/списанное;
- просроченные возвраты.

## 12. Связь с мероприятиями

EquipmentIssue может быть связан с Event. Это позволяет получить историю:

`Event → выданное снаряжение → кто получил → когда вернул → в каком состоянии.`

## 13. Документы

К Equipment могут относиться:

- гарантийные документы;
- паспорта;
- сертификаты;
- инструкции;
- фотографии;
- документы ремонта.

Файлы хранятся через общий Document/File Storage контур.

## 14. Права доступа

Администратор: полный доступ.

Инструктор: просмотр доступного снаряжения и управление выдачами в разрешённых мероприятиях.

Участник: просмотр выданного ему снаряжения и своей истории.

Родитель: доступ к снаряжению ребёнка только в необходимом объёме.

## 15. Аудит

Аудируются:

- создание и изменение Equipment;
- изменение статуса;
- выдача;
- возврат;
- изменение состояния;
- списание;
- резервирование;
- экспорт инвентарных данных.

## 16. Приёмочные критерии

- каждая единица имеет уникальный inventory number;
- нельзя одновременно выдать один предмет двум получателям;
- состояние при выдаче и возврате сохраняется;
- оборудование в ремонте не предлагается как доступное;
- просроченные выдачи находятся поиском и отчётом;
- история выдач доступна с карточки оборудования;
- доступ управляется permissions;
- все значимые изменения отражаются в AuditLog.

## 17. Открытые решения

До реализации необходимо уточнить:

- нужен ли штрихкод/QR-код для инвентарных номеров;
- нужна ли мобильная операция сканирования;
- нужно ли массовое назначение комплекта;
- нужна ли инвентаризация по месту хранения;
- требуется ли периодическая обязательная проверка отдельных категорий снаряжения.
