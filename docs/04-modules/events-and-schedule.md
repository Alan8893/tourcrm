# TourCRM — Домен мероприятий и расписания

## 1. Назначение

Документ определяет функциональные и технические требования к центральному домену мероприятий (`Event`) и расписания.

Документ является нормативным источником требований для:

- модели данных;
- API;
- web/mobile UI;
- уведомлений;
- посещаемости;
- последующих специализированных модулей (`Trip`, `Competition`, `TourSlet` и др.).

## 2. Архитектурный принцип

`Event` является общей календарной сущностью, но не универсальной таблицей для всех специализированных данных.

Базовая структура:

```text
Event
├── EventParticipation
├── EventInstructor
├── Attendance
├── EventSchedule / recurrence metadata
├── Documents
├── Notifications
└── specialized extension
    ├── Trip
    ├── Competition
    └── TourSlet integration
```

Специализированные данные не должны добавляться в `Event` только ради удобства CRUD.

## 3. Типы мероприятий

Обязательные типы первой модели:

- `lesson` — учебное занятие;
- `training` — тренировка;
- `trip` — поход/выезд;
- `competition` — соревнование;
- `tour_slet` — турслёт;
- `excursion` — экскурсия;
- `meeting` — собрание/встреча;
- `other` — прочее.

Справочник типов должен быть расширяемым без изменения архитектуры API.

## 4. Жизненный цикл Event

Предлагаемые статусы:

```text
DRAFT
PUBLISHED
IN_PROGRESS
COMPLETED
CANCELLED
ARCHIVED
```

### Правила переходов

```text
DRAFT → PUBLISHED
PUBLISHED → IN_PROGRESS
PUBLISHED → CANCELLED
IN_PROGRESS → COMPLETED
IN_PROGRESS → CANCELLED
COMPLETED → ARCHIVED
CANCELLED → ARCHIVED
```

Недопустимые переходы должны отклоняться API.

Повторная публикация отменённого или завершённого мероприятия выполняется только через явно определённую бизнес-операцию, если такая необходимость появится позже.

## 5. Основные атрибуты Event

Минимальный набор:

- `id`;
- `club_id`;
- `event_type`;
- `title`;
- `description`;
- `start_at`;
- `end_at`;
- `timezone`;
- `location_type`;
- `location_name`;
- `location_address`;
- `location_latitude`;
- `location_longitude`;
- `status`;
- `cancellation_reason`;
- `created_by`;
- `created_at`;
- `updated_at`.

Координаты и адрес опциональны и должны проходить валидацию целостности.

## 6. Время и часовые пояса

Все timestamps хранятся в UTC на уровне инфраструктуры/БД, если выбранный стек это поддерживает штатно.

Для отображения применяется timezone пользователя или timezone мероприятия по правилам приложения.

`Event.timezone` является явным IANA timezone, например `Europe/Moscow`.

Нельзя использовать в API или БД неявное локальное время сервера для бизнес-логики расписания.

## 7. Повторяющиеся мероприятия

Расписание должно поддерживать повторения без создания отдельной вручную заполненной записи на каждое занятие.

Предлагаемая модель:

```text
EventSeries
├── recurrence_rule
├── series_start
├── series_end / occurrence_limit
├── timezone
└── exceptions
```

Правила повторения должны быть совместимы с iCalendar/RRULE-подходом.

Каждое фактическое занятие должно иметь собственную идентичность после материализации occurrence, если на него ведётся отдельная посещаемость, отмена или изменение состава.

### Исключения серии

Необходимо поддержать как минимум:

- отмену одного occurrence;
- перенос одного occurrence;
- изменение продолжительности одного occurrence;
- изменение места одного occurrence;
- изменение преподавателя/инструктора одного occurrence.

Изменение всей серии не должно безвозвратно перетирать исторические индивидуальные исключения.

## 8. Участники мероприятия

Участие хранится отдельно от `Person` и не выводится автоматически только из принадлежности к группе.

`EventParticipation` содержит как минимум:

- `event_id`;
- `person_id`;
- `registration_status`;
- `attendance_status`;
- `participant_role`;
- `registered_at`;
- `registered_by`;
- `attendance_marked_at`;
- `attendance_marked_by`;
- `absence_reason`;
- `result`;
- `notes`.

## 9. Статусы регистрации

Предлагаемые значения:

- `invited`;
- `registered`;
- `waitlisted`;
- `declined`;
- `removed`.

Конкретные допустимые переходы должны быть определены сервером.

## 10. Посещаемость

Посещаемость является фактом присутствия на конкретном occurrence/event.

Минимальные статусы:

- `unknown`;
- `present`;
- `absent`;
- `excused`;
- `late`.

Для `absent` и `excused` причина может быть обязательной согласно настройке клуба.

Посещаемость изменяют только пользователи с соответствующим permission/scope.

Для учебных мероприятий по умолчанию редактировать посещаемость могут инструктор мероприятия/ответственный руководитель и администратор.

## 11. Инструкторы и руководители

Инструктор или руководитель мероприятия связывается с `Event` явной связью.

Не допускается определять руководителя как «первого пользователя с ролью instructor».

Связь должна поддерживать как минимум:

- person/user;
- роль в мероприятии (`instructor`, `leader`, `assistant` и т. п.);
- primary/responsible flag;
- период действия при необходимости.

Для `trip` должно быть возможно отдельно определить руководителя похода.

## 12. Связь с группами

Мероприятие может быть адресовано:

- одной группе;
- нескольким группам;
- конкретным участникам;
- всему клубу.

Целевая аудитория не означает автоматического участия.

Например:

```text
Event → Group A
```

означает, что мероприятие доступно группе A, но запись/посещаемость ведутся через `EventParticipation`.

## 13. Расписание

Расписание должно поддерживать:

- день;
- неделю;
- месяц;
- список ближайших мероприятий;
- фильтр по группе;
- фильтр по типу;
- фильтр по инструктору;
- фильтр по статусу;
- поиск;
- переход к карточке мероприятия.

Для мобильного UI основным представлением является список/agenda, календарная сетка является дополнительным режимом.

## 14. Создание мероприятия

Администратор или инструктор с соответствующим permission создаёт мероприятие в `DRAFT`.

Минимальный сценарий:

```text
Создание
↓
валидация
↓
DRAFT
↓
назначение групп/участников/инструкторов
↓
PUBLISHED
↓
уведомления
```

Публикация означает, что мероприятие становится доступным пользователям и может инициировать уведомления.

## 15. Изменение опубликованного мероприятия

При изменении значимых полей опубликованного мероприятия:

- сохраняется аудит изменения;
- при необходимости создаётся уведомление;
- пользователь должен понимать, что именно изменилось.

Значимыми считаются как минимум:

- дата;
- время;
- timezone;
- место;
- статус;
- ответственный;
- целевая группа;
- отмена.

## 16. Перенос

Перенос должен сохранять историю.

Не следует просто перезаписывать старые значения без аудита.

Рекомендуется хранить событие изменения:

```text
old_start_at
new_start_at
old_end_at
new_end_at
reason
actor
changed_at
```

## 17. Отмена

При отмене:

- статус становится `CANCELLED`;
- причина сохраняется;
- история сохраняется;
- при необходимости отправляется уведомление зарегистрированным участникам, их guardians и инструкторам.

Отменённое мероприятие остаётся доступным в истории.

## 18. Архивирование

Архивирование не удаляет данные.

Архивные мероприятия доступны пользователям в соответствии с permissions, но не должны появляться в обычном списке предстоящих мероприятий.

## 19. Серии и учебный год

Серия занятий должна позволять определить период действия, например учебный год.

Учебный год не должен быть вычислен исключительно по календарному году.

Рекомендуется отдельная сущность `AcademicPeriod` на последующем этапе.

## 20. Уведомления

Минимальные события уведомлений:

- публикация мероприятия;
- регистрация участника;
- изменение времени;
- изменение места;
- отмена;
- напоминание перед мероприятием;
- изменение участия;
- изменение инструктора/ответственного.

Каналы определяются пользовательскими и системными настройками:

- email;
- Telegram;
- MAX.

Уведомление должно создаваться как отдельный объект/задача доставки, а не отправляться синхронно внутри основного CRUD-транзакционного кода.

## 21. Напоминания

Должна поддерживаться конфигурация напоминаний, например:

- за 24 часа;
- за 2 часа;
- другое значение на уровне клуба/мероприятия.

Конкретные значения должны быть настраиваемыми.

Повторная отправка не должна создавать дубликаты для одной комбинации:

`event + recipient + notification_type + scheduled_occurrence`.

## 22. Приватность

Пользователь видит мероприятие и состав участников согласно permissions.

Участник не должен получать полный список персональных данных других участников только из факта участия в одном мероприятии.

Для родителя видимость определяется отношением guardian → child и permissions.

## 23. Удаление

Опубликованные, завершённые и отменённые мероприятия физически не удаляются обычным CRUD endpoint.

Для черновиков возможна отдельная операция удаления при отсутствии связанных значимых данных.

Удаление/архивирование должно быть отражено в аудите.

## 24. Связь со специализированными доменами

### Trip

`Trip.event_id` ссылается на базовое мероприятие.

Trip добавляет:

- вид туризма;
- категорию сложности;
- маршрут;
- дистанцию;
- длительность;
- руководителя;
- туристские результаты.

### Competition

Использует Event как календарную основу и добавляет результаты/места/дисциплины.

### TourSlet

На первом этапе интеграция должна быть адаптерной. Event может содержать внешний идентификатор и ссылку на внешнее мероприятие, но структура интеграции не должна быть зашита в базовую Event-модель до анализа существующего архива TourSlet.

## 25. API-операции

Минимальный набор логических операций:

```text
GET    /api/v1/events
POST   /api/v1/events
GET    /api/v1/events/{id}
PATCH  /api/v1/events/{id}
DELETE /api/v1/events/{id}        # только для разрешённых состояний
POST   /api/v1/events/{id}/publish
POST   /api/v1/events/{id}/cancel
POST   /api/v1/events/{id}/complete
POST   /api/v1/events/{id}/archive
POST   /api/v1/events/{id}/participants
PATCH  /api/v1/events/{id}/participants/{person_id}
POST   /api/v1/events/{id}/attendance
PATCH  /api/v1/events/{id}/attendance/{person_id}
```

Фактические response schemas и pagination rules определяются общим API contract.

## 26. Валидация

Сервер обязан проверять:

- `end_at > start_at`;
- корректность timezone;
- допустимость перехода статуса;
- существование club/group/person;
- права на управление мероприятием;
- недопустимость дублирования участия;
- согласованность occurrence и series;
- корректность связанных специализированных сущностей.

Клиентские проверки не заменяют серверные.

## 27. Конфликты расписания

Система должна уметь обнаруживать потенциальные конфликты как минимум для:

- инструктора;
- помещения/локации, если они введены как ресурс;
- группы;
- участника.

На первом этапе обнаружение может быть предупреждением, а не жёстким запретом.

Для критических типов ресурсов возможность запрета должна быть предусмотрена настройкой/политикой.

## 28. Массовые операции

Должны поддерживаться или быть предусмотрены архитектурно:

- массовое добавление участников по группе;
- массовая отметка посещаемости;
- массовая отправка уведомления;
- массовое создание occurrence для серии.

Массовая операция должна быть безопасной к повторному выполнению и иметь аудит.

## 29. Экспорт

На уровне требований предусмотрен экспорт:

- списка участников мероприятия;
- ведомости посещаемости;
- календаря;
- расписания группы;
- при необходимости ICS/iCalendar.

Форматы PDF/Excel/CSV документируются отдельно в модуле отчётности.

## 30. Нефункциональные требования

- Все операции проверяют authorization на backend.
- CRUD и массовые операции аудируются согласно общей политике.
- Операции списка поддерживают pagination/filter/sort согласно API conventions.
- UI должен оставаться usable на мобильном экране.
- Ошибка отправки уведомления не должна откатывать успешно созданное мероприятие.
- Ошибка вторичной интеграции не должна делать Event неконсистентным.

## 32. Отложенные решения

До получения существующего проекта турслётов не фиксировать конкретную модель интеграции.

Не вводить полноценное управление ресурсами помещений, если бизнес-требования ещё не определены.

Не смешивать академический календарь, учебный год и календарное событие в одну сущность.
