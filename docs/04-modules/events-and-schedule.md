# TourCRM — Домен мероприятий и расписания

## 1. Назначение

Документ определяет функциональные и технические требования к центральному домену мероприятий (`Event`) и расписания.

Документ является нормативным источником требований для:

- модели данных;
- API;
- web/mobile UI;
- уведомлений;
- посещаемости;
- последующих специализированных модулей (`Trip`, `Competition`, `TourSlet` и др.).

## 2. Архитектурный принцип

`Event` является общей календарной сущностью, но не универсальной таблицей для всех специализированных данных.

Базовая структура:

```text
Event
├── EventParticipation
├── EventStaffAssignment
├── EventGroupTarget
├── Attendance
├── EventSchedule / recurrence metadata
├── Documents
├── Notifications
└── specialized extension
    ├── Trip
    ├── Competition
    └── TourSlet integration
```

Специализированные данные не должны добавляться в `Event` только ради удобства CRUD.

## 3. Типы мероприятий

Обязательные типы первой модели:

- `lesson` — учебное занятие;
- `training` — тренировка;
- `trip` — поход/выезд;
- `competition` — соревнование;
- `tour_slet` — турслёт;
- `excursion` — экскурсия;
- `meeting` — собрание/встреча;
- `other` — прочее.

Справочник типов должен быть расширяемым без изменения архитектуры API.

## 4. Жизненный цикл Event

Канонические статусы определены ADR-0018 и являются единым контрактом домена и API:

```text
draft
published
in_progress
completed
cancelled
archived
```

### Правила переходов

```text
draft → published
published → in_progress
published → cancelled
in_progress → completed
in_progress → cancelled
completed → archived
cancelled → archived
```

Недопустимые переходы должны отклоняться API. Статус `planned` не является отдельным состоянием: запланированное, но ещё не опубликованное мероприятие остаётся в `draft`.

## 5. Основные атрибуты Event

Канонический набор определён ADR-0019:

- `id`;
- `club_id`;
- `event_type`;
- `title`;
- `description`;
- `start_at`;
- `end_at`;
- `timezone`;
- `location_type`;
- `location_name`;
- `location_address`;
- `location_latitude`;
- `location_longitude`;
- `status`;
- `cancellation_reason`;
- `created_by`;
- `updated_by`;
- `created_at`;
- `updated_at`.

Координаты и адрес опциональны и должны проходить валидацию целостности.

## 6. Время и часовые пояса

Все timestamps хранятся в UTC на уровне инфраструктуры/БД.

Для отображения применяется timezone пользователя или timezone мероприятия по правилам приложения.

`Event.timezone` является явным IANA timezone, например `Europe/Moscow`.

Нельзя использовать неявное локальное время сервера для бизнес-логики расписания.

## 7. Повторяющиеся мероприятия

Расписание должно поддерживать повторения без создания отдельной вручную заполненной записи на каждое занятие.

Предлагаемая модель:

```text
EventSeries
├── recurrence_rule
├── series_start
├── series_end / occurrence_limit
├── timezone
└── exceptions
```

Правила повторения должны быть совместимы с iCalendar/RRULE-подходом. Каноническая стратегия материализации occurrence определяется ADR-0015.

## 8. Участники мероприятия

Участие хранится отдельно от `Person` и не выводится автоматически только из принадлежности к группе.

`EventGroupTarget` определяет целевую аудиторию, но не создаёт `EventParticipation`.

`EventParticipation` остаётся отдельной persistence-зависимостью. Self-registration и детальные переходы registration status не реализуются и не определяются до отдельного бизнес-решения.

## 9. Посещаемость

Посещаемость является фактом присутствия на конкретном occurrence/event.

Канонические permissions: `attendance.read` и `attendance.update`. Для коррекции требуется `attendance.update`, причина и audit; отдельного `attendance.correct` нет.

## 10. Event responsibility / staff

`EventStaffAssignment` — каноническая явная связь `User ↔ Event`, используемая для ответственности и scope `own_events`.

Поля:

- `id`;
- `event_id`;
- `user_id`;
- `role_in_event`;
- `is_primary`;
- `valid_from`;
- `valid_to`;
- `created_at`;
- `updated_at`.

Допускается несколько активных staff assignments, но не более одной активной primary assignment для Event. Исторические назначения сохраняются.

Назначение допустимо только если Person назначаемого User имеет active ClubMembership в Club Event. `Event.created_by` не заменяет EventStaffAssignment.

Канонический контракт определён ADR-0023.

## 11. Связь с группами

`EventGroupTarget` — каноническая явная связь `Event ↔ Group`, определяющая целевую аудиторию.

Поля:

- `id`;
- `event_id`;
- `group_id`;
- `valid_from`;
- `valid_to`;
- `created_at`;
- `updated_at`.

Event может быть адресован нескольким группам, Group может быть целью нескольких Events. Историческое targeting сохраняется.

Связь допустима только при `Event.club_id == Group.club_id` и проверяется на authoritative application/service boundary согласно ADR-0022.

`own_groups` определяется через active `EventGroupTarget` + active `GroupInstructorAssignment` requester.

Targeting не создаёт `EventParticipation`.

## 12. Расписание

Расписание должно поддерживать:

- день;
- неделю;
- месяц;
- список ближайших мероприятий;
- фильтр по группе;
- фильтр по типу;
- фильтр по инструктору;
- фильтр по статусу;
- поиск;
- переход к карточке мероприятия.

Для мобильного UI основным представлением является список/agenda, календарная сетка является дополнительным режимом.

## 13. Создание мероприятия

Администратор или пользователь с соответствующим permission создаёт мероприятие в `draft`.

Минимальный сценарий:

```text
Создание
↓
валидация
↓
draft
↓
назначение групп/участников/staff
↓
published
↓
уведомления
```

Публикация означает, что мероприятие становится доступным пользователям согласно permission/scope policy.

## 14. Изменение опубликованного мероприятия

При изменении значимых полей опубликованного мероприятия:

- сохраняется аудит изменения;
- при необходимости создаётся уведомление;
- пользователь должен понимать, что именно изменилось.

Значимыми считаются как минимум дата, время, timezone, место, статус, ответственный и целевые группы.

## 15. Перенос

Перенос должен сохранять историю. Не следует просто перезаписывать старые значения без аудита.

## 16. Отмена

При отмене:

- статус становится `cancelled`;
- причина обязательна;
- история сохраняется;
- уведомления выполняются через отдельный notification workflow при необходимости.

Отменённое мероприятие остаётся доступным в истории.

## 17. Архивирование

Архивирование не удаляет данные.

Архивные мероприятия доступны пользователям в соответствии с permissions, но не должны появляться в обычном списке предстоящих мероприятий.

## 18. Серии и учебный год

Серия занятий должна позволять определить период действия, например учебный год.

Учебный год не должен быть вычислен исключительно по календарному году.

Рекомендуется отдельная сущность `AcademicPeriod` на последующем этапе.

## 19. Уведомления

Минимальные события уведомлений:

- публикация мероприятия;
- регистрация участника;
- изменение времени;
- изменение места;
- отмена;
- напоминание перед мероприятием;
- изменение участия;
- изменение инструктора/ответственного.

Каналы определяются пользовательскими и системными настройками: email, Telegram, MAX.

Уведомление должно создаваться как отдельный объект/задача доставки, а не отправляться синхронно внутри основного CRUD-транзакционного кода.

## 20. Приватность

Пользователь видит мероприятие и состав участников согласно permissions.

Участник не должен получать полный список персональных данных других участников только из факта участия в одном мероприятии.

Для guardian видимость определяется активной `GuardianRelationship`, связью ребёнка с Event и permissions. Guardian не получает неограниченный доступ ко всему каталогу клуба.

## 21. Удаление

Опубликованные, завершённые и отменённые мероприятия физически не удаляются обычным CRUD endpoint.

Для draft возможна отдельная операция удаления при отсутствии значимых связанных данных.

Удаление/архивирование должно быть отражено в аудите.

## 22. Связь со специализированными доменами

### Trip

`Trip.event_id` ссылается на базовое мероприятие.

Trip добавляет специализированные туристские данные.

### Competition

Использует Event как календарную основу и добавляет результаты, места и дисциплины.

### TourSlet

На первом этапе интеграция должна быть адаптерной. Конкретная модель интеграции не фиксируется до анализа существующего архива TourSlet.

## 23. API-операции

Фактический набор Event endpoints определяется `docs/05-api/events-api.md` и `docs/05-api/endpoint-inventory.md`.

Response envelope, pagination, errors и authorization contract определяются общими API conventions и ADR-0020.

## 24. Валидация

Сервер обязан проверять:

- `end_at > start_at`;
- корректность timezone;
- допустимость перехода статуса;
- существование и Club ownership связанных объектов;
- authorization;
- отсутствие дублирования EventParticipation после реализации этого слоя;
- корректность recurrence/occurrence связей после реализации соответствующего слоя.

Клиентские проверки не заменяют серверные.

## 25. Конфликты расписания

Система должна уметь обнаруживать потенциальные конфликты инструктора, группы, участника и локации/ресурса. На первом этапе конфликт может быть предупреждением.

## 26. Массовые операции

Архитектурно должны быть предусмотрены массовое назначение участников по группе, массовая посещаемость и массовые операции над occurrence. Все операции должны быть безопасны к повторному выполнению и аудироваться.

## 27. Экспорт

Предусмотрен экспорт списка участников, посещаемости, календаря и расписания группы. Форматы документируются модулем отчётности.

## 28. Нефункциональные требования

- backend authorization обязателен;
- списки используют pagination/filter/sort;
- UI usable на мобильном экране;
- ошибка уведомления не откатывает успешный Event;
- вторичная интеграция не должна делать Event неконсистентным.

## 29. Канонические решения

- Event lifecycle: ADR-0018.
- Event field model: ADR-0019.
- Event authorization/participation: ADR-0020.
- Group persistence: ADR-0021.
- Cross-Club ownership: ADR-0022.
- Event responsibility, EventGroupTarget, GuardianRelationship и EventParticipation dependency boundary: ADR-0023.

## 30. Отложенные решения

До получения существующего проекта турслётов не фиксировать конкретную модель интеграции.

Не вводить полноценное управление ресурсами помещений, если бизнес-требования ещё не определены.

Не смешивать академический календарь, учебный год и календарное событие в одну сущность.
