# TourCRM — Интеграция с модулем турслётов

## 1. Статус

Существующий модуль проведения турслётов существует как отдельный сайт и будет предоставлен в виде ZIP-архива для анализа.

До анализа исходного архива конкретные API endpoints, схемы данных и протоколы авторизации **не считаются утверждёнными**.

Этот документ фиксирует только целевую архитектурную модель и требования к интеграции.

## 2. Цель

Пользователь должен воспринимать TourCRM и систему турслётов как связанные части одной экосистемы, при этом независимость существующего модуля должна быть сохранена настолько, насколько это технически и организационно оправдано.

## 3. Предпочтительная модель

На уровне архитектуры предпочтительна интеграция через API/события:

`TourCRM ↔ Integration Layer ↔ TourSlet`

TourCRM не должен напрямую читать таблицы TourSlet и не должен зависеть от его внутренней схемы БД.

## 4. Идентичность

До анализа существующей системы рассматриваются два варианта:

### A. Единая аутентификация

TourCRM является одним из доверенных клиентов общей системы идентичности.

Преимущество: пользователь не вводит пароль повторно.

### B. Связанные учётные записи

Пользователь TourCRM и пользователь TourSlet связываются явной интеграционной связью.

Этот вариант используется, если существующая система не поддерживает необходимый SSO.

Окончательный вариант выбирается после анализа архива.

## 5. Канонический источник данных

Нужно определить ownership для каждого класса данных.

Предварительно:

- Person/ClubMembership — TourCRM;
- User/Role — TourCRM;
- история членства — TourCRM;
- учебная активность — TourCRM;
- регистрация на конкретный турслёт — TourSlet или согласованный integration owner;
- результаты турслёта — TourSlet с публикацией подтверждённых результатов в TourCRM;
- фотографии/медиа — определяется контрактом.

Нельзя создавать две независимые истины для одного и того же факта.

## 6. Целевые сценарии

1. Пользователь из TourCRM открывает турслёт.
2. Пользователь без повторного ввода credentials авторизуется в TourSlet, если SSO поддерживается.
3. Участник регистрируется на турслёт.
4. Статус регистрации становится виден в TourCRM.
5. По завершении турслёта результаты передаются в TourCRM.
6. Результат может стать основанием для Achievement/статистики.
7. Ошибки интеграции отображаются администраторам, но не приводят к потере локальных данных.

## 7. Интеграционный объект

Если доменная модель подтверждает это после анализа архива, TourCRM будет использовать ссылочную сущность наподобие `ExternalEvent`/`TourSletEvent`:

- local_event_id;
- external_system;
- external_id;
- external_url;
- sync_status;
- last_synced_at;
- synchronization metadata.

## 8. Синхронизация

Предпочтительный порядок:

1. API request/response для операций, требующих немедленного результата.
2. Webhook/event delivery для изменений, инициированных TourSlet.
3. Периодический reconciliation job для обнаружения пропущенных событий.

Интеграция должна быть идемпотентной.

## 9. Сопоставление людей

Нельзя полагаться только на ФИО.

Предпочтение:

1. стабильный внешний идентификатор;
2. заранее согласованный mapping;
3. подтверждаемое сопоставление администратором.

Автоматическое сопоставление только по ФИО и дате рождения не должно считаться достаточно надёжным для финального связывания без дополнительной проверки.

## 10. Ошибки

Интеграция должна различать:

- authentication error;
- authorization error;
- validation error;
- duplicate/idempotency conflict;
- temporary network error;
- remote service unavailable;
- data mapping error;
- unknown error.

Временные ошибки подлежат повтору. Постоянные ошибки должны попадать в журнал интеграции и быть видимы администратору.

## 11. Security

- credentials внешней системы не должны храниться в открытом виде;
- секреты находятся только в secrets/configuration storage;
- внешние webhook должны проверять подлинность;
- интеграционные permissions выделяются отдельно;
- внешняя система не получает больше данных, чем требует контракт;
- персональные данные передаются по принципу минимизации.

## 12. Audit

Логируются:

- связывание учётных записей;
- создание/удаление integration mapping;
- импорт результата;
- повторная синхронизация;
- ручное исправление сопоставления;
- ошибки интеграции.

## 13. Offline/LAN

TourCRM должен продолжать работать в LAN даже при недоступности внешнего TourSlet-сервиса в рамках операций, не требующих внешнего сервиса.

Недоступность интеграции не должна блокировать просмотр локальной истории и работу основных модулей CRM.

## 14. Требования после получения архива

После получения ZIP необходимо определить:

- технологический стек TourSlet;
- его архитектуру;
- модель пользователей;
- модель событий;
- существующие API;
- схему БД;
- способ авторизации;
- доступность SSO;
- форматы экспорта/импорта;
- точки расширения;
- текущие ограничения;
- требования к обратной совместимости.

По результатам анализа этот документ заменяется конкретным Integration Contract с точными endpoint, схемами данных и правилами синхронизации.

## 15. Приёмочные критерии интеграции

После утверждения конкретного контракта должно быть возможно:

- однозначно сопоставить пользователя/участника;
- открыть связанный турслёт;
- синхронизировать его статус;
- получить подтверждённые результаты;
- избежать дублей при повторной доставке;
- восстановить состояние после временной недоступности;
- увидеть интеграционные ошибки и историю синхронизации;
- не нарушить локальную безопасность и права доступа.
