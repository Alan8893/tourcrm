# TourCRM — Модуль «Люди и членство»

## 1. Назначение

Модуль является каноническим источником требований для управления людьми, учётными записями, членством в клубе, ролями, родительскими связями, инструкторами, группами, приглашениями и импортом участников.

Модуль должен обеспечивать:

- разделение физического лица и учётной записи;
- многоролевую модель;
- историческое членство в клубе и группах;
- поддержку несовершеннолетних участников;
- связь одного родителя с несколькими детьми и одного ребёнка с несколькими законными представителями;
- несколько способов создания участников;
- управление жизненным циклом аккаунта и членства;
- аудит значимых изменений.

## 2. Канонические сущности

Модуль использует сущности:

- `Person` — физическое лицо;
- `User` — учётная запись;
- `ClubMembership` — членство физического лица в клубе;
- `Role` / `Permission` — полномочия;
- `RoleAssignment` — назначение роли пользователю;
- `GuardianRelationship` — связь законного представителя и ребёнка;
- `Group` — учебная/организационная группа;
- `GroupMembership` — историческая принадлежность к группе;
- `GroupInstructorAssignment` — явное назначение пользователя ответственным за группу;
- `Invitation` — приглашение в систему/клуб;
- `RegistrationRequest` — заявка на самостоятельную регистрацию;
- `ImportBatch` / `ImportRow` — импорт участников.

`Person`, `User` и `ClubMembership` не объединяются в одну сущность.

## 3. Person

### 3.1. Назначение

`Person` представляет физическое лицо независимо от наличия аккаунта и текущего членства.

### 3.2. Обязательные данные

Минимальный набор:

- `id`;
- `first_name`;
- `last_name`;
- `middle_name` — nullable;
- `date_of_birth` — nullable на этапе предварительной регистрации, обязательно для активного несовершеннолетнего участника;
- `phone` — nullable;
- `email` — nullable;
- `status`;
- `created_at`;
- `updated_at`.

### 3.3. Дополнительные данные

Могут добавляться без изменения идентичности `Person`:

- фото;
- адрес;
- пол;
- дополнительные контакты;
- экстренные контакты;
- класс/образовательная организация;
- примечания с отдельными правами доступа.

Чувствительные медицинские данные не должны храниться как произвольный текст в общем профиле; они относятся к отдельному домену и должны иметь собственные правила доступа.

## 4. User

### 4.1. Назначение

`User` предоставляет доступ к системе.

Один `Person` может иметь не более одной активной основной учётной записи, если отдельное ADR не разрешит иной сценарий.

### 4.2. Состояния

Минимальный жизненный цикл:

```text
pending
  ↓
active
  ↓
suspended
  ↓
active

active → blocked
active → deactivated
```

`blocked` означает запрет входа до решения администратора.

`deactivated` означает завершение использования учётной записи без удаления исторических данных.

### 4.3. Credentials

Пароль не хранится в открытом виде.

Схема хранения credential должна использовать современный адаптивный password hashing алгоритм, выбранный в security ADR.

## 5. ClubMembership

### 5.1. Назначение

Связывает `Person` с конкретным `Club` и хранит историю участия.

### 5.2. Типы членства

Минимально:

- `member` — участник клуба;
- `instructor` — инструктор;
- `staff` — административный/служебный профиль;
- `other` — для расширения.

Тип членства не заменяет `Role`. Полномочия определяются ролями.

### 5.3. Статусы

```text
pending
active
suspended
inactive
archived
```

Правила:

- `pending` — человек добавлен, но членство ещё не подтверждено;
- `active` — обычное действующее членство;
- `suspended` — временно приостановлено;
- `inactive` — членство завершено без потери истории;
- `archived` — историческая запись, не участвующая в обычных рабочих процессах.

### 5.4. История

Закрытие одного периода членства не должно уничтожать прошлые данные.

Для повторного вступления создаётся новый период членства или новая versioned record по правилам модели БД.

## 6. RoleAssignment

### 6.1. Назначение

Связывает `User` с `Role` и, при необходимости, с областью действия.

### 6.2. Scope

Канонический словарь scope определяется ADR-0013:

- `all`;
- `self`;
- `children`;
- `own_groups`;
- `own_events`;
- `none`.

`assigned_events` является alias для `own_events`; `own_records` не является scope.

Примеры:

```text
admin + all
instructor + own_groups
member + self
guardian + children
```

### 6.3. Несколько ролей

Один пользователь может одновременно иметь несколько ролей.

Пример:

```text
Person A
 ├── member
 ├── instructor
 └── guardian
```

Разрешение на действие определяется объединением активных полномочий с учётом scope.

Запрещено использовать «старшую» роль как основание для неограниченного доступа, если permission отсутствует.

## 7. GuardianRelationship

### 7.1. Назначение

Многие-ко-многим связь между `Person` как guardian и `Person` как child.

### 7.2. Атрибуты

Минимум:

- `guardian_person_id`;
- `child_person_id`;
- `relationship_type`;
- `status`;
- `is_primary_contact`;
- `valid_from`;
- `valid_to`;
- `verified_at`;
- `verified_by`.

### 7.3. Ограничения

- guardian и child не могут быть одной записью `Person`;
- один guardian может иметь несколько детей;
- один ребёнок может иметь несколько guardian;
- признак `is_primary_contact` не означает исключительность всей связи;
- доступ guardian к данным ребёнка появляется только после подтверждённой активной связи.

### 7.4. Подтверждение

Для несовершеннолетних связь должна иметь состояние верификации.

Допустимые состояния:

```text
pending
verified
rejected
revoked
```

Источник подтверждения и порядок верификации определяются отдельным policy документом, но API не должен считать `pending` полноценным доступом к данным ребёнка.

## 8. Group

### 8.1. Назначение

Учебная или организационная группа.

Примеры:

- `5–6 класс`;
- `7–8 класс`;
- `9–11 класс`.

### 8.2. Состав

Группа связана с `Club`.

В ней могут находиться участники и назначенные инструкторы.

### 8.3. Каноническая persistence-модель

`Group` имеет следующие поля:

- `id`;
- `club_id`;
- `name`;
- `description`;
- `status`;
- `valid_from`;
- `valid_to`;
- `created_at`;
- `updated_at`.

`Group.status` остаётся строковым значением. Канонический набор lifecycle-значений не определён этим модулем.

`Group` принадлежит ровно одному `Club`.

### 8.4. GroupMembership

`GroupMembership` — историческая ассоциация `ClubMembership` с `Group`.

Канонические поля:

```text
id
group_id
club_membership_id
valid_from
valid_to
membership_status
created_at
updated_at
```

`person_id` в `GroupMembership` не хранится. Человек определяется через `club_membership_id -> ClubMembership.person_id`.

`membership_status` — каноническое имя поля.

`is_primary` не входит в первую persistence-модель. Возможность одновременной принадлежности к нескольким группам и наличие основной группы требуют отдельного business-policy решения.

`assigned_by` не является доменным полем `GroupMembership`; информация об инициаторе изменения относится к audit/created-by инфраструктуре.

Исторические записи сохраняются; закрытие периода не удаляет запись.

### 8.5. Cross-Club integrity

`GroupMembership` допустим только при совпадении:

```text
Group.club_id == ClubMembership.club_id
```

Проверка выполняется на authoritative application/service boundary согласно ADR-0022. Пользовательский интерфейс не является границей безопасности.

### 8.6. GroupInstructorAssignment

Явное назначение `User` ответственным за группу хранится отдельно от членства в группе.

Канонические поля:

```text
id
group_id
user_id
role_in_group
is_primary
valid_from
valid_to
created_at
updated_at
```

`user_id` используется потому, что ответственность для authorization относится к аутентифицированному `User` principal.

`role_in_group` пока не закрывается enum-справочником. Допустимый словарь должен быть согласован с моделью ответственности Event.

`is_primary` различает основного ответственного и другие явные назначения.

Для `GroupInstructorAssignment` назначаемый `User` должен иметь active `ClubMembership` в Club группы. Глобальная роль `instructor` сама по себе недостаточна.

История назначений сохраняется через `valid_from` / `valid_to`.

## 9. Invitation

### 9.1. Назначение

Приглашение позволяет создать или связать пользователя без ручного ввода всей информации.

### 9.2. Способы

- персональная ссылка;
- код приглашения;
- импорт с последующим приглашением.

### 9.3. Жизненный цикл

```text
created
→ sent
→ accepted
→ expired
→ revoked
```

### 9.4. Безопасность

Приглашение должно иметь:

- случайный неугадываемый токен;
- дату истечения;
- ограничение повторного использования;
- состояние отзыва;
- аудит создания и принятия.

Не следует передавать персональные данные ребёнка непосредственно в URL приглашения.

## 10. RegistrationRequest

### 10.1. Назначение

Самостоятельная регистрация нового пользователя с последующим подтверждением администратора.

### 10.2. Статусы

```text
submitted
under_review
approved
rejected
cancelled
expired
```

### 10.3. Правила

После `approved` система создаёт/связывает `Person`, создаёт `User` и, при необходимости, `ClubMembership`.

При `rejected` причина должна храниться в аудитируемом поле, но пользовательскому интерфейсу следует показывать только разрешённый объём информации.

## 11. Import

### 11.1. Источники

Первая версия должна быть рассчитана минимум на CSV/XLSX импорт.

### 11.2. Pipeline

```text
upload
→ parse
→ validate
→ preview
→ approve
→ apply
→ report
```

Никогда не применять импорт непосредственно после загрузки файла без предварительной валидации и предварительного просмотра результата.

### 11.3. Дубликаты

Система должна проверять потенциальные дубликаты по нескольким полям, а не по одному ФИО.

Рекомендованный порядок эвристики:

1. точный внешний идентификатор, если есть;
2. email;
3. телефон;
4. комбинация ФИО + дата рождения;
5. fuzzy match как предупреждение, не как автоматическое слияние.

Автоматическое объединение (`merge`) без явного правила и аудита запрещено.

## 12. Ключевые пользовательские сценарии

### 12.1. Самостоятельная регистрация взрослого

1. Пользователь заполняет регистрацию.
2. Создаётся `RegistrationRequest`.
3. Администратор рассматривает заявку.
4. После approval создаются/связываются `Person`, `User`, `ClubMembership`.
5. Пользователю отправляется уведомление.
6. Вход становится доступен согласно статусам безопасности.

### 12.2. Самостоятельная регистрация родителя

1. Родитель регистрируется.
2. Создаётся собственный `Person/User`.
3. Родитель либо выбирает существующего ребёнка по безопасному механизму связи, либо создаёт запрос на связывание.
4. Связь получает `pending`.
5. После подтверждения администратора или предусмотренного безопасного процесса становится `verified`.

### 12.3. Приглашение участника

1. Администратор/уполномоченный инструктор создаёт приглашение.
2. Ссылка/код передаётся адресату.
3. Адресат принимает приглашение.
4. Система предотвращает повторное использование.
5. Создаётся или связывается User/Person.
6. Назначается допустимый контекст клуба/группы.

### 12.4. Добавление участника администратором

Администратор может создать `Person` без активного `User`.

Позже этому человеку может быть назначен аккаунт через приглашение.

Это обязательный сценарий для импортированных списков и ручного ведения базы.

### 12.5. Перевод участника в другую группу

1. Текущая `GroupMembership` закрывается.
2. Создаётся новая `GroupMembership`.
3. История сохраняется.
4. Будущие permissions со scope `own_groups` должны учитывать актуальную принадлежность.
5. Прошлые события не должны менять свою историческую принадлежность.

### 12.6. Уход из клуба

1. Членство переводится в `inactive`.
2. История мероприятий, походов, достижений, финансов и документов сохраняется.
3. Доступ пользователя определяется отдельно и может быть деактивирован.
4. Удаление `Person` не используется как механизм выхода из клуба.

## 13. Правила отображения данных

### Администратор

Видит данные в соответствии с административными permissions.

### Инструктор

По умолчанию видит только данные участников групп и мероприятий, в которых имеет разрешённую область действия.

### Участник

Видит собственные данные и разрешённые клубные сведения.

### Guardian

Видит собственные данные и данные связанных детей в рамках scope `children`.

Guardian не получает административные данные клуба только из-за наличия родительской связи.

## 14. Уникальность и идентификация

Системные идентификаторы сущностей должны быть стабильными и не зависеть от ФИО.

ФИО не является уникальным идентификатором.

Email и телефон могут быть уникальными в контексте `User` по отдельным правилам идентификации и верификации.

Для одного `Person` не должно существовать двух активных основных `User` без документированного основания.

## 15. Аудит

Аудит обязателен для:

- создания/изменения/деактивации User;
- назначения и снятия ролей;
- создания/изменения членства;
- подтверждения/отзыва guardian relationship;
- изменения групповой принадлежности;
- принятия/отзыва invitation;
- approve/reject registration request;
- применения import batch;
- ручного merge записей.

## 16. Запрещённые решения

Claude не должен:

- использовать одну таблицу `users` для Person + credentials + membership + roles;
- хранить ребёнка только через поле `parent_id`;
- хранить группу только через `current_group_id` без истории;
- использовать роль `admin` как универсальный обход permission checks;
- удалять исторические записи при деактивации участника;
- автоматически объединять похожих людей без явного правила;
- выдавать guardian доступ к ребёнку до подтверждения связи.

## 17. API — логические ресурсы

Окончательные URI определяются API ADR, но должны существовать отдельные ресурсы для:

- `/people`;
- `/users`;
- `/memberships`;
- `/roles`;
- `/groups`;
- `/group-memberships`;
- `/guardianships`;
- `/invitations`;
- `/registration-requests`;
- `/imports`.

Один endpoint не должен скрывать несколько доменных операций без необходимости.

## 18. Технические требования к реализации

Реализация должна обеспечивать транзакционность для операций, изменяющих несколько связанных сущностей.

Например, approval registration не должен оставлять частично созданный объект `User` при неудачном создании `ClubMembership`.

Конкурентные операции над членством, ролями и приглашениями должны быть защищены от race conditions.

Права доступа проверяются на backend; ограничения UI являются дополнительным уровнем удобства, а не security boundary.

## 19. Приёмочные критерии

Модуль считается реализованным только если:

- [ ] Person и User разделены;
- [ ] поддерживаются несколько ролей;
- [ ] permissions работают с scope;
- [ ] хранится история членства;
- [ ] хранится история групп;
- [ ] один guardian может иметь несколько детей;
- [ ] один ребёнок может иметь нескольких guardians;
- [ ] guardian access требует подтверждённой связи;
- [ ] GroupMembership использует `club_membership_id` как связь с участником;
- [ ] GroupMembership не хранит дублирующий `person_id`;
- [ ] GroupInstructorAssignment хранит явную ответственность пользователя за группу;
- [ ] cross-Club Group relationships проверяются на authoritative application/service boundary;
- [ ] исторические назначения не уничтожаются;
- [ ] invitation tokens не хранятся в открытом виде;
- [ ] критические изменения аудитируются.
