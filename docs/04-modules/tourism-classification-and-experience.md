# TourCRM — Tourism Classification and Experience Specification

## 1. Назначение

Документ определяет модель туристской классификации, подтверждённого опыта и правил его расчёта.

TourCRM должна хранить первичные факты отдельно от производных показателей. Правила расчёта не должны быть зашиты в UI.

## 2. Основной принцип

Первичный источник туристского опыта:

- `Trip`;
- `TripParticipant`;
- подтверждённый `Qualification`;
- подтверждённые результаты мероприятия.

`TouristProfile` является производным представлением и может пересчитываться.

## 3. Вид туризма

Система использует справочник `TourismType`.

Минимально предусматривается расширяемый набор, включающий:

- hiking;
- water;
- ski;
- mountain;
- cycling;
- speleo;
- combined;
- other.

Справочник не должен быть захардкожен так, чтобы добавление нового вида требовало изменения кода.

## 4. Категория сложности

`DifficultyCategory` является структурированным справочником.

Запись категории должна содержать:

- code;
- name;
- tourism_type;
- sort_order;
- active;
- source/reference, если категория получена из внешнего нормативного источника;
- version/effective_from при необходимости.

Категория, присвоенная конкретному походу, должна сохраняться в истории даже если справочник позднее изменён.

## 5. Факт участия

Для каждого участника похода сохраняются:

- факт допуска/регистрации;
- фактическое участие;
- дата/период участия при необходимости;
- роль в походе;
- пройденная дистанция;
- результат;
- подтверждение руководителя;
- комментарий.

Частичное участие не должно автоматически считаться полным прохождением маршрута.

## 6. Подтверждение

Каждый факт, который влияет на официальный/подтверждённый туристский опыт, должен иметь источник подтверждения.

Возможные уровни:

- club_record;
- instructor_confirmed;
- event_result;
- imported_record;
- official_document.

Перечень уровней расширяемый.

## 7. Агрегируемые показатели

Система может рассчитывать:

- количество подтверждённых походов;
- суммарный подтверждённый километраж;
- число походов по видам туризма;
- количество категорийных мероприятий;
- опыт руководителя/инструктора;
- опыт участника;
- квалификационные достижения.

Каждый агрегат должен иметь однозначный источник и формулу.

## 8. Расчёт километража

Приоритет источников:

1. подтверждённая индивидуальная дистанция `TripParticipant.completed_distance`;
2. документированное значение по сегменту;
3. фактическая дистанция похода с правилами распределения, если это разрешено настройкой;
4. плановая дистанция не используется для подтверждённого пройденного километража.

Плановые показатели используются отдельно от фактических.

## 9. Правило полного зачёта

Полный зачёт похода для туристского опыта допускается только при выполнении условий, заданных клубной политикой.

Минимальная техническая модель должна поддерживать:

- completed;
- partial;
- not_completed;
- disqualified;
- pending_confirmation.

## 10. Квалификации

`Qualification` должна позволять хранить:

- тип квалификации;
- уровень;
- вид туризма;
- дату получения;
- срок действия;
- основание;
- подтверждающий документ;
- статус проверки.

Квалификация не должна автоматически считаться подтверждённой только из факта определённого количества походов, пока не утверждено соответствующее правило.

## 11. Инструкторский опыт

Инструктор/руководитель похода должен иметь отдельные показатели опыта, не смешанные с обычным участием.

Минимально различать роли:

- participant;
- assistant;
- instructor;
- leader;
- deputy_leader;
- other.

Опыт руководителя может рассчитываться отдельно от общего опыта участника.

## 12. Аномалии и исправления

Если фактические данные изменены:

- исходная запись не должна бесследно изменяться;
- изменение должно быть аудировано;
- производные показатели должны быть пересчитаны;
- ранее выданное достижение может быть отозвано только отдельным контролируемым workflow.

## 13. Импорт истории

Импорт исторических походов должен поддерживать:

- dry-run;
- validation report;
- duplicate detection;
- mapping tourism types;
- mapping difficulty categories;
- source reference;
- imported status;
- возможность ручного подтверждения.

Импортированные записи не считаются официально подтверждёнными автоматически, если политика клуба этого не разрешает.

## 14. Открытые нормативные решения

До реализации расчётного движка необходимо утвердить:

1. официальный набор видов туризма клуба;
2. используемую классификацию сложности и её версию/источник;
3. что именно считается походом для стажа;
4. правила полного и частичного зачёта;
5. правила зачёта километража;
6. правила учёта руководства;
7. правила влияния участия в соревнованиях и турслётах;
8. правила подтверждения импортированной истории.

## 15. Acceptance Criteria

- Первичные факты отделены от агрегатов профиля.
- Категории сложности и виды туризма являются расширяемыми справочниками.
- Частичное участие поддерживается.
- Есть источник/уровень подтверждения.
- Изменение исходного факта запускает контролируемый пересчёт.
- Плановые и фактические показатели не смешиваются.
- Импорт истории имеет dry-run и валидацию.
- Нормативные правила расчёта вынесены из UI и могут быть версионированы.
