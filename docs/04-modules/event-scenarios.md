# TourCRM — Пользовательские сценарии мероприятий

## Назначение

Документ фиксирует сквозные сценарии работы с мероприятиями и расписанием.

## Scenario E-01 — Инструктор создаёт занятие

**Актор:** instructor

1. Открывает создание мероприятия.
2. Выбирает тип `lesson` или `training`.
3. Указывает название, дату, время, timezone и место.
4. Назначает одну или несколько групп.
5. При необходимости назначает себя/другого инструктора.
6. Сохраняет как draft.
7. Проверяет данные.
8. Публикует.
9. Система делает мероприятие доступным целевой аудитории.
10. При включённых уведомлениях создаются задания доставки.

## Scenario E-02 — Перенос занятия

**Актор:** instructor/admin с permission изменения Event.

1. Открывает опубликованное мероприятие.
2. Меняет дату/время.
3. Указывает причину переноса.
4. Система сохраняет историю старого значения.
5. Система создаёт audit record.
6. Система определяет затронутых получателей.
7. При включённом уведомлении ставится доставка через активные каналы.

## Scenario E-03 — Отмена занятия

**Актор:** instructor/admin.

1. Выбирает отмену.
2. Указывает причину.
3. Подтверждает.
4. Event переходит в `CANCELLED`.
5. Участники сохраняются в истории.
6. Уведомления создаются согласно настройкам.

## Scenario E-04 — Регистрация участника

**Актор:** member / guardian / instructor/admin согласно permissions.

1. Открывает карточку Event.
2. Выполняет регистрацию для себя или доступного ребёнка.
3. Система проверяет доступность регистрации.
4. Создаётся `EventParticipation`.
5. Повторная регистрация не создаёт дубликат.
6. Статус уведомляется согласно настройкам.

## Scenario E-05 — Отметка посещаемости

**Актор:** instructor/admin.

1. Открывает ведомость Event.
2. Система показывает зарегистрированных участников.
3. Ответственный выставляет статусы.
4. Для `absent`/`excused` при включённом правиле указывает причину.
5. Изменение фиксируется в audit.
6. Данные становятся доступны аналитике и профилю участника.

## Scenario E-06 — Создание серии занятий

**Актор:** instructor/admin.

1. Создаёт базовую Event Series.
2. Указывает RRULE и период действия.
3. Сохраняет серию.
4. Система рассчитывает occurrences в пределах необходимого горизонта.
5. Пользователь может изменять отдельный occurrence без изменения всей серии.

## Scenario E-07 — Перенос одного occurrence

1. Пользователь выбирает конкретное occurrence.
2. Выбирает изменение только этого события.
3. Система создаёт/обновляет exception.
4. Остальные occurrence не изменяются.
5. Audit отражает изменение.

## Scenario E-08 — Массовая отметка группы

1. Инструктор выбирает Event.
2. Выбирает массовое действие.
3. Указывает статус.
4. Система применяет его только к разрешённому набору участников.
5. Результат проверяется на idempotency.
6. Все существенные изменения журналируются.

## Scenario E-09 — Родитель просматривает расписание ребёнка

1. Guardian входит в систему.
2. Открывает календарь/agenda ребёнка.
3. Система определяет детей через активные GuardianRelationship.
4. Показываются только разрешённые мероприятия.
5. Скрытые поля других участников не раскрываются.

## Scenario E-10 — Конфликт инструктора

1. Создаётся/переносится Event.
2. Backend проверяет пересечения времени с другими мероприятиями.
3. При конфликте система показывает предупреждение.
4. Если политика клуба требует блокировки — операция отклоняется.
5. Если используется warning-only — пользователь может продолжить, если имеет соответствующее право.
