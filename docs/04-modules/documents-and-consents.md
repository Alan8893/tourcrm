# TourCRM — Documents and Consents

## 1. Назначение

Модуль отвечает за хранение метаданных и безопасную работу с документами клуба, участников, законных представителей, мероприятий и других доменов, а также за фиксацию согласий.

Модуль не должен превращать PostgreSQL в файловое хранилище. База данных хранит метаданные и ссылки на объект хранения, а бинарное содержимое хранится в файловом/object storage согласно инфраструктурной спецификации.

## 2. Document

Document — логическая запись документа.

### Обязательные атрибуты

- id;
- club_id;
- document_type_id;
- title;
- status;
- owner_type;
- owner_id;
- storage_object_id;
- original_filename;
- mime_type;
- file_size;
- checksum;
- uploaded_by;
- uploaded_at;
- issued_at, если применимо;
- valid_from, если применимо;
- valid_to, если применимо;
- version;
- description;
- created_at;
- updated_at.

`checksum` используется для контроля целостности и обнаружения случайных дублей.

## 3. DocumentType

Справочник типов документов должен быть настраиваемым.

Примеры:

- заявление о вступлении;
- согласие законного представителя;
- медицинская справка;
- страховой документ;
- разрешение на участие в мероприятии;
- маршрутный документ;
- отчёт о походе;
- сертификат;
- грамота;
- финансовый документ;
- внутренний документ клуба.

Тип документа должен определять дополнительные требования:

- обязательность срока действия;
- необходимость владельца;
- допустимый тип субъекта;
- необходимость подтверждения;
- уровень конфиденциальности.

## 4. Версионирование

Изменение содержимого документа не должно молча перезаписывать историю.

При изменении создаётся новая версия либо новый DocumentVersion, в зависимости от выбранной физической модели БД.

История должна сохранять:

- номер версии;
- автора загрузки;
- дату;
- checksum;
- причину изменения.

## 5. Статусы документа

Минимальные статусы:

`draft` → `active` → `expired` / `revoked` / `archived`.

Конкретный переход определяется типом документа.

Просроченный документ сохраняется как исторический факт.

## 6. Срок действия

Если документ имеет срок действия:

- `valid_to` обязателен;
- система должна уметь находить документы, истекающие в заданный период;
- уведомление об истечении должно быть реализовано через Notification Service;
- истечение срока не удаляет документ.

## 7. Consent

Consent представляет отдельное юридически значимое согласие.

Минимальные атрибуты:

- id;
- club_id;
- subject_person_id;
- guardian_person_id, если применимо;
- consent_type;
- policy_document/version;
- status;
- granted_at;
- revoked_at;
- source_document_id, если согласие подтверждается файлом;
- created_at;
- updated_at.

## 8. Принцип версии текста

Согласие должно ссылаться не просто на название политики, а на конкретную версию текста/условий.

Изменение текста согласия не изменяет историческую запись.

Например:

`photo_publication.v1`
`photo_publication.v2`

— разные юридические основания.

## 9. Участие несовершеннолетних

Для несовершеннолетнего субъекта система должна поддерживать проверку, кто имеет право дать согласие.

Связь с GuardianRelationship является необходимым фактором авторизации, но конкретное юридическое основание и обязательность отдельного согласия определяются политикой клуба и применимым законодательством.

Система не должна делать юридические выводы только из даты рождения.

Она должна позволять настроить требование согласия для конкретного действия или типа документа.

## 10. Привязка документов

Document может принадлежать:

- Person;
- GuardianRelationship;
- Event;
- Trip;
- Club;
- Payment/Expense;
- Equipment.

Связь должна быть типизированной и проверяемой API.

## 11. Хранилище

Бинарные файлы должны храниться отдельно от PostgreSQL.

На уровне абстракции StorageObject должен поддерживать:

- provider;
- bucket/volume;
- object key;
- checksum;
- size;
- content type;
- encryption metadata при использовании;
- created_at.

Конкретный storage backend выбирается отдельным ADR.

Архитектура не должна зависеть от локального диска настолько, чтобы миграция на object storage требовала переделки доменной модели.

## 12. Доступ к файлам

Нельзя выдавать бинарные файлы через угадываемые публичные URL.

Доступ должен проходить через авторизацию TourCRM либо краткоживущую подписанную ссылку, выдаваемую только после проверки прав.

Уровень доступа определяется владельцем документа, типом документа и permissions.

## 13. Загрузка

API загрузки должно проверять как минимум:

- размер;
- MIME/type;
- расширение;
- допустимый тип документа;
- права пользователя;
- целевой объект;
- целостность файла.

При необходимости должна быть предусмотрена антивирусная проверка/сервис сканирования отдельной инфраструктурной задачей.

## 14. Скачивание и просмотр

Система должна различать:

- возможность просмотра метаданных;
- возможность просмотра содержимого;
- возможность скачивания;
- возможность удаления/архивирования.

Эти действия не обязаны иметь одинаковое permission.

## 15. Конфиденциальность

Документы должны иметь уровень конфиденциальности, как минимум:

- internal;
- restricted;
- sensitive.

Медицинские и аналогичные чувствительные документы должны иметь более строгий доступ, чем обычные сертификаты или публично опубликованные материалы.

## 16. Аудит

В AuditLog должны попадать:

- загрузка;
- просмотр содержимого чувствительного документа;
- скачивание;
- изменение метаданных;
- создание новой версии;
- изменение статуса;
- отзыв;
- удаление/архивирование;
- создание/изменение/отзыв Consent.

Сам файл в AuditLog не копируется.

## 17. Retention

Правила хранения должны зависеть от типа документа.

До определения юридических сроков система должна поддерживать конфигурацию retention policy без автоматического безвозвратного удаления исторических документов по умолчанию.

## 18. Пользовательские сценарии

### Загрузка документа участника

1. Уполномоченный пользователь открывает профиль.
2. Выбирает тип документа.
3. Загружает файл.
4. Система валидирует файл.
5. Создаёт Document и StorageObject.
6. Записывает AuditLog.
7. При наличии срока действия рассчитывает статус.

### Истечение срока

1. Background job находит документы, приближающиеся к `valid_to`.
2. Создаёт уведомление для соответствующих получателей.
3. После наступления срока документ получает `expired` согласно правилам типа.

### Работа с Consent

1. Система определяет субъект и тип действия.
2. Проверяет актуальную версию требуемого согласия.
3. Если согласие отсутствует или устарело, действие блокируется или переводится в статус pending согласно бизнес-правилу.
4. После подтверждения создаётся Consent с привязкой к версии текста.

## 19. API-level requirements

API должен поддерживать минимум:

- создание метаданных документа;
- upload content;
- получение списка документов с фильтрами;
- получение метаданных;
- выдачу доступа к содержимому;
- создание новой версии;
- изменение статуса;
- архивирование согласно policy;
- создание/просмотр/отзыв Consent.

Ответ API не должен раскрывать внутренний `storage_object_id` как механизм доступа к файлу без необходимости.

## 20. Acceptance Criteria

- [ ] Document отделён от бинарного StorageObject.
- [ ] Поддерживаются типы документов.
- [ ] Поддерживаются версии.
- [ ] История документов сохраняется.
- [ ] Срок действия и просрочка моделируются явно.
- [ ] Consent хранит версию текста/политики.
- [ ] Поддерживаются связи guardian/несовершеннолетний.
- [ ] Бинарные файлы не требуют хранения в PostgreSQL blob.
- [ ] Доступ к файлу проходит авторизацию.
- [ ] Чувствительные документы имеют отдельный уровень доступа.
- [ ] Значимые операции аудируются.
- [ ] Архитектура допускает миграцию storage backend.
- [ ] Retention policy конфигурируема.
