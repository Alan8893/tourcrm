# TourCRM — Core Use Cases

## 1. Назначение

Документ описывает ключевые пользовательские сценарии TourCRM и связывает бизнес-требования, роли, UI и backend behavior.

Use Case не заменяет детальную спецификацию отдельного модуля, но задаёт обязательную end-to-end логику.

## 2. UC-01 Самостоятельная регистрация

**Actors:** потенциальный пользователь.

### Preconditions

- публичная регистрация включена;
- пользователь не имеет активной учётной записи с тем же идентификатором.

### Flow

1. Пользователь открывает регистрацию.
2. Вводит обязательные данные.
3. Система выполняет client-side validation.
4. Backend повторно валидирует данные.
5. Создаётся Person/User в состоянии, предусмотренном политикой регистрации.
6. Если требуется подтверждение администратора, User получает статус `pending_approval`.
7. Пользователю отображается понятный статус.
8. После административного подтверждения система разрешает вход.

### Security

- пароль никогда не хранится в исходном виде;
- registration endpoint защищён от массового abuse;
- нельзя раскрывать существование аккаунта через различающиеся сообщения там, где это создаёт user enumeration risk.

## 3. UC-02 Регистрация по приглашению

**Actors:** потенциальный пользователь, приглашающий пользователь.

### Flow

1. Администратор/разрешённый пользователь создаёт invitation.
2. Система генерирует одноразовый или ограниченный по использованию токен.
3. Получатель открывает ссылку.
4. Система проверяет срок действия, статус и ограничения invitation.
5. Пользователь завершает регистрацию.
6. Необходимая Person/ClubMembership/User связь создаётся согласно типу приглашения.
7. Invitation переводится в consumed/expired state.

Invitation token не должен содержать чувствительные персональные данные.

## 4. UC-03 Подтверждение заявки администратором

1. Администратор открывает список pending registrations.
2. Просматривает данные кандидата.
3. При необходимости корректирует или дополняет профиль.
4. Одобряет либо отклоняет заявку.
5. Система записывает действие в AuditLog.
6. Пользователь получает уведомление согласно настройкам.

## 5. UC-04 Создание участника через импорт

1. Администратор загружает подготовленный файл.
2. Система проверяет формат и структуру.
3. Система валидирует строки.
4. Ошибочные строки возвращаются с понятными причинами.
5. Валидные записи импортируются.
6. Для каждой созданной Person/ClubMembership фиксируется источник импорта.
7. Результат импорта доступен администратору.
8. Импорт не должен частично портить существующие данные при нарушении заданных transaction rules.

## 6. UC-05 Создание и ведение профиля участника

1. Авторизованный пользователь открывает профиль.
2. Система показывает только разрешённые поля.
3. Уполномоченный пользователь изменяет данные.
4. Backend проверяет permission и validation.
5. Изменение сохраняется.
6. AuditLog фиксирует существенное действие.

## 7. UC-06 Добавление родителя/законного представителя

1. Уполномоченный пользователь создаёт Person родителя либо использует существующую Person.
2. Создаёт GuardianRelationship с ребёнком.
3. Указывает тип связи и статус.
4. При необходимости определяет primary contact.
5. Если родителю требуется доступ, создаётся/привязывается User.
6. Backend проверяет право действовать от имени соответствующего ребёнка.

## 8. UC-07 Ведение группы

1. Администратор создаёт группу.
2. Назначает инструкторов.
3. Добавляет/переводит участников.
4. Система сохраняет историю принадлежности.
5. Группа появляется в календарях и соответствующих фильтрах.

## 9. UC-08 Создание мероприятия

1. Администратор или инструктор с permission создаёт Event.
2. Выбирает тип мероприятия.
3. Указывает название, время, timezone, место и описание.
4. Добавляет группы, участников, инструкторов/руководителей.
5. Для специализированного типа создаёт связанный Trip/TourSlet/Competition объект.
6. При сохранении система валидирует пересечения/ограничения, определённые модулем.
7. При необходимости формирует уведомления.

## 10. UC-09 Проведение занятия и отметка посещаемости

1. Инструктор открывает Event.
2. Система показывает состав ожидаемых участников.
3. Инструктор отмечает attendance status.
4. Для отсутствующих может указать reason.
5. Система сохраняет отметки и время изменения.
6. Изменения отражаются в статистике посещаемости.

## 11. UC-10 Перенос или отмена мероприятия

1. Уполномоченный пользователь изменяет время либо переводит Event в cancelled.
2. При отмене причина обязательна, если это определено типом события.
3. Система сохраняет историю изменения.
4. Пользователи с соответствующими подписками получают уведомления.
5. Старое состояние не должно быть потеряно из аудита.

## 12. UC-11 Проведение похода

1. Создаётся Event типа `trip`.
2. Создаётся Trip extension.
3. Выбирается/создаётся Route.
4. Загружается GPX при наличии.
5. Назначаются руководитель и инструкторы.
6. Формируется состав участников.
7. После похода вносится фактическая дистанция и результаты.
8. TripParticipant фиксирует фактическое участие и пройденную дистанцию.
9. Система обновляет производные туристские агрегаты.
10. Доступные автоматические достижения пересчитываются по правилам.

## 13. UC-12 Выдача достижения

### Manual

1. Уполномоченный пользователь открывает профиль.
2. Выбирает достижение.
3. Указывает основание при необходимости.
4. Система создаёт AchievementAward.
5. Действие попадает в аудит.

### Automatic

1. Происходит событие, влияющее на eligibility.
2. Система оценивает правила achievement.
3. При выполнении условий создаётся AchievementAward.
4. Повторная выдача предотвращается, если достижение одноразовое.

## 14. UC-13 Работа с документом

1. Уполномоченный пользователь загружает Document.
2. Указывает тип, объект, срок действия и дополнительные метаданные.
3. Система сохраняет metadata и файл в object/file storage.
4. Пользователям с permission становится доступно действие просмотра/скачивания.
5. До истечения срока может быть создано уведомление.

## 15. UC-14 Согласие родителя

1. Система определяет необходимость Consent.
2. Родителю показывается запрос.
3. Родитель подтверждает или отклоняет согласие согласно доступному механизму.
4. Система фиксирует субъект, версию текста, дату и подписанта.
5. При необходимости сохраняется подтверждающий документ.
6. Изменение попадает в аудит.

## 16. UC-15 Выдача оборудования

1. Ответственный пользователь выбирает Equipment.
2. Выбирает получателя и мероприятие.
3. Фиксирует состояние до выдачи и ожидаемую дату возврата.
4. Система создаёт EquipmentIssue.
5. При возврате записывается состояние после возврата.
6. Система сохраняет историю.

## 17. UC-16 Финансовая операция

1. Уполномоченный пользователь создаёт Payment или Expense.
2. Указывает тип, сумму, дату и связанный контекст.
3. Backend проверяет permission и бизнес-правила.
4. Операция сохраняется.
5. Финансовые агрегаты пересчитываются.
6. Действие попадает в аудит.

Финансовый документ должен запрещать изменение критических полей после финализации без отдельного documented correction flow.

## 18. UC-17 Отправка уведомления

1. Происходит событие домена или запланированная отправка.
2. Notification service создаёт логическое уведомление.
3. Выбираются получатели по правилам.
4. Выбираются разрешённые каналы.
5. Message отправляется асинхронно при необходимости.
6. Результат доставки и retry state сохраняются.
7. Ошибки интеграции не должны блокировать основную транзакцию, если уведомление не является обязательной частью операции.

## 19. UC-18 Работа с базой знаний

1. Автор создаёт Article в draft.
2. Материал проходит review, если workflow включён.
3. Уполномоченный пользователь публикует материал.
4. Создаётся version history.
5. Пользователи видят только опубликованные версии, доступные их роли.

## 20. UC-19 Просмотр родителем данных ребёнка

1. Guardian авторизуется.
2. Система определяет активные GuardianRelationship.
3. Система отображает список доступных детей.
4. При открытии ребёнка backend проверяет `children` scope.
5. Показываются только поля и разделы, разрешённые для guardian.

Родитель не получает доступ ко всему профилю автоматически только из-за наличия родственной связи.

## 21. UC-20 Административная аналитика

1. Администратор выбирает период/фильтры.
2. Backend формирует показатели из канонических источников.
3. UI показывает значения и применённые фильтры.
4. При необходимости пользователь экспортирует отчёт.

Производные показатели не должны становиться единственным источником истины.

## 22. UC-21 Импорт/экспорт

Поддерживаемые направления:
- участники;
- группы;
- мероприятия;
- attendance;
- финансовые данные в рамках отдельного documented import format.

Импорт и экспорт должны иметь версию формата.

## 23. UC-22 Работа при недоступности сети

Для LAN/Internet сценариев приложение должно корректно сообщать о временной недоступности backend.

Критические операции не должны тихо подтверждаться без получения серверного результата.

Offline-first синхронизация для mutation operations не входит в MVP без отдельного ADR.

## 24. Трассируемость

Каждый Use Case должен быть связан с:
- одним или несколькими FR-*;
- ролями;
- permissions;
- экраном/экранами;
- API endpoint'ами;
- acceptance criteria;
- тестами.

Матрица трассируемости будет развиваться вместе с детализацией модулей.
