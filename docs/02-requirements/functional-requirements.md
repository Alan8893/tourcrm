# TourCRM — Functional Requirements

## 1. Назначение

Документ описывает функциональные требования к первой полной версии TourCRM. Требования являются основой для декомпозиции проекта на GitHub Issues.

Обозначения:

- **MUST** — обязательное требование;
- **SHOULD** — желательно, но допустима аргументированная реализация иначе;
- **MAY** — опциональная возможность.

## 2. Authentication

### FR-AUTH-001
Система MUST поддерживать регистрацию новой учётной записи.

### FR-AUTH-002
Система MUST поддерживать вход по идентификатору пользователя и паролю.

### FR-AUTH-003
Система MUST поддерживать выход из системы и отзыв активной сессии.

### FR-AUTH-004
Система MUST обеспечивать безопасное хранение паролей только в виде стойких password hashes.

### FR-AUTH-005
Система MUST поддерживать восстановление доступа через подтверждённый канал связи, если канал предусмотрен пользователем.

### FR-AUTH-006
Система MUST различать неподтверждённую регистрацию, подтверждённый аккаунт, заблокированный и деактивированный аккаунт.

## 3. Registration / Onboarding

### FR-REG-001
Самостоятельная регистрация MUST создавать заявку на вступление в клуб со статусом pending.

### FR-REG-002
Администратор MUST иметь возможность подтвердить или отклонить заявку.

### FR-REG-003
Система MUST поддерживать приглашения по ссылке/коду.

### FR-REG-004
Система MUST поддерживать импорт людей/участников без создания User.

### FR-REG-005
После импорта пользователь SHOULD иметь возможность получить приглашение и привязать существующий Person к User вместо создания дубликата.

## 4. Users / Persons / Membership

### FR-USER-001
Администратор MUST иметь CRUD для User в пределах доступной ему области.

### FR-USER-002
Система MUST позволять Person существовать без User.

### FR-USER-003
Система MUST поддерживать членство Person в Club с историей статусов.

### FR-USER-004
Система MUST предотвращать создание некорректных дублирующих активных идентификаторов пользователя.

### FR-USER-005
Деактивация User MUST сохранять Person и историю деятельности.

## 5. Roles / Permissions

### FR-RBAC-001
Система MUST поддерживать базовые роли admin, instructor, member, guardian.

### FR-RBAC-002
User MUST иметь возможность иметь несколько ролей.

### FR-RBAC-003
Проверка доступа MUST происходить на backend.

### FR-RBAC-004
Permission MUST поддерживать scope.

### FR-RBAC-005
Администратор MUST иметь интерфейс просмотра/управления назначениями ролей и permissions, если это разрешено его уровнем доступа.

## 6. Guardians

### FR-GUA-001
Система MUST поддерживать связь guardian ↔ child в обе стороны через GuardianRelationship.

### FR-GUA-002
Один guardian MUST иметь возможность быть связанным с несколькими детьми.

### FR-GUA-003
Один child MUST иметь возможность иметь нескольких guardians.

### FR-GUA-004
Guardian MUST видеть данные ребёнка только при наличии активной связи и соответствующего permission.

### FR-GUA-005
Guardian SHOULD видеть расписание, мероприятия, посещаемость, документы и достижения ребёнка в пределах разрешённой политики клуба.

## 7. Member Profile

### FR-MEM-001
Система MUST иметь карточку участника.

### FR-MEM-002
Карточка MUST отображать ФИО и основные контактные данные.

### FR-MEM-003
Карточка SHOULD отображать дату рождения, статус членства, группу и связанные контакты.

### FR-MEM-004
Туристский опыт, походы, достижения, квалификации и навыки MUST быть представлены отдельными разделами профиля.

### FR-MEM-005
Администратор/разрешённый инструктор MUST иметь возможность просматривать расширенную карточку участника согласно permission scope.

## 8. Groups

### FR-GRP-001
Администратор MUST создавать, изменять, закрывать и архивировать группы.

### FR-GRP-002
Участники MUST быть привязываемыми к группам с датами действия связи.

### FR-GRP-003
Система MUST сохранять историю переводов между группами.

### FR-GRP-004
Инструктор MUST видеть участников назначенных ему групп.

## 9. Events / Schedule

### FR-EVT-001
Система MUST иметь единый календарь мероприятий.

### FR-EVT-002
Мероприятие MUST поддерживать типы lesson, training, trip, competition, tour_slet, excursion, meeting, other.

### FR-EVT-003
Пользователь с соответствующим permission MUST создавать и редактировать мероприятие.

### FR-EVT-004
Мероприятие MUST иметь дату/время начала и окончания, timezone context, место и статус.

### FR-EVT-005
Система MUST поддерживать повторяющиеся занятия как отдельный механизм планирования без разрушения отдельных экземпляров мероприятия.

### FR-EVT-006
Система MUST поддерживать перенос и отмену мероприятия с сохранением истории.

### FR-EVT-007
При отмене/переносе система SHOULD инициировать уведомления в соответствии с настройками.

### FR-EVT-008
Участники, инструкторы и ответственные SHOULD быть явно привязаны к мероприятию.

## 10. Attendance

### FR-ATT-001
Система MUST поддерживать отметку посещаемости.

### FR-ATT-002
Посещаемость MUST быть отделена от факта регистрации на мероприятие.

### FR-ATT-003
Инструктор/руководитель с permission MUST иметь возможность отмечать посещаемость своей группы/мероприятия.

### FR-ATT-004
Система MUST хранить причину отсутствия, если она указана или обязательна политикой клуба.

### FR-ATT-005
Изменение уже зафиксированной посещаемости MUST быть аудируемым.

## 11. Trips / Tourism

### FR-TRP-001
Поход MUST быть специализированным мероприятием.

### FR-TRP-002
Поход MUST поддерживать вид туризма, регион, руководителя и состав участников.

### FR-TRP-003
Система MUST поддерживать маршрутную информацию.

### FR-TRP-004
Система MUST поддерживать GPX-файлы и производные геоданные.

### FR-TRP-005
Система SHOULD сохранять плановую и фактическую дистанцию/длительность.

### FR-TRP-006
Система MUST фиксировать индивидуальное участие человека в походе отдельно от общей регистрации на Event.

### FR-TRP-007
Система MUST иметь источник расчёта туристского опыта на основе подтверждённых фактов походов.

## 12. Tourist Profile

### FR-TOUR-001
Система MUST иметь туристский профиль участника.

### FR-TOUR-002
Система SHOULD агрегировать число походов, подтверждённый километраж и иные показатели.

### FR-TOUR-003
Агрегированные показатели MUST быть пересчитываемыми из первичных данных.

## 13. Achievements / Skills / Qualifications

### FR-ACH-001
Система MUST поддерживать каталог достижений.

### FR-ACH-002
Достижения MUST поддерживать manual и automatic способы получения.

### FR-ACH-003
Система MUST хранить историю выдачи достижения.

### FR-ACH-004
Система SHOULD поддерживать автоматическую проверку правил достижения.

### FR-SKILL-001
Система MUST поддерживать каталог туристских навыков.

### FR-QUAL-001
Система MUST поддерживать формализованные квалификации/разряды.

### FR-QUAL-002
Квалификация SHOULD иметь возможность привязки к документу и сроку действия.

### FR-RATING-001
Система SHOULD иметь пользовательский рейтинг, но функция MUST отключаться через feature setting.

## 14. Knowledge Base

### FR-KB-001
Система MUST поддерживать публикацию материалов базы знаний.

### FR-KB-002
Материалы MUST иметь автора, статус и категорию.

### FR-KB-003
Опубликованные материалы SHOULD поддерживать версионирование.

### FR-KB-004
Материалы SHOULD связываться с навыками, мероприятиями и другими объектами.

## 15. Documents / Consents

### FR-DOC-001
Система MUST поддерживать загрузку и хранение метаданных документов.

### FR-DOC-002
Система MUST поддерживать срок действия документа.

### FR-DOC-003
Система SHOULD уведомлять о приближении срока истечения документов.

### FR-DOC-004
Система MUST поддерживать согласия с указанием версии текста.

### FR-DOC-005
Система MUST сохранять историю предоставленных и отозванных согласий.

## 16. Equipment

### FR-EQP-001
Система MUST поддерживать каталог имущества клуба.

### FR-EQP-002
Каждая единица оборудования MUST иметь уникальный инвентарный идентификатор.

### FR-EQP-003
Система MUST поддерживать выдачу оборудования человеку и/или мероприятию.

### FR-EQP-004
Система MUST сохранять историю выдачи и возврата.

## 17. Finance

### FR-FIN-001
Система MUST поддерживать учёт поступлений и расходов клуба.

### FR-FIN-002
Система MUST поддерживать платежи, связанные с участником/мероприятием при необходимости.

### FR-FIN-003
Финансовые операции MUST иметь статусы и/или корректирующие операции вместо бесследного удаления проведённых операций.

### FR-FIN-004
Финансовый модуль MUST поддерживать feature setting `finance.enabled`.

## 18. Notifications

### FR-NOT-001
Система MUST иметь единый механизм системных уведомлений.

### FR-NOT-002
Должны поддерживаться каналы email, Telegram и MAX.

### FR-NOT-003
Система MUST сохранять статус доставки.

### FR-NOT-004
Система SHOULD поддерживать повторные попытки доставки.

### FR-NOT-005
Пользователь SHOULD иметь настройки предпочтительных каналов и типов уведомлений в пределах политики клуба.

## 19. Calendar Integrations

### FR-CAL-001
Система SHOULD поддерживать интеграцию календаря.

### FR-CAL-002
На первом этапе предпочтительна экспортная/подписочная интеграция, например ICS, прежде чем реализовывать двустороннюю синхронизацию с внешними календарями.

## 20. Communications

### FR-COM-001
Система MUST поддерживать объявления/уведомления внутри CRM.

### FR-COM-002
Telegram SHOULD использоваться как внешний канал оперативной коммуникации.

### FR-COM-003
Встроенный чат MAY быть реализован позже после уточнения требований.

## 21. Analytics / Reporting

### FR-ANL-001
Система MUST иметь базовый административный dashboard.

### FR-ANL-002
Dashboard SHOULD отображать число участников, активность, мероприятия и посещаемость.

### FR-ANL-003
Система SHOULD поддерживать отчёты по группам, участникам, мероприятиям и туристскому опыту.

### FR-ANL-004
Экспорт отчётов в CSV/XLSX/PDF SHOULD поддерживаться по мере необходимости конкретного отчёта.

## 22. Audit

### FR-AUD-001
Система MUST вести audit log для критичных изменений.

### FR-AUD-002
Audit log MUST фиксировать actor, action, target, timestamp и результат.

### FR-AUD-003
Audit log MUST быть недоступен для изменения обычными прикладными операциями.

## 23. Search / Filtering

### FR-SRH-001
Система MUST поддерживать поиск участников по основным идентификаторам.

### FR-SRH-002
Система SHOULD поддерживать фильтры по группе, статусу, возрасту, ролям и другим релевантным признакам.

### FR-SRH-003
Списочные экраны MUST поддерживать предсказуемые сортировку и пагинацию там, где это необходимо по объёму данных.

## 24. Mobile / Responsive

### FR-MOB-001
Frontend MUST быть адаптивным.

### FR-MOB-002
Основные пользовательские сценарии MUST быть доступны на смартфоне.

### FR-MOB-003
Не допускается отдельный мобильный codebase на первой версии без отдельного ADR.

## 25. LAN / Internet

### FR-NET-001
Приложение MUST работать в локальной сети клуба при соответствующей конфигурации инфраструктуры.

### FR-NET-002
Приложение MUST поддерживать работу через Internet с использованием reverse proxy и TLS в production deployment.

### FR-NET-003
Архитектура не должна предполагать постоянный доступ клиента к БД.

## 26. Feature Flags / Settings

### FR-SET-001
Система MUST поддерживать настройки включения необязательных модулей.

### FR-SET-002
Минимальный набор настраиваемых функций SHOULD включать achievements, rating, finance и внешние каналы уведомлений.

### FR-SET-003
Настройки функций MUST храниться централизованно и иметь аудит изменений для критичных опций.

## 27. Import / Export

### FR-IMP-001
Система MUST поддерживать импорт участников из структурированного файла.

### FR-IMP-002
Импорт MUST валидировать входные данные и выдавать понятный отчёт об ошибках.

### FR-EXP-001
Система SHOULD поддерживать экспорт данных и отчётов с учётом permissions.

## 28. TourSlet integration

### FR-TS-001
Архитектура MUST предусматривать интеграцию отдельного сайта проведения турслётов.

### FR-TS-002
Конкретный механизм интеграции (API, SSO, shared identity, events, синхронизация) определяется после анализа предоставленного архива сайта.

### FR-TS-003
Интеграция MUST избегать дублирования сущностей Person/User там, где возможно сопоставление.
