# TourCRM — Business Rules

## 1. Назначение

Документ определяет бизнес-правила, которым должна соответствовать система независимо от конкретной реализации UI, API или БД.

Документ является нормативным для реализации. Если поведение приложения противоречит правилу, реализация считается некорректной до отдельного изменения требования.

## 2. Базовые принципы

1. TourCRM обслуживает один конкретный туристский клуб.
2. Архитектура сохраняет сущность `Club`, чтобы явно обозначить границу организации и не блокировать последующее расширение.
3. Один человек (`Person`) может иметь одну или несколько ролей в клубе через назначение ролей, а не через взаимоисключающий тип профиля.
4. Учётная запись (`User`) не равна физическому лицу (`Person`) и не равна членству в клубе (`ClubMembership`).
5. Исторически значимые факты не должны теряться из-за изменения текущего состояния объекта.
6. Персональные данные доступны только субъектам и ролям, которым они необходимы для работы.
7. Проверка permissions выполняется на backend; скрытие элемента интерфейса само по себе не является защитой.

## 3. Пользователь и человек

### 3.1 Person

`Person` описывает физическое лицо независимо от наличия учётной записи.

Человек может существовать в системе без `User`, например после импорта списка участников.

### 3.2 User

`User` предоставляет доступ к системе.

Один `User` связан максимум с одним `Person`. Один `Person` не должен иметь несколько активных пользовательских учётных записей без отдельного документированного основания.

### 3.3 Деактивация

Деактивация `User` не удаляет `Person`, членство, участие в мероприятиях, достижения, документы или историю.

## 4. Членство в клубе

`ClubMembership` является исторической записью принадлежности человека к клубу.

Статус членства должен позволять как минимум различать:

- pending;
- active;
- suspended;
- inactive;
- archived.

Переход между статусами не должен уничтожать предыдущую историю.

Человек может повторно вступить в клуб после периода inactive; такое повторное вступление должно иметь корректную историю членства.

## 5. Родители и законные представители

1. У одного родителя/законного представителя может быть несколько детей.
2. У одного участника может быть несколько законных представителей.
3. Связь хранится через `GuardianRelationship`.
4. Связь имеет статус и тип отношения.
5. Доступ родителя к данным ребёнка определяется и существованием активной связи, и соответствующим permission.
6. Удаление/деактивация связи не удаляет исторические документы или события, где представитель являлся подписантом/контактом.

### 5.1 Основной контакт

У ребёнка может быть один или несколько представителей, но не более одного активного `primary contact` для конкретного типа контактной функции одновременно.

## 6. Несовершеннолетние

Система должна поддерживать признак несовершеннолетнего участника и связь с законными представителями.

Дата рождения является основанием для вычисления возраста; возраст не следует хранить как самостоятельное постоянное поле.

Юридические ограничения на конкретные действия несовершеннолетнего должны оформляться отдельными бизнес-правилами и не должны зашиваться в общий механизм возраста.

## 7. Регистрация и вступление в клуб

Поддерживаются три основных сценария:

### 7.1 Самостоятельная регистрация

`RegistrationRequest` создаётся пользователем и получает статус pending.

До подтверждения администратором пользователь не получает расширенных прав клуба.

### 7.2 Приглашение

Приглашение содержит:

- код/ссылку;
- срок действия;
- ограничение количества использований при необходимости;
- инициатора;
- целевую роль/группу при необходимости.

После использования приглашение становится недействительным, если достигнут лимит использования или истёк срок.

### 7.3 Импорт

Импорт может создать `Person` без `User`.

Приглашение в систему может быть отправлено позднее.

## 8. Роли

Базовые роли:

- admin;
- instructor;
- member;
- guardian.

Один `User` может иметь несколько ролей.

Роль не является достаточной проверкой доступа: authorization должна учитывать permission и scope.

## 9. Группы

1. Группа принадлежит клубу.
2. Член клуба может состоять в нескольких группах в разные периоды истории.
3. Для одного периода допускается одна основная учебная группа, если это правило будет включено в настройки клуба.
4. Перевод в другую группу не должен удалять прошлую принадлежность.
5. Закрытая группа сохраняется как историческая сущность.

## 10. Мероприятия

`Event` — базовая сущность календарного мероприятия.

Поддерживаются типы:

- lesson;
- training;
- trip;
- competition;
- tour_slet;
- excursion;
- meeting;
- other.

### 10.1 Жизненный цикл Event

Канонические статусы Event определены ADR-0018:

- `draft`;
- `published`;
- `in_progress`;
- `completed`;
- `cancelled`;
- `archived`.

Допустимые переходы:

```text
draft -> published
published -> in_progress
published -> cancelled
in_progress -> completed
in_progress -> cancelled
completed -> archived
cancelled -> archived
```

Другие переходы не допускаются базовым контрактом API. Статус `planned` не является отдельным состоянием: запланированное, но ещё не опубликованное мероприятие остаётся в `draft`.

Канонические значения статусов в домене и API записываются в lowercase.

### 10.2 Отмена

Отменённое мероприятие не удаляется.

Для отмены требуется причина. Участникам могут отправляться уведомления в зависимости от настроек клуба.

## 11. Запись на мероприятие

`EventParticipation` отделяет факт регистрации от факта посещения.

Минимально должны различаться:

- invited;
- registered;
- waitlisted;
- declined;
- attended;
- absent;
- excused;
- cancelled.

Нельзя считать человека посетившим мероприятие только потому, что он был зарегистрирован.

## 12. Посещаемость

Посещаемость отмечает инструктор или руководитель с соответствующим permission.

При указании статуса `absent` рекомендуется требовать причину, если это предусмотрено настройками клуба.

Изменение посещаемости после закрытия периода должно аудироваться.

## 13. Походы

Поход является специализированным объектом на базе `Event`.

Каждый поход должен иметь:

- вид туризма;
- руководителя;
- состав участников;
- маршрут или описание маршрута;
- планируемые и фактические показатели при наличии;
- итоговый статус.

### 13.1 Туристский стаж

Источником факта участия является `TripParticipant`, а не вручную введённый итоговый километраж в профиле.

Агрегаты туристского профиля должны быть вычисляемыми/пересчитываемыми.

Правила зачёта километража, категорий и отдельных видов опыта должны быть описаны в специализированной политике расчётов до реализации автоматических достижений.

## 14. Руководитель и инструкторы

Руководитель похода/мероприятия должен храниться явно.

Наличие роли `instructor` само по себе не означает, что пользователь является инструктором конкретного мероприятия.

У мероприятия должна быть явная связь с ответственными сотрудниками/инструкторами.

## 15. Достижения

Достижения бывают двух типов:

- manual;
- automatic.

Ручное достижение требует указания инициатора/выдавшего лица.

Автоматическое достижение должно основываться на формализованном и воспроизводимом правиле.

Выдача достижения не должна дублироваться, если одно и то же достижение рассчитано как одноразовое.

Рейтинг и система достижений могут быть отключены соответствующими feature settings.

Отключение функции не должно удалять исторические достижения.

## 16. Навыки и квалификации

`Skill` отражает текущую или исторически зафиксированную подготовку.

`Qualification` отражает формализованную квалификацию/разряд и при необходимости должна иметь документальное подтверждение и срок действия.

Достижение не заменяет квалификацию.

## 17. База знаний

Материалы базы знаний могут быть публичными внутри клуба или ограниченными по ролям/группам.

Публикация должна иметь статус и автора.

Изменения опубликованных материалов должны быть версионируемыми, чтобы существовала возможность определить содержание на момент проведения занятия/мероприятия.

## 18. Документы

Документы могут относиться к человеку, законному представителю, мероприятию, походу, клубу или финансовой записи.

Документ может иметь срок действия.

Истечение срока действия не удаляет документ, а переводит его в состояние expired/invalid согласно типу документа.

Для документов, которые влияют на допуск к мероприятию, критерии допуска должны быть задокументированы отдельно.

## 19. Согласия

Согласие всегда связано с конкретной версией текста/политики.

Изменение текста согласия должно создавать новую версию, а не переписывать старую запись.

Отозванное согласие не должно удалять факт его предыдущего предоставления.

## 20. Финансы

Финансовые операции не удаляются после проведения, если это нарушает финансовую историю.

Отмена операции должна отражаться отдельной корректирующей операцией или документированным статусом, а не бесследным удалением.

Оплата участника должна быть связана с конкретным основанием: мероприятием, задолженностью, взносом или другим финансовым объектом.

## 21. Снаряжение

Каждая единица снаряжения должна иметь уникальный инвентарный идентификатор в пределах клуба.

Выдача оборудования создаёт историческую запись `EquipmentIssue`.

Возврат фиксирует состояние оборудования после использования.

Удаление оборудования из текущего списка не должно уничтожать его историю использования.

## 22. Уведомления

Системное событие и доставка уведомления — разные сущности.

Неуспешная доставка не должна означать, что исходное событие не произошло.

Повторная попытка доставки должна быть идемпотентной и не создавать дубликаты без необходимости.

Пользователь должен иметь возможность отключать необязательные типы уведомлений в рамках разрешённой политики клуба.

## 23. Аудит

Любое изменение критичных персональных, финансовых, permission-related и исторически значимых данных должно быть аудируемым.

Аудит нельзя редактировать обычными прикладными действиями пользователя.

## 24. Поиск и удаление

Удаление должно следовать политике сохранения истории.

Там, где физическое удаление допустимо, должны быть явно определены зависимости и последствия.

По умолчанию для исторически значимых сущностей предпочтительнее архивирование/деактивация.

## 25. Настройки функций

Feature settings управляют доступностью необязательных функций, но не должны предоставлять права, которых нет у пользователя.

Пример: `finance.enabled=false` скрывает и отключает финансовый модуль, но `finance.enabled=true` не делает обычного участника финансовым администратором.

## 26. Timezone

Все события и временные отметки должны храниться однозначно.

Для серверного хранения предпочтительно использовать UTC с преобразованием в timezone клуба/пользователя при отображении.

`Event` сохраняет timezone контекста мероприятия, если это необходимо для корректного отображения.

## 27. Историчность

При изменении ФИО, группы, роли, статуса членства, состава мероприятия и других атрибутов, влияющих на историческую достоверность, старые факты не должны изменяться задним числом без явного действия с аудитом.

## 28. Изменение этих правил

Любое изменение данного документа:

1. фиксируется в Git;
2. при архитектурном влиянии сопровождается ADR;
3. при влиянии на реализацию отражается в Issue;
4. не считается действующим, пока документация и связанная реализация не приведены в согласованное состояние.
