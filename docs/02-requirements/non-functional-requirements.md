# TourCRM — Non-Functional Requirements

## 1. Назначение

Документ определяет нефункциональные требования TourCRM. Они являются обязательными архитектурными ограничениями для реализации и последующей технической приёмки.

## 2. Приоритеты

Приоритеты требований:

1. безопасность и целостность данных;
2. корректность бизнес-логики;
3. доступность и восстановление;
4. сопровождаемость;
5. производительность;
6. удобство эксплуатации;
7. масштабируемость.

## 3. Web и совместимость

Система должна быть адаптивным web-приложением.

Поддерживаются сценарии:

- desktop;
- laptop;
- tablet;
- smartphone.

Интерфейс не должен требовать отдельной кодовой базы для mobile.

Система должна корректно работать как через LAN, так и через Internet.

Основной протокол production-доступа — HTTPS.

HTTP допускается только для локальных development сценариев либо редиректа на HTTPS там, где это применимо.

## 4. Производительность

### NFR-PERF-001

Для типовых CRUD/API операций целевой p95 latency должен быть не более 500 ms на уровне backend при нормальной нагрузке без учёта медленного клиентского соединения.

### NFR-PERF-002

Операции, требующие фоновой обработки, не должны блокировать HTTP request дольше разумного интерактивного порога. Для длительных операций используется asynchronous job.

### NFR-PERF-003

Списковые интерфейсы обязаны поддерживать серверную пагинацию, фильтрацию и сортировку там, где объём данных может расти.

### NFR-PERF-004

Поиск не должен загружать весь набор записей в frontend.

### NFR-PERF-005

Большие файлы загружаются и скачиваются потоково либо через storage механизм, не через полную загрузку файла в RAM приложения.

## 5. Масштабируемость

Система должна корректно работать на одной машине для стартовой инсталляции.

Архитектура не должна требовать горизонтального масштабирования на первом этапе.

При дальнейшем росте должно быть возможно независимо масштабировать:

- frontend/reverse proxy;
- backend API;
- background workers;
- PostgreSQL;
- storage.

Состояние backend должно по возможности оставаться stateless, кроме явно определённых внешних хранилищ состояния.

## 6. Надёжность

### NFR-REL-001

Критичные операции изменения данных должны выполняться транзакционно.

### NFR-REL-002

Ошибки фоновых задач должны иметь retry policy и сохраняться в логах/job status.

### NFR-REL-003

Система должна корректно переживать перезапуск контейнеров без потери уже зафиксированных транзакций.

### NFR-REL-004

Восстановление базы данных и файлов должно быть проверяемым процессом, а не только фактом наличия backup-файлов.

## 7. Backup и disaster recovery

Должны резервироваться как минимум:

- PostgreSQL;
- пользовательские документы;
- фотографии;
- GPX;
- критичные конфигурации.

Резервные копии не должны храниться только на том же физическом диске, что и production data.

Должны быть определены:

- RPO;
- RTO;
- retention backups;
- процедура восстановления;
- периодическая проверка restore.

Конкретные численные RPO/RTO являются инфраструктурным решением и должны быть зафиксированы до production launch.

## 8. Безопасность

### NFR-SEC-001

Все изменения доступа к данным должны проверяться на backend.

UI-скрытие элемента не считается механизмом безопасности.

### NFR-SEC-002

Пароли не хранятся в открытом виде.

### NFR-SEC-003

Secrets не хранятся в Git репозитории.

### NFR-SEC-004

Чувствительные данные не должны попадать в обычные application logs.

### NFR-SEC-005

Файловое содержимое защищённых документов не должно быть публично доступным по постоянному URL.

### NFR-SEC-006

Изменение критичных данных должно быть аудируемым.

### NFR-SEC-007

API должен защищаться от базовых классов атак, включая brute force на auth endpoints, injection, некорректный access control и небезопасную обработку файлов.

## 9. Персональные данные

Система должна проектироваться с учётом требований применимого законодательства о персональных данных.

Для персональных и чувствительных данных должны быть реализованы:

- минимизация доступа;
- принцип least privilege;
- аудит;
- управляемая retention policy;
- разграничение ролей;
- возможность архивирования.

Юридические требования должны быть дополнительно проверены перед production deployment в конкретной юрисдикции.

## 10. Аудит и трассировка

Критичные операции должны иметь correlation/request id.

Логи и AuditLog должны позволять связать:

`request → actor → action → result → target`.

Системное время хранится в UTC. UI показывает даты в часовом поясе пользователя или клуба согласно бизнес-правилу.

## 11. Наблюдаемость

Production должен предоставлять минимум:

- structured application logs;
- health endpoint;
- readiness endpoint;
- error monitoring;
- базовые системные метрики;
- состояние фоновых задач.

Health и readiness должны различать:

- процесс приложения жив;
- приложение готово принимать запросы;
- критичные зависимости доступны.

## 12. Конфигурация

Конфигурация должна разделяться на:

- безопасно версионируемые defaults;
- environment-specific configuration;
- secrets.

Никакие секреты не должны попадать в source control, Docker image или обычные логи.

## 13. Database

PostgreSQL является source of truth для транзакционных доменных данных.

Миграции должны быть версионируемыми и применяться последовательно.

Изменение схемы БД выполняется через миграции, а не ручное изменение production schema.

## 14. Storage

Binary storage должен быть абстрагирован от доменной модели.

Минимально поддерживаемые операции:

- upload;
- download/stream;
- delete/archive согласно policy;
- metadata;
- checksum.

## 15. Background processing

Background jobs используются для задач, которые:

- не должны блокировать HTTP request;
- выполняются по расписанию;
- требуют retry;
- работают с уведомлениями;
- перерабатывают документы/медиа;
- пересчитывают производные показатели.

Redis допускается как infrastructure component для очереди/cache, но бизнес-истина не должна храниться только в Redis.

## 16. Локальная эксплуатация

Для LAN deployment должна существовать возможность запуска системы без обязательной зависимости от внешних SaaS.

Внешние integrations должны быть изолированы feature settings и graceful degradation:

если Telegram/MAX/email недоступны, core CRM должна продолжать работу.

## 17. Международность и локализация

Первая версия интерфейса — русский язык.

Архитектура frontend/backend должна допускать добавление других языков без изменения доменной модели.

Даты, время и часовые пояса должны обрабатываться явно.

## 18. Accessibility

Интерфейс должен следовать разумным требованиям доступности:

- keyboard navigation;
- labels для form controls;
- достаточный визуальный контраст;
- понятные validation messages;
- отсутствие зависимости от цвета как единственного сигнала состояния.

## 19. Maintainability

Код и архитектура должны обеспечивать:

- разделение доменов;
- тестируемость бизнес-логики;
- отсутствие циклических зависимостей между модулями;
- явные API contracts;
- документированные архитектурные решения.

## 20. Portability

Система должна разворачиваться на Linux + Docker.

Нельзя делать критичную бизнес-функциональность зависимой от конкретного VPS/vendor.

Переезд с собственного сервера на VPS не должен требовать изменения бизнес-логики.

## 21. Acceptance Criteria

- [ ] Производительность измеряется на уровне API и имеет определённые targets.
- [ ] Все большие списки поддерживают server-side pagination/filtering.
- [ ] Backend остаётся stateless насколько это возможно.
- [ ] Backup включает БД и пользовательские файлы.
- [ ] Restore проверяется процедурно.
- [ ] Критичные действия аудируются.
- [ ] Health/readiness endpoints предусмотрены.
- [ ] Secrets отделены от version-controlled configuration.
- [ ] External integrations не ломают core CRM при недоступности.
- [ ] PostgreSQL является source of truth для транзакционных данных.
- [ ] Storage абстрагирован.
- [ ] Production deployment рассчитан на Linux + Docker.
