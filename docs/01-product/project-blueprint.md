# TourCRM — Project Blueprint

**Статус:** Draft / живой документ

## 1. Назначение

TourCRM — многопользовательская web-система для управления школьным туристским клубом. Система объединяет CRM-функции, управление учебным процессом и мероприятиями, учёт туристской деятельности, базу знаний, документы, финансы, оборудование, коммуникации и аналитику.

Система ориентирована на desktop, tablet и mobile и должна одинаково поддерживать работу через локальную сеть и интернет.

## 2. Принцип единого источника истины

Репозиторий TourCRM является источником актуальной проектной документации. Существенные продуктовые, архитектурные и технические решения должны быть отражены в документации и, когда решение влияет на архитектуру, в ADR.

Кодовая реализация не должна самостоятельно вводить новые существенные бизнес-правила, которые не определены документацией. При обнаружении неоднозначности разработчик обязан создать или уточнить Issue, а не молча выбирать произвольное поведение.

## 3. Заинтересованные стороны и зоны ответственности

### Инициатор / владелец продукта

Отвечает за бизнес-цели, приоритеты, предметную область и окончательные продуктовые решения.

### Системный и технический аналитик

Отвечает за сбор и структурирование требований, архитектурную модель, технические ограничения, доменную модель, API-контракты, правила доступа, документацию, ADR и постановку задач.

### Claude / разработчик

Отвечает за реализацию требований: код, тесты, Docker, CI/CD и технические изменения в репозитории в пределах согласованных Issue.

## 4. Основные пользовательские роли

- Администратор клуба.
- Инструктор.
- Участник клуба.
- Родитель / законный представитель.

Один пользователь может одновременно иметь несколько ролей. Модель полномочий должна быть расширяемой для будущих ролей.

## 5. Ключевые домены

1. Аутентификация и авторизация.
2. Пользователи и профили.
3. Членство в клубе.
4. Родители и законные представители.
5. Группы.
6. Мероприятия и расписание.
7. Посещаемость.
8. Походы и туристский опыт.
9. Маршруты и GPX.
10. Навыки, квалификации, достижения и рейтинг.
11. База знаний.
12. Документы и согласия.
13. Финансы.
14. Снаряжение.
15. Уведомления и коммуникации.
16. Турслёты и внешние интеграции.
17. Аналитика и отчётность.
18. Аудит действий.

## 6. Базовые архитектурные принципы

- Адаптивный web вместо отдельного мобильного приложения на первом этапе.
- API-first backend.
- Чёткое разделение доменных сущностей, учётных записей и членства.
- RBAC с возможностью расширения до granular permissions.
- PostgreSQL как основная транзакционная БД.
- Файлы и медиаданные не хранятся в PostgreSQL как основной механизм хранения.
- Асинхронные/фоновые операции выделяются в отдельный механизм; Redis вводится по мере появления реальных требований.
- Внешние системы подключаются через явные интеграционные контракты.
- Все критичные действия с персональными и финансовыми данными должны быть аудируемыми.
- Бизнес-правила должны быть тестируемыми и не зависеть от UI.
- Конфигурация и secrets отделяются от исходного кода.

## 7. Жизненный цикл разработки

Для каждой задачи действует последовательность:

`Issue → анализ требований → реализация Claude → автоматические проверки → проверка результата → закрытие Issue`.

Нельзя считать задачу завершённой только потому, что код собирается. Acceptance Criteria должны быть выполнены полностью.

## 8. Предварительная технологическая основа

### Frontend

- React.
- TypeScript.
- Компонентная архитектура.
- Адаптивная вёрстка.

### Backend

- Python.
- FastAPI.
- SQLAlchemy.
- Alembic.

### Data

- PostgreSQL.
- Redis — по необходимости для cache/background jobs/очередей.

### Infrastructure

- Linux LTS.
- Docker / Docker Compose.
- GitHub Actions.
- Reverse proxy определяется отдельным ADR.

Окончательные версии зависимостей фиксируются при создании технического baseline и проверяются по актуальным стабильным версиям на дату реализации.

## 9. Целевая стартовая инфраструктура

- 4 vCPU.
- 16 GB RAM.
- 256 GB SSD — минимально рекомендуемый основной диск.
- 512 GB SSD — предпочтительный размер.
- Linux LTS.
- Docker / Docker Compose.
- PostgreSQL.
- Отдельное или внешнее хранилище для резервных копий.

## 10. Нефункциональные требования верхнего уровня

### Доступность

Система должна работать как в локальной сети клуба/школы, так и через интернет без изменения прикладной логики.

### Производительность

Обычные CRUD-операции интерфейса должны выполняться без необходимости ручного обновления страницы и без зависания UI. Точные SLO/latency targets будут зафиксированы отдельной NFR-спецификацией после оценки объёма данных.

### Безопасность

Доступ к данным строится на принципе минимально необходимых полномочий. Особенно защищаются данные несовершеннолетних, родителей, документы, финансовая информация и аудит.

### Аудируемость

Критичные изменения должны позволять установить актор, время, объект, действие и результат операции.

### Расширяемость

Новые роли, типы мероприятий, каналы уведомлений, виды туризма и интеграции не должны требовать переписывания базовой архитектуры.

## 11. Отложенные решения

Следующие вопросы намеренно не считаются окончательно решёнными до появления дополнительной информации:

- точная интеграционная модель существующего сайта турслётов;
- SSO между TourCRM и турслётами;
- окончательный reverse proxy;
- конкретный провайдер файлового/object storage;
- интеграция с календарями;
- конкретные правила финансового учёта;
- окончательная модель коммуникаций и чатов;
- детальные юридические требования к согласию родителей и обработке ПД.

## 12. Definition of Done для документации

Документ считается достаточным для передачи в разработку, когда требование:

1. однозначно сформулировано;
2. имеет понятный объект/домен;
3. не противоречит другим требованиям;
4. содержит ограничения и права доступа, если они применимы;
5. допускает автоматическое тестирование или объективную проверку;
6. не требует от разработчика угадывать бизнес-логику.
