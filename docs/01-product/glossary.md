# TourCRM — Glossary

Документ определяет термины, которые должны использоваться одинаково в требованиях, API, БД, интерфейсе и Issues.

| Термин | Определение |
|---|---|
| Club | Конкретный школьный туристский клуб, обслуживаемый данной инсталляцией TourCRM. Архитектурно сущность сохраняется даже при одном клубе. |
| User | Учётная запись для аутентификации и авторизации в системе. Не является автоматически физическим лицом или членом клуба. |
| Person | Физическое лицо. Используется как базовый субъект для участника, родителя, инструктора и других ролей. |
| Membership | Связь физического лица с клубом с определённым статусом и периодом действия. |
| Role | Набор полномочий пользователя внутри системы. Один пользователь может иметь несколько ролей. |
| Permission | Атомарное право выполнить действие над определённым ресурсом/доменом. |
| Member / Участник | Человек, имеющий членство в туристском клубе и относящийся к категории участников клуба. Статус участника не является технической ролью User и определяется доменными связями/атрибутами членства. |
| Instructor / Инструктор | Человек, выполняющий инструкторские функции в клубе. Инструкторство не исключает наличие других доменных связей и ролей. Например, один Person может одновременно быть участником, инструктором и guardian другого участника. |
| Guardian / Законный представитель | Родитель или иной законный представитель несовершеннолетнего участника, связанный с ним через GuardianRelationship. Наличие такой связи само по себе не выдаёт полный доступ к профилю ребёнка. |
| Group | Организационная учебная группа клуба. |
| Event | Базовое календарное мероприятие. Может иметь тип занятия, тренировки, похода, соревнования, турслёта и т. д. |
| Lesson | Мероприятие учебного типа. |
| Trip | Поход/выезд, содержащий туристские характеристики, состав группы, маршрут и результаты. |
| Route | Логическое описание туристского маршрута. |
| GPX Track | Файл/трек геоданных маршрута или фактического прохождения. |
| Attendance | Факт присутствия конкретного человека на мероприятии с возможным статусом и причиной отсутствия. |
| Achievement | Достижение участника, назначенное вручную или полученное по автоматическому правилу. |
| Skill | Туристский навык, которым владеет или должен овладеть человек. |
| Qualification | Формализованная квалификация/разряд/подтверждённый уровень подготовки. |
| Knowledge Article | Материал базы знаний клуба. |
| Document | Файл или логическая запись документа, относящегося к человеку, событию или клубу. |
| Consent | Юридически значимое согласие/разрешение, связанное с участником или его законным представителем. |
| Equipment | Единица материального имущества/снаряжения клуба. |
| Payment | Поступление денежных средств, относящееся к участнику, событию или клубу. |
| Expense | Расход денежных средств клуба или мероприятия. |
| Notification | Системное сообщение, предназначенное одному или нескольким пользователям. |
| Integration | Взаимодействие TourCRM с внешней системой через определённый контракт. |
| Audit Log | Неизменяемая или контролируемая история значимых действий пользователей и системных операций. |
| Feature Flag / System Setting | Настройка, разрешающая или запрещающая функциональность без изменения исходного кода. |
| Active | Состояние, при котором сущность допускает обычное использование согласно бизнес-правилам. |
| Archived | Состояние, при котором данные сохраняются для истории, но исключаются из обычных рабочих процессов. |

## Правило терминологии

В англоязычных именах API и БД используются термины таблицы выше. В UI допускается человекочитаемый русский эквивалент. Один и тот же доменный объект не должен называться разными техническими именами в разных модулях без документированного основания.

## Правило идентичности

`Person`, `User`, `ClubMembership` и `RoleAssignment` — разные понятия и не должны объединяться в одну техническую сущность.

Один `Person` может иметь несколько независимых доменных связей, например:

- быть участником клуба;
- быть инструктором;
- быть guardian одного или нескольких участников.

Эти факты не должны моделироваться как взаимоисключающие статусы одного поля.
