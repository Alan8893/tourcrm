# TourCRM — Medical Data Specification

## 1. Назначение

Документ определяет технические правила работы с медицинскими и иными чувствительными сведениями участников. Документ не является юридической политикой и не устанавливает юридические сроки хранения.

## 2. Принцип минимизации

Медицинские данные не являются обязательной частью базового профиля Person.

В систему разрешается добавлять только те медицинские сведения, для которых клуб определил конкретную рабочую необходимость, правовое основание и срок хранения.

## 3. Классы данных

### 3.1. Не медицинские данные

Контактные и организационные сведения участника хранятся в обычном профиле Person.

### 3.2. Медицинские сведения

Потенциально чувствительные данные должны быть выделены в отдельный доменный контур. Примеры:

- ограничения по участию;
- аллергии;
- сведения, критичные для экстренной помощи;
- медицинские допуски;
- документы медицинского характера.

Свободные медицинские заметки не должны становиться способом неограниченного хранения медицинской истории.

## 4. Рекомендуемая модель

Медицинские сведения должны быть разделены как минимум на:

- `MedicalProfile` — ограниченный набор структурированных полей, разрешённых политикой клуба;
- `MedicalDocument` — документ/файл, подтверждающий сведения;
- `MedicalAccessGrant` — при необходимости дополнительное ограничение доступа.

Конкретный набор полей утверждается отдельным решением клуба.

## 5. Доступ

По умолчанию:

- участник может видеть свои медицинские сведения в пределах разрешённого self-scope;
- родитель может видеть сведения ребёнка только при действующей связи Guardian и наличии соответствующего permission;
- инструктор не получает автоматически доступ ко всем медицинским данным клуба;
- инструктор получает только минимально необходимый набор operational-critical данных для связанных мероприятий, если это разрешено политикой клуба;
- администратор имеет расширенный доступ в рамках своих полномочий;
- API обязан повторно проверять доступ независимо от ограничений UI.

## 6. Operational-critical сведения

Для мероприятия может существовать производное ограниченное представление, содержащее только сведения, реально необходимые руководителю/инструктору.

Например, вместо полного медицинского профиля мероприятие может получать:

- наличие критического ограничения;
- наличие аллергии, влияющей на питание или безопасность;
- необходимость учёта экстренного контакта;
- ссылку на подтверждающий документ без автоматического раскрытия всего документа.

## 7. Хранение файлов

Медицинские документы хранятся через общий storage abstraction и не должны напрямую публиковаться по постоянному URL.

Доступ к файлу предоставляется через авторизованный backend flow или короткоживущую защищённую ссылку, если такая схема будет утверждена.

## 8. Аудит

Все административные действия с медицинскими данными подлежат аудиту.

В audit log запрещено записывать:

- полное содержимое медицинского профиля;
- содержимое медицинского документа;
- токены доступа;
- пароли и секреты.

Аудит должен фиксировать факт действия, субъект, объект, actor, timestamp и результат.

## 9. Экспорт

Медицинские сведения не включаются в обычные экспортные отчёты по умолчанию.

Для включения медицинских данных экспорт должен явно указывать:

- состав включаемых полей;
- назначение;
- инициатора;
- scope;
- формат;
- факт экспорта в аудит.

## 10. Retention

Юридические и внутренние сроки хранения должны задаваться отдельной политикой. Техническая реализация должна поддерживать для медицинских данных:

- дата создания;
- дата последнего изменения;
- дата истечения, если применимо;
- статус archived;
- дата удаления/анонимизации при выполнении политики.

## 11. Запреты

Система не должна:

- хранить медицинские данные в логах приложения;
- отправлять их в Telegram/MАX/email без специально определённой политики и явного сценария;
- индексировать свободный медицинский текст в общем поиске без отдельного решения;
- отдавать медицинские документы по незащищённым публичным URL;
- использовать feature flags для обхода security permissions.

## 12. Acceptance Criteria

- Медицинские данные физически/логически отделены от обычного Person profile.
- Permissions для доступа проверяются на backend.
- Есть отдельный audit trail доступа/изменений.
- Обычный экспорт не содержит медицинские сведения.
- Медицинские файлы проходят через защищённый storage flow.
- Реализована возможность применения срока истечения/архивирования без изменения модели данных.
- В системе нет логирования содержимого медицинских данных.

## 13. Открытые решения

До начала реализации медицинского контура должны быть отдельно утверждены:

1. точный состав полей MedicalProfile;
2. перечень operational-critical данных, доступных инструктору;
3. юридические основания и сроки хранения;
4. требования к подтверждающим документам;
5. правила экстренного доступа при мероприятии.
