# Infrastructure

## Стартовая конфигурация

Для первого развёртывания рекомендуется:

- CPU: 4 vCPU;
- RAM: 16 GB;
- storage: минимум 256 GB SSD, рекомендуется 512 GB SSD;
- OS: Linux LTS;
- container runtime: Docker + Docker Compose;
- сеть: Gigabit Ethernet при наличии;
- резервное копирование: отдельный физический/сетевой носитель или внешнее хранилище.

128 GB HDD не рекомендуется как основной диск. В системе предполагается хранение PostgreSQL, документов, фотографий, GPX-файлов, фотографий мероприятий и резервных копий; SSD предпочтителен для базы данных и общего отклика приложения.

## Логическая структура

```text
Internet / LAN
      |
      v
 Reverse Proxy
      |
 +----+------------------+
 |                       |
 v                       v
Frontend               Backend API
                         |
                  +------+------+
                  |             |
                  v             v
              PostgreSQL      Redis*
                  |
                  v
              File Storage

* Redis используется при необходимости для кэширования, фоновых задач,
  rate limiting и очередей.
```

## Контейнеризация

На первом этапе сервисы размещаются в Docker Compose. Архитектура должна позволять позднее перенести компоненты на Kubernetes или другую оркестрацию без изменения бизнес-логики, если масштаб проекта это потребует.

## Среды

Предусмотреть минимум:

- development;
- production.

Позднее добавить staging при необходимости.

## Backup

Резервные копии должны охватывать как минимум:

- PostgreSQL;
- загруженные документы и файлы;
- конфигурацию приложения, не содержащую секретов в открытом виде;
- критические данные интеграций.

Backup должен проверяться восстановлением, а не только фактом создания архива.

## Мониторинг и логирование

Предусмотреть:

- состояние контейнеров;
- доступность приложения;
- ошибки backend/frontend;
- состояние PostgreSQL;
- заполнение диска;
- CPU/RAM;
- срок и успешность последнего backup.

Персональные данные не должны попадать в технические логи без необходимости.

## Доступ из LAN и Internet

Приложение должно быть доступно по HTTP(S) внутри локальной сети. Удалённый доступ через интернет реализуется через reverse proxy и защищённое соединение. Внутреннее размещение не должно означать отсутствие аутентификации и контроля доступа.

## Перспективный перенос

Развёртывание на собственном сервере не должно создавать жёсткой зависимости от конкретного железа. Целевая возможность — перенос контейнеризированного приложения и PostgreSQL на российский VPS или другое Linux-окружение с минимальными изменениями.
