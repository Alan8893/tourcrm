# TourCRM — Data Retention and Deletion

## 1. Назначение

Документ является каноническим местом для правил хранения, архивирования и удаления данных TourCRM.

Он не устанавливает сроки хранения сам по себе: конкретные сроки и основания должны быть утверждены Product Owner с учётом применимого законодательства и политики клуба.

## 2. Текущий статус

**Статус: частично определён, реализация политики хранения заблокирована.**

Общие требования к сохранению истории и аудиту существуют в нормативной документации проекта, однако конкретные сроки хранения и правила удаления для категорий данных пока не утверждены.

Открытое архитектурное решение: **ODR-013 — retention and deletion policy** в `docs/03-architecture/adr/ADR-0008-open-decisions.md`.

До закрытия ODR-013 Claude не должен самостоятельно выбирать сроки хранения, правила окончательного удаления, исключения из удаления или retention для AuditLog/security events.

## 3. Категории данных, для которых требуется отдельное решение

Минимально необходимо определить политику для:

- персональных данных (`Person` и связанных membership records);
- аутентификационных и security events;
- audit records;
- файлов и их метаданных;
- финансовых операций;
- событий, поездок и другой операционной истории;
- документов, согласий и связанных версий;
- импортов/экспортов и технических журналов, если они содержат данные предметной области.

Для каждой категории необходимо определить:

- срок хранения;
- начало отсчёта срока;
- условия архивирования;
- условия окончательного удаления;
- допустимость/необходимость сохранения истории;
- связь с юридическими обязанностями или политикой клуба, если применимо;
- кто имеет право инициировать удаление/архивирование;
- требования к аудиту самого удаления/архивирования.

## 4. Audit retention

На текущем этапе нельзя считать срок хранения AuditLog определённым.

Audit infrastructure может быть реализована только после того, как Product Owner утвердит как минимум:

1. срок хранения audit records;
2. правила удаления/архивирования audit records;
3. допустимые основания для досрочного удаления, если такие основания вообще существуют;
4. связь audit retention с общими правилами персональных данных.

## 5. Удаление и архивирование

TourCRM не должен трактовать `DELETE` как автоматическое окончательное уничтожение исторически значимой информации.

Для каждой сущности необходимо отдельно определить, является ли операция:

- физическим удалением;
- логическим удалением/деактивацией;
- архивированием с сохранением истории;
- запрещённой операцией удаления.

Нельзя добавлять универсальный механизм hard-delete для всех сущностей без соответствующего доменного решения.

## 6. Текущие ограничения реализации

До закрытия ODR-013:

- не внедрять автоматическое удаление по сроку давности;
- не внедрять retention jobs;
- не задавать TTL для audit/security records;
- не считать конкретный срок хранения частью модели данных;
- не использовать отсутствие retention policy как основание для удаления исторических записей.

## 8. Правило изменения

После принятия Product Owner решения соответствующая политика должна быть отражена в этом документе и, если изменение является архитектурным решением, зафиксирована отдельным ADR. Только после этого реализация может использовать утверждённые правила retention/deletion.
