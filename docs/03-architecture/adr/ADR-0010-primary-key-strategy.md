# ADR-0010 — Primary key strategy

## Status

Accepted.

## Context

TourCRM contains many independently created entities, must expose resource identifiers through APIs, and may eventually integrate with external systems. IDs should not encode business meaning and should be safe to expose where appropriate.

## Decision

Use UUID-based primary identifiers for domain entities exposed through APIs or referenced across domains.

Requirements:

- IDs are generated by the application/database using a cryptographically strong UUID mechanism supported by the chosen PostgreSQL/Python stack;
- IDs carry no business meaning;
- API clients must treat IDs as opaque strings;
- external identifiers from integrations are stored separately from internal primary IDs;
- human-readable numbers (for example equipment inventory numbers or document numbers) are separate business identifiers;
- database foreign keys use the same ID type as their referenced primary keys;
- identifiers are immutable for the lifetime of the entity.

The implementation may select an appropriate UUID representation supported cleanly by PostgreSQL and SQLAlchemy. The exact UUID version/storage representation is an implementation-level decision and must be documented before code is merged.

## Rationale

UUIDs reduce accidental coupling to insertion order, simplify distributed/integration scenarios and avoid making internal IDs meaningful to users.

## Consequences

- URLs and API payloads use opaque UUIDs.
- Numeric sequential identifiers must not be introduced merely for convenience.
- Business-facing codes require explicit fields and uniqueness rules.
