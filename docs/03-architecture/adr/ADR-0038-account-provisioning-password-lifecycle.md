# ADR-0038 — Account Provisioning and Password Lifecycle

**Status:** Accepted  
**Date:** 2026-09-20  
**Decision type:** PO Decision  
**Scope:** Authentication / People Management

## Context

TourCRM allows an administrator to create a Person and, where required, provide that Person with a system account. The administrator must be able to recover access for a user, but the product should not make the administrator the holder of the user's permanent password.

The existing Authentication API already defines password change and password-reset flows, one-time reset tokens, password policy enforcement, and security auditing.

## Decision

### 1. Administrator never sets or receives a user's permanent password

The administrator does not choose a user's permanent password and cannot read an existing password.

### 2. First account access uses a one-time setup credential

When an administrator creates/enables a user's account, the user receives a one-time setup/reset challenge.

On first access the user must:
1. authenticate with the one-time setup credential;
2. enter a new password;
3. confirm the new password.

The permanent password is then established by the user.

The one-time credential becomes invalid after successful password setup or expiry.

### 3. MVP fallback when email delivery is not available

The first implementation may provide the administrator with a one-time temporary credential generated by the system.

The administrator may copy/provide that temporary credential to the user.

This credential is explicitly temporary and MUST be replaced by the user on first access.

The system must never display or return the user's permanent password.

### 4. Normal login

After first setup, normal authentication uses the existing login contract: identifier + password.

### 5. User-initiated password change

An authenticated user can change their own password through the canonical password-change operation.

The current password must be verified before changing it.

### 6. Password recovery

The existing password-reset flow remains the canonical recovery mechanism:
- request reset;
- receive/use one-time reset challenge;
- set a new password;
- enforce expiry and single-use semantics.

### 7. Administrator password reset

An administrator must have an explicit Reset password action for a managed user account.

The administrator action does not expose the existing password and does not set a permanent password.

It creates a new one-time setup/reset credential.

The exact API endpoint and UI implementation are deferred to the implementation task and must reuse the existing authentication security model rather than introduce a parallel password mechanism.

### 8. Security

Passwords, raw reset/setup tokens and other credentials are never returned through ordinary API responses.

Password setup/reset operations must be audited as security events.

Rate limiting, brute-force protection, token expiry and single-use semantics remain mandatory.

## Consequences

- Administrators can recover access without knowing users' permanent passwords.
- Users establish their own permanent credentials.
- The same model works with future email-based delivery.
- MVP can operate before email delivery infrastructure is complete.
- A dedicated administrative reset operation is required in the future implementation slice.

## Explicitly not decided here

This ADR does not define:
- email provider or delivery mechanism;
- MFA;
- password policy values;
- invitation UI;
- account creation UI;
- exact administrative reset endpoint name;
- automatic role assignment.
