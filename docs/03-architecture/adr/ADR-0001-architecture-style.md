# ADR-0001: Архитектурный стиль TourCRM

## Статус
Accepted

## Контекст

TourCRM должен обслуживать одного школьного туристского клуба, но архитектурно сохранять границы доменов и возможность дальнейшего масштабирования. Система включает CRM, расписание, мероприятия, туристскую деятельность, документы, финансы, снаряжение, коммуникации и интеграции.

## Решение

Используется модульный backend с чёткими доменными границами внутри одного приложения (modular monolith) на первом этапе.

Основные слои:

- Web frontend;
- API/application layer;
- domain/module layer;
- persistence/data access;
- background jobs;
- file/object storage;
- external integrations.

Разделение на отдельные deployable services не требуется для MVP.

## Причины

- существенно проще эксплуатация на стартовом сервере;
- проще транзакции между тесно связанными доменами;
- меньше инфраструктурной сложности;
- доменные границы сохраняются и позволяют выделить сервисы позже;
- легче реализовать последовательную разработку Claude.

## Ограничения

Модули не должны обращаться к таблицам другого домена в обход определённых service/application contracts. Прямой доступ к чужим внутренним repository/model API запрещается без документированного основания.

## Последствия

Первоначальная система проще в эксплуатации, но требует дисциплины архитектурных границ внутри монолита.

## Альтернативы

### Microservices
Отклонено для MVP из-за избыточной инфраструктурной сложности.

### Полностью неструктурированный monolith
Отклонено из-за высокого риска связности и невозможности дальнейшего масштабирования.
